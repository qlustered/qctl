## USAGE

    qctl alert resolve <alert-id>
    qctl alert retract <alert-id>
    qctl alert submit
    qctl describe alert <id>
    qctl download alert-report [table-id-or-name]
    qctl get alerts

## EXAMPLES

    # unresolved alerts in the org (pass --resolved to see resolved ones)
    qctl get alerts

    # alerts raised on one table
    qctl get alerts --table orders

    # alerts across the period tables of one series
    qctl get alerts --series "Monthly reports"

    # the row-level alerts on one file's quarantined rows, each count exact for the file
    qctl get alerts --file-id 55

    # only the alerts of one issue type (tab-completes; the server validates)
    qctl get alerts --issue-type severe_rule_bug

    # late intakes, with the period each one is late for
    qctl get alerts --issue-type late_file --columns id,data_source_model_name,period_key,msg

    # everything except the series routing and late-intake alerts (repeatable)
    qctl get alerts --exclude-issue-type series_file_routing --exclude-issue-type late_file

    # every unresolved alert one table rule raised, row-level ones included
    qctl get alerts --table orders --rule email_check

    # alerts a change proposal holds, with the proposal's id and state
    qctl get alerts --has-change-proposal

    # only those waiting on a reviewer
    qctl get alerts --change-proposal-state pending_review

    # full detail for one alert
    qctl describe alert 123

    # the quarantine rows a row-level alert holds (describe alert prints this line)
    qctl get data orders --is-bad-data --alert-item-id 8817

    # hand the backlog to a person: an Excel workbook of the unresolved issues and the rows each one holds
    qctl download alert-report orders

    # alerts only, each listed row named by two columns
    qctl download alert-report orders --include-warnings=false --key region --key order_no

    # confirm a draft schema migration
    qctl alert resolve 123 --action apply_migration

    # a mirror or append table's first migration also chooses its key columns (describe table-schema lists candidates)
    qctl alert resolve 123 --action apply_migration --key-columns order_id

    # ...or records that the table has none
    qctl alert resolve 123 --action apply_migration --no-key-columns

    # permanently stop anomaly detection on a column (also resolves sibling anomaly alerts)
    qctl alert resolve 124 --action ignore_column_for_future_anomalies --yes

    # discard it instead
    qctl alert resolve 123 --action discard_migration

    # an action that needs input: write the manifest, edit it, send it
    qctl alert resolve 9 --action map_value --dry-run > fix.yaml
    qctl alert resolve -f fix.yaml

    # keep a cell fix: fill in spec.ids, leaving new_value out to keep the current fix
    qctl alert resolve 9 --action reapply_cell_override --dry-run > keep-fix.yaml
    qctl alert resolve -f keep-fix.yaml

    # a file waiting for its reporting period: choose the period in a manifest, then send it
    qctl alert resolve 9 --action assign_reporting_period --dry-run > period.yaml
    qctl alert resolve -f period.yaml

    # discard only file 123 of an alert that holds several files; the alert stays open while another is kept
    qctl alert resolve 9 --action trash_file --file-id 123 --comment "sent twice"

    # initial_fields or unexpected_field_name: generate column mappings without an action
    qctl alert resolve 9 --dry-run > columns.yaml
    qctl alert resolve -f columns.yaml

    # raise your own alert on a cell of a quarantined row (this HOLDS the row)
    qctl alert submit --table orders --row 1042 --field amount --comment "wrong FX rate"

    # ...with a value you think it should hold
    qctl alert submit --table orders --row 1042 --field amount --comment "wrong FX rate" --suggest 1420.00

    # withdraw it again ("I flagged the wrong cell")
    qctl alert retract 8817 --row 1042 --yes

## GOTCHAS


- `describe alert` shows a `cell_override_conflict` alert's fix as `spec.field_value`, with `spec.body.pipeline_value`, `pipeline_value_is_number` and `base_displaced_value` at default verbosity and `-v`. Numeric values use the applied column's display format, fetched from the table schema; `-vv` keeps stored values and skips that lookup. Explicit nulls stay null and an absent baseline stays absent. Upstream numeric text is converted from stored units when `pipeline_value_is_number` is true; an explicit false keeps source text unchanged. Composite alerts omit the flag and their upstream text is treated as stored data. Baseline text on a percent column is kept as sent, while a numeric baseline such as `0.125` displays as `12.50%`. A failed schema lookup warns that values use stored units. `get data --include-issues` shows the backend's message, which already names the three values in display units. [backend]
- `describe alert` leaves a masked cell-override conflict's `field_value`, `pipeline_value` and `base_displaced_value` as the server sent them — mask text, never converted to the column's display units — whenever `masked_fields` names the alert's field. [backend]
- For `cell_override_conflict`, `discard_cell_override` takes the upstream value and `reapply_cell_override` keeps the fix; both require a non-empty `ids` list in an `AlertResolution` manifest. With reapply, omit `new_value` to keep the fix or supply it to edit the fix. On composite tables, reapply requires an active override on every selected row (otherwise 404); discard skips rows with no active override. NEXT ACTIONS and the generated manifest print the full backend notes for both actions. [backend]
- `get alerts --series` accepts an exact, case-sensitive table-series name or full UUID, using the same resolver as `get tables --series`. The table view prints the echoed series name and UUID on stderr, including for empty results and pages past the end. JSON/YAML List output includes the echoed `series` object when present; `-o name` keeps the usual alert references.
- `get alerts --file-id <id>` lists only the row-level alerts on the file's live quarantined rows, and each `count` is how many of that file's rows carry the alert, exact and never capped (`count_capped: false`); the table view says so in one line on stderr. qctl sends `is_row_level=true` with it, because the server matches only row-level alerts for a file while defaulting `is_row_level` to false, so `--is-row-level=false` with `--file-id` exits 2. It intersects with `--table`, `--table-id` and `--series`, and an unknown file id is a 404. [backend]
- `get alerts --series` intersects with `--table` or `--table-id` and the other server-side filters; a table outside the series returns no alerts. [backend]
- A locked period's unresolved alerts are hidden from `get alerts`, including with `--series` or a table selector, except `series_file_routing` and `late_file` alerts. Resolved alerts remain listable with `--resolved`; unlocking the period makes its unresolved alerts visible again. [backend]
- Integer fields in a YAML manifest reject fractional numbers during parsing (exit 2): `2.7` is refused instead of becoming `2`. Whole-valued YAML numbers such as `2.0` remain accepted.
- While waiting for a prepared download, `--wait-timeout` and SIGINT/SIGTERM cancel an inbox poll in flight, including a request waiting to retry; a successful response arriving after cancellation is discarded.

- An unresolved `needs_review_migration` alert's NEXT ACTIONS footer points to `qctl get rule-suggestions --table-id <id> --show-params` to inspect pending rule proposals before resolving the schema review.

- Before `apply_migration`, both `--action` and `-f` list the table's running ingestion jobs on stderr, including dry-run carriers, with a describe command for each. This preview runs under `--yes`; a failed job lookup warns without refusing confirmation. A successful confirmation can still leave the schema waiting for those jobs: `qctl guide unblock-table` explains the wait.
- `alert resolve -f` and `alert propose -f` reject a non-empty `spec.key_columns` or `spec.no_key_columns: true` on a column mapping (`spec.field_names_resolution`, on either alert type) locally with exit 2 before posting.
- At a required key step, the missing-choice refusal suggests explicitly reusing the previous period's keys when the schema response marks them reusable. It still requires `--key-columns` or `spec.key_columns`; it does not fill in the choice.
- `initial_fields` and `unexpected_field_name` accept column mappings in `spec.field_names_resolution` without `spec.action`; each entry supplies `incoming_field_name`, `field_name`, `operation` (`new`, `map`, `delete`), `scope` (`dataset`, `data_source_model`, `stored_item`), and optional `expand`. An empty `field_name` is valid: `new` uses the normalized incoming name, while `delete` ignores the incoming column. The backend checks mapping targets and permissions, and a successful submission may leave the alert open until its migration completes. Neither alert type takes key columns with a mapping: the backend accepts `key_columns` and `no_key_columns` only with `apply_migration` on a `needs_review_migration` alert. [backend]
- For a column-mapping alert, `qctl alert resolve <id> --dry-run` generates a template without `--action`; fill it in and send it with `-f`. qctl rejects an unedited template, empty mappings, a mapping combined with an action or unrelated request fields, and a mapping for another alert type or an alert already resolved or parked behind a migration. Structured results keep `action` as an empty string for column mappings. The template lists the scopes in the alert's `field_mapping_scopes` and prefills each `scope` with the first, the widest (`alert propose --dry-run` lists all three and prefills none, because the approver's role decides); it comments each entry with the server's recommended operation and target and with `blank in this file`, and ends with a `table columns:` comment block of `name (label) [required]` that flags a required column absent from the file that no column with data is recommended for. With no `field_mapping_scopes` on the alert, the template lists all three scopes and leaves `scope` blank. `describe alert` shows `spec.field_mapping_scopes` and names the scopes in its NEXT ACTIONS column-mapping entry.
- `alert resolve -f` refuses, exit 2 before sending, a column mapping that writes at a scope the alert's `field_mapping_scopes` leaves out, which is the same mapping the server answers with 403: a `delete`, a `map` naming a column, or an `expand`. `alert propose -f` sends it anyway, and an alert without `field_mapping_scopes` is never checked.
- On an unresolved `initial_fields` or `unexpected_field_name` alert that you may resolve without an action, the server sends `field_mapping_scopes`, the scopes your role may give a column mapping, widest first: `dataset`, `data_source_model` and `stored_item` for ops, admin, member and agent, and only the last two for any other role, editors included. Only a mapping that writes at `dataset` is refused with 403: a `delete`, a `map` naming a column, or an `expand`. A `new` ignores `scope` and always adds the column to the table, which only ops and admin may do, and a `map` with an empty `field_name` is accepted at any scope. A proposal's mappings are checked against the role of the approver, not the author. [backend]
- On `unexpected_field_name`, a column mapping is refused with 422, naming each column by its label, when a required table column gets no data from the file: no file column feeds it, or every file column that feeds it is blank. A column is required when an enabled Required value rule with severity `blocker` or `as_declared` checks it, unless an enabled rule writes the column without reading or validating it. The alert's `field_names_suggestions_info.dataset_fields` lists every table column in table order with its `label` and `required`, and each suggestion's `blank_in_file` says whether every row of the file leaves that column empty or holds one of the table's null values; on `initial_fields` the list is empty and this refusal never happens. [backend]
- `describe alert <id>` rejects a non-numeric ID locally as bad usage (exit 2), before any API request.
- `describe alert <id> -o table` renders the backend Markdown in `spec.message` before embedding `spec` in its one-line JSON cell, then prints the complete plain-text value under `Message` outside the cell. JSON/YAML behavior is unchanged, and `-vv` remains the untouched wire response.
- a row-level alert's `count` is approximate and stops at 1000: `count_capped: true` means at least 1000 rows, and `get alerts` prints such a count as `1000+` while `-o json` and `-o yaml` keep the number. The exact figure is `status.affecting_rows_count`, which `describe alert` reads from the alert's separate stats request (`raw_stats` under `-vv`); when that request fails the field is left out, one warning goes to stderr, and the describe still exits 0. A table-level alert (`is_row_level` false) gets no stats request and no `affecting_rows_count`: its `count` is how many times it was reported. [backend]
- which kind a failure raises is decided by the table rule's `spec.severity` policy together with the severity the rule gave that particular issue, and it is no longer a conjunction of two switches: the policy is applied once, where the issue is minted — and what lands here is whatever that resolves to `blocker`. So `spec.severity: blocker` sends every finding of that rule here, `warning` sends every data-quality finding to `qctl get warnings` instead (a configuration error — an undeclared write, or a row filter that does not compile or misses its column — lands here whatever the policy), and `as_declared` sends each finding wherever the rule itself marked it — under `as_declared` a rule that only ever emits warning-severity issues raises no alert, and one emitting both raises an alert and a warning on the same row. Flip it on the rule (`qctl explain table-rule`), not on the alert, and expect the change to be retroactive in one direction only: once the new `severity` reaches the live rule (a patch validated as a revalidation candidate gets there on promotion, see `qctl guide triage-alerts`), the backend reprocesses the bad rows that rule already quarantined, on a mirror-loaded table too, so loosening the policy releases rows — but that reprocess never reaches back into rows already accepted as clean. An upload that re-sends those rows validates them under the new policy and quarantines one that now fails — on a mirror-loaded table that is the next mirror upload, on an append table a new version of the same file — while any other file leaves them clean; a non-series cloud source other than `simple_url` can load changed content at an ingested path with reprocessing off, and one that retains its files skips the path without downloading it while the provider's listing metadata for it is unchanged; a manual upload enables reprocessing for its own job. [backend]
- `describe alert -v` shows `spec.body.declared_severity`, and it is the RULE's value for this issue, never the alert's own: the backend writes it exactly when the two differ — so its presence IS the statement that the table rule's `spec.severity` policy overrode what the rule asked for, and its absence means the policy changed nothing, which is the common case. On an alert it can only read `warning`, promoted to `blocker`; the same key on a warning reads `blocker`, demoted. The value is in the `-v` body tier and the `-vv` dump, while the footer's `DECLARED SEVERITY` note explains it on every view but `-o json` — the machine view, which carries no footer at all. Nothing in the alert says which of the three `spec.severity` values the rule instance holds; read that off `qctl get table-rule`. [backend]
- an alert is acted on through **its own** `spec.actions` list, not through a fixed set of verbs: `qctl alert resolve <id> --action <name>` takes any name that list contains, and qctl rejects a name it does not. The list is per-alert and per-caller — the backend filters it by your role and by runtime checks — so read it from `qctl describe alert <id>` rather than assuming. Most alert **types** are not rule findings at all (header sniffing, sheet choice, datetime inference and dozens more come from ingestion). `get alerts --resolvable-by-user` filters on each alert's `resolvable_by_user` flag, which is not the same as having actions you can take: a `preload_check_held` alert carries it false yet still offers `release_held_file`, `reject_held_file` and `send_held_file_to_period` to every role but `read_only`, so that filter hides held files waiting on your decision. [backend]
- On a `mirror` or `append` table whose key columns are not locked, `apply_migration` carries the table's key choice: `--key-columns a,b` (`spec.key_columns`) sets them, replacing any already set, and `--no-key-columns` (`spec.no_key_columns: true`) records the table as keyless. `qctl describe table-schema` shows the key step: `required` (no key columns yet: the apply must send one of the two), `optional` (key columns already set: sending neither keeps them unless one is no longer a live column of the draft or is a rule output, and `no_key_columns` is refused — to go keyless, first apply the table's manifest with `spec.settings_model.key_columns: null`, which puts the table back at `required`), or none (the keys lock once a migration of the table is applied or a draft confirmed, and other loading processes take none: either field is refused). `alert resolve` and `alert propose`, on `--action` and `-f`, read that step first and refuse those cases with exit 2 before sending, the required-step refusal listing the key candidates; a failed read warns and sends. The server refuses an invalid key (empty, surrounding whitespace, reserved, not a column of the draft, deleted, a rule output) with a 422 at `body.key_columns`, and a key step that changed mid-apply with `409 ERR_MIGRATION_CONFLICT`; qctl explains both (exit 2). The confirmation states the key outcome, and the `--dry-run` manifest at the `required` step has a bare `key_columns:`, a commented `no_key_columns: true` and the candidates. Applying locks the key columns. [backend]
- `apply_migration` accepts pending `create` rule suggestions staged against its draft migration; pending `update`/`delete` suggestions on that draft block the request (`409 PENDING_SUGGESTIONS_BLOCK_MIGRATION`) until decided, except validated revalidation candidates, which pass the request gate. A suggestion carried from the table a period recreate replaced (source `recreated_period`) that reads a column the draft migration does not have and no other pending suggestion stages is dismissed instead, and naming one in `spec.accept_suggestion_ids` is a 422 at `body.accept_suggestion_ids` that applies nothing. An `-f` manifest can decide them in the same request with `spec.accept_suggestion_ids` and `spec.dismiss_suggestion_ids`: the server dismisses those, then accepts those, then accepts the draft's remaining creates, and an id that is not a pending suggestion of the draft is a 409 that applies nothing. After the schema applies, the migration job attempts to promote those candidates and to apply other pending user, profiling and carried suggestions on the table, even when they name another migration or none. A candidate may fail, be dismissed or remain pending when promotion cannot proceed; an ordinary suggestion the job cannot apply may also remain pending. qctl previews these groups before confirmation, showing carried suggestions that fit separately from misfits and naming the missing columns. An explicit accept of a known misfit exits 2 before sending. When the fit cannot be read for this draft, qctl reports that uncertainty and leaves the check to the server. Dismissing a suggestion can remove an output another carried suggestion needs, so the server rechecks fits without dismissed suggestions. A blocked request changes nothing because it rolls back. [backend]
- the `apply_migration` pre-flight reads every page of pending suggestions. It fetches full details for user suggestions to distinguish blockers and validated candidates, while compact profiling rows suffice to preview the job's work. It prints the number of user details it will check before the sequential reads; `--yes` skips the prompt but never this check.
- A code-less `apply_migration` 409 saying `These rule suggestions are not pending on the draft migration` gets guidance from `alert resolve` and `change-proposal approve` at exit 2: inspect the suggestions and remove or replace the named IDs in the resolution manifest. For a proposal, use `change-proposal edit <id> -f <file> --submit` to replace its payload for review. qctl leaves ID membership to the server because its preview omits periodic suggestions. `alert propose -f` preserves both decision lists in the proposal payload without separate suggestion writes.
- Before confirming `apply_migration`, both `--action` and `-f` warn on stderr about table rules whose row filters or column mappings read columns marked deleted or absent from the alert's draft schema. The check requires the schema response to identify that same draft and table; it lists every page of rules and shares enabled-rule detail reads between the two warnings. It prints each affected rule's state and possible outcome (`qctl explain table-schema` describes retirement, optional CAF unbinding and custom-rule effects), including under `--yes`. An unavailable or mismatched draft or a failed rule lookup warns without refusing resolution; a draft deleting no columns makes no rule lookup. `--dry-run` and other actions skip this check.
- `qctl alert resolve` drives every action an alert offers: parameterless ones with `--action` (the two trash actions with `--comment`), and ones that need other request fields with a manifest — `qctl alert resolve <id> --action <name> --dry-run` writes the skeleton, and `qctl alert resolve -f <file>` sends it. Which fields an action reads comes from the spec's `x-alert-action-fields` at runtime, so a regenerated spec changes what qctl accepts with no code change. Verified parameterless today, including: `apply_migration` (its key choice, which a required key step demands, rides `--key-columns` or `--no-key-columns`), `discard_migration`, `rerun_training`, `define_file_header`, `choose_excel_sheet`, `notify_rule_author`, `disable_rule`, `upgrade_rule_revision`, `retry_requeue`. [backend]
- qctl validates a manifest against that contract before sending anything: a missing required field, an unsatisfied one-of group (`overwrite_value` needs `ids` **or** `initial_signatures`), and a field the action does not read are each exit 2 naming what is wrong. Present means non-empty for a list, so `ids: []` is refused rather than sent as a selector that matches nothing. The action's own `note` is prose the backend marks non-machine-consumable, so qctl prints it with a 4xx instead of enforcing it. Note that choose_excel_sheet is *not* one of the actions that need input — it reopens the file's multiple_sheets_found alert, where the sheet is chosen with `proceed_with_sheet_name`, or, when the file has none, clears the file's or the cloud source's sheet choice and ingests the file again. Verified to need input today, including: `proceed_with_sheet_name`, `overwrite_value`, `allow_multi_formats_n_define_date_format`. [backend]
- forty of the eighty-nine alert actions `x-alert-action-fields` covers need a request field. `alert resolve --action` refuses only `trash_file` and `trash_alert_associated_files` without `--comment`, the one required field a flag supplies; for the rest, unlike the warning side, `alerts.ValidateAction` checks only the alert's own offered list — deliberately, there is no needs-input arm — so it sends the action and lets the backend answer (a 422 naming the missing value, exit 2), while a manifest is what actually supplies the fields. The `AlertAction` enum carries six more the map never mentions (`append_rule_param_list`, `call_webhook`, `ignore_issue_for_pattern`, `other`, `overwrite_values_for_same_rule`, `update_rule_param`) and qctl reads an absent entry as "no fields", so any of them would be driven as parameterless and a manifest setting any field for one would be refused; no issue type in `x-issue-type-alert-actions` offers one today, which is what makes that fail-open safe. [backend]
- `issue_type` is what you act on, not just what you read: it determines which actions the backend can offer, and `qctl explain alert.issue_type` lists the actions per value. Rule findings are a minority of the types — header sniffing, sheet choice, datetime inference, migration review and dozens more come from ingestion. [backend]
- an alert offering `update_configs_to_recommended_value` carries a recommendation TRIPLE in its body and `describe alert -v` prints all three parts — `recommended_settings_module_to_update`, `recommended_settings_field_name` and `recommended_settings_value` — because the module is what decides which object the field lives on, and the two producers disagree: a `migration_frozen` alert recommends `migration_policy: ask_user` on the `DataSet` while a `bad_settings` alert recommends `max_boundary_element_length` on the `SettingsModel`, and both land in one `kind: Table` manifest at different depths — top-level `spec.migration_policy` versus `spec.settings_model.<key>` — so the field name alone does not say which half to edit by hand. The action itself takes no request fields, so `qctl alert resolve <id> --action update_configs_to_recommended_value` applies it outright, and the backend offers it only when all three keys are present. `migration_frozen` is the type raised when a schema change is detected on a table whose `migration_policy` is `frozen`; it blocks neither ingestion nor profiling and the backend resolves it itself once a migration lands. [backend]
- a successful `alert resolve` call is not the same as a resolved alert: several actions return 200 after queueing background work or handing the web UI a redirect, leaving the alert open, and `validation_add_a_new_keyword` on an `invalid_keyword` alert can stage the keyword as a rule suggestion instead of adding it — a revalidation candidate when the rule is in `error` or already has one pending, or a suggestion held behind the table's draft migration — answering 200 with its `dataset_rule_suggestion_id` while the alert stays open. qctl re-reads the alert, prints that suggestion id (`dataset_rule_suggestion_id` under `-o json|yaml`) and the step that decides it: `qctl suggestion accept <uuid> --table-id <id>` for a draft-migration suggestion, which applying the migration also attempts, and `qctl describe rule-suggestion <uuid> --table-id <id>` for a revalidation candidate, which cannot be accepted because its validation run decides it. Either kind resolves the alert when it is applied, but only when the staged keyword is the alert's own value, not a different `new_value`, and the rule's `allowed` params then hold it: once the keyword is live, re-read the alert and, if it is still open, send the same resolve again, which resolves it because the keyword is then already allowed. [backend]
- the compound keyword actions — `validation_add_a_new_keyword__map_value`, `__map_value_for_field`, `__map_value_for_field_for_source`, `__map_value_for_source` and `__overwrite_value` — add `spec.new_value` as a keyword and fix the value in one request, so when the keyword would be staged rather than applied they are refused with a 409 that carries no error code, and nothing is applied. qctl recognizes the refusal by the action sent and names the two steps: `validation_add_a_new_keyword` on its own with the same `spec.new_value` (`qctl alert resolve <id> --action validation_add_a_new_keyword --dry-run` writes the manifest; without `new_value` it adds the alert's own value), followed through any suggestion it stages until the keyword is live, then the compound action again for the value fix. [backend]
- a staged keyword change holds the rule's live keyword list plus the one new keyword, and accepting it overwrites the rule's params with that list. So two keyword resolves staged behind one draft migration each carry only their own new keyword, and accepting both leaves the rule with only the one accepted last; a second keyword resolve while a revalidation candidate is pending replaces that candidate's list, dropping the first keyword. Resolve one keyword at a time, and get it live before resolving the next. [backend]
- `mark_data_as_valid` on a casting or range alert proposes a column type change; it does not restore a deleted column. A pending deletion can leave the alert open. Any non-null schema override on that column, including a deletion override, is refused first with 422 (exit 2). Without such an override, a column the backend still sees as deleted is refused with `409 ERR_MIGRATION_CONFLICT`, "Restore column ... before editing it." (exit 2). Inspect `qctl get table-schema <table-id> -o yaml`; to keep the column, restore it with a `TableSchema` block whose only change is `is_deleted: false` before other edits (see `qctl explain table-schema`), or choose another action the alert offers. Restoration still leaves a schema override, so it does not by itself unblock `mark_data_as_valid`. Migration cleanup automatically resolves casting and range alerts after the schema applies; re-read the alert before sending another resolution. [backend]
- omitting `--resolved` is not "no filter": qctl leaves the param off the wire, and the server then defaults it to `false` — so `get alerts` with no flag shows only **unresolved** alerts; pass `--resolved` to see the resolved ones. [backend]
- `get alerts` scopes to a table with `--table` (a NAME) or `--table-id` (an ID); neither accepts the other, so a table whose name is a number (`42`) is reachable with `--table 42`. The original `--dataset-id` is a hidden alias of `--table-id` and still works for scripts, but a non-positive alias or one passed together with `--table`/`--table-id` is a usage error (exit 2) checked before config or credentials, not a precedence rule.
- `get alerts` filters row-level alerts with `--is-row-level`. The original `--is-muted` is a hidden alias and still works for scripts, but passing both is a usage error (exit 2), not a precedence rule.
- a bare `get alerts` is not every open alert: besides resolved ones, the server hides ROW-LEVEL alerts (the per-row findings that hold rows in quarantine) and alerts PARKED until a schema migration lands. `--is-row-level` lists only the first kind and `--resolve-after-migration` only the second — each flag swaps which alerts are shown rather than adding them, so no single `get alerts` lists them all. No flag lists an unresolved alert on a frozen table-series period's table unless it is a `series_file_routing` or `late_file` one; `get latest-alert` and the alert counts on `describe cloud-source` and `describe profiling-job` leave it out too, and so do the table's own alert counts, which except a `series_file_routing` one alone, while `describe alert <id>` still reads it. [backend]
- `get alerts --rule <table-rule>` lists the alerts one table rule raised, and with it the server stops hiding ROW-LEVEL and resolve-after-migration alerts, so for that one rule a plain `--rule` lists them alongside the rest; `--is-row-level` and `--resolve-after-migration` (either value) still narrow it, and resolved alerts and those on a frozen table-series period's table stay hidden as on every list. - a `severe_rule_bug` alert is the backend's crash-loop circuit breaker: a rule crashed on a confirmed-severe share of the rows applicable to it in the processed portion of a file, the rule moved to `state: error`, and the alert **blocks the table's ingestion** until that rule is out of service. Of the four actions it offers, `disable_rule` clears it immediately and `upgrade_rule_revision` clears it once the replacement is live; `notify_rule_author` mails the rule's owners and leaves the alert open, while `retry_requeue` re-publishes a failed requeue (422 if there is nothing stranded) and also leaves it open. The upgrade is **not idempotent**: a second send is refused with `409 RULE_UPGRADE_REPLACEMENT_EXISTS`, and it refuses outright with `409 RULE_UPGRADE_TOUCHES_SCHEMA` when the upgrade would add or retype a column. On the ordinary close path, `409 SEVERE_RULE_BUG_RULE_STILL_ACTIVE` refuses to close the alert while the rule it names is neither disabled nor deleted, so the held files are never requeued with that rule's validation switched off. It is a guard, not an outcome you can pick: disable first makes the rule safe, upgrade clears through the replacement lifecycle instead, notify and retry return before that close path, and `alert resolve` will not send a name the alert did not offer. Patching the rule to `disabled` or `deleted` through `qctl apply -f` clears the blocker and requeues too — **unless the table has a draft migration under review**, in which case the backend stages that state patch as a rule suggestion (202) instead of applying it and nothing clears until you accept it with `qctl suggestion accept`, whereas the `disable_rule` action writes the state directly and is never staged. On a locked table-series period the patch and the suggestion accept are both refused with `409 PERIOD_LOCKED` (exit 2). [backend]
- `409 RULE_UPGRADE_TOUCHES_SCHEMA` has **two doors and one message**: `upgrade_rule_revision` is refused when the NEW revision would add or retype a column, and — checked first, before the new revision is compared to anything — when the CRASHED rule already declares produced fields of its own. Same code, same wording on the wire, so nothing distinguishes them there; `qctl alert resolve` reads the rule back and prints the door-specific way out, because only one door has one. The produced-fields door is not the dead end it reads as: a patch-mode `TableRule` manifest rebinds the crashed rule to a release that fixes it — the candidate takes the rule's live declarations when the body omits them, so `spec.produced_fields` is not needed and is best left out — and that rebind is validated as a revalidation candidate whose passing dry run moves the rule from `error` back to `enabled` and resolves this alert itself, without anyone accepting the suggestion. Two warts on that manifest: `qctl get table-rule -o yaml` writes `spec.state: error` into it (the state has no `omitempty`) and the backend refuses that key outright, so qctl rejects it with exit 2 and you delete the line; and `spec.produced_fields` cannot be used to *fix* a declaration either, since a patch that drops or retypes one without adding a column is refused before the request — a drop of an active column read by a linked table would be refused at PATCH time, while another drop or retype can pass its dry run and then fail to promote. An ordinary second rule cannot claim those same columns, but an instantiate with `spec.upgradedFrom` can reclaim a predecessor's output when the rule field and column schema match. `alert resolve` still prints the rebind on the produced-fields door because it keeps the live declarations without restating them, and suggests an upgrade manifest on the other door; retirement happens when the replacement becomes enabled. Disabling the crashed rule remains the immediate unblock while validation or a migration is pending. [backend]

A non-delta file of a table that loads by `mirror`, `append` or `append_skip_identical_rows` is held when, for a source in a table series, it would replace the last file of its cloud source loaded into its period (`replaces_loaded_file`), or when it has more than the cloud source's `preload_row_drop_share` fewer data rows than the last non-delta file of its cloud source loaded into its table (`row_drop`); under the two append processes only a file of the same name counts for either. A non-ops caller is offered only `release_held_file`, `reject_held_file` and `send_held_file_to_period`, because the type is not resolvable by a user; ops can also see `try_again`. `release_held_file` resolves the alert and requeues its jobs, which then load the file without checking it again — unless a later file of the same cloud source loads into its table first, which stops the run and settles the file `superseded`; `reject_held_file` trashes the file, stops its blocked jobs and resolves the alert without requeueing them. An undecided hold is settled `superseded`, with no user, once a later file of the same cloud source is queued for or loads into the same table (for a source in no series whose table appends, only a file of the same name); when either file's period was assumed, only once the later file has loaded, and a held file whose period was assumed stays open when its hold has a `period_mismatch` finding. `send_held_file_to_period` takes a period key in `new_value`, so it goes through a manifest (`--dry-run`, then `-f`): it resolves the alert without deciding the file, records the key in the body's `sent_to_period_key` and requeues the jobs into that period, where the file is checked again. A key naming neither an active nor a creatable period of the series (any key, for a source in no series), or naming the file's own period, is a 400 at `new_value`; a locked period is `409 PERIOD_LOCKED`, and one a later file of the same cloud source has loaded into is `409 PERIOD_HAS_LATER_FILE` (exit 2). [backend]
- a held file is decided once: a resolved alert lists no actions, so a second `alert resolve` exits 2 before sending, and a decision that races another gets `409 HELD_FILE_SETTLED` (the file already has the other decision, was replaced by a later file, or its alert closed without one). `release_held_file` on a file that a later file of the same cloud source has already loaded into its table (for a source in no table series whose table loads by `append` or `append_skip_identical_rows`, only a later file under the same key) is `409 HELD_FILE_SUPERSEDED`, while `reject_held_file` still turns such a file down; a locked period is `409 PERIOD_LOCKED`, for reject only when the file has loaded rows. Each 409 exits 2. [backend]
- `describe alert` shows a `preload_check_held` alert's `spec.body.findings` at every verbosity, one entry per tripped trigger carrying only that trigger's numbers. For a file that arrived by email, `spec.body.asked_user_id` names the sender once they were asked whether this is the right file, with any other periods they were offered in `spec.body.offered_period_keys`, or `spec.body.not_asked_reason` says why the sender could not be asked; none is shown while nobody has been asked, and nobody is asked about a file that did not arrive by email. [backend]
- `describe alert` shows at every verbosity what a `series_file_routing` alert on an emailed file asked: for any `reason` but `file_read_failed` and `no_unlocked_period`, the server tries once to email the sender a choice of periods, then `spec.body.asked_user_id` names the sender and `spec.body.offered_period_keys` lists the periods offered, or `spec.body.not_asked_reason` says why the sender could not be asked; none is shown before that attempt, or after one that sent nothing because no period could be offered or replies to the sender are suppressed. [backend]
- `describe alert` shows a `preload_check_held` alert's `spec.body.removed_row_count` at every verbosity: how many loaded rows of the file's table (its period, in a table series) loading the file would remove, counted when the file was held — under `mirror` the cloud source's rows in that table, under `append` and `append_skip_identical_rows` only the rows earlier uploads under the file's name loaded, less, under `append_skip_identical_rows`, the rows the latest upload under another file name also holds — and `0` when it would remove none. It is absent under any other loading process, for a delta file, and when the count failed. [backend]
- `describe alert` shows a `replaces_loaded_file` finding's `replaced_stored_item_id`, `replaced_file_name`, `replaced_loaded_at` (when the job that loaded that file finished), `replaced_row_count` and `period_label` at every verbosity, beside its `row_count` and `routed_period_key`: they name the loaded file of the period the held file would replace. Once `send_held_file_to_period` resolves the alert, `spec.body.sent_to_period_key` names the period the file was sent to, also at every verbosity; `release_held_file` and `reject_held_file` never set it. [backend]
- an `inbound_email_held` alert holds the data files of an inbound email instead of submitting them — `spec.body.reason` is `auth_failed` (the sender check failed) or `multiple_data_files` — and offers `use_held_email_file` and `reject_held_email_file`, both parameterless, to every role but `read_only` and `external` that holds `dataset:ingest:upload`, although the type is not resolvable by a user; it no longer offers `try_again`. `use_held_email_file` is offered only for `auth_failed` with exactly one linked file: it resolves the alert and publishes the file, which then goes through its pre-load check like any emailed file, and a locked period is a `409 PERIOD_LOCKED` that leaves the alert open. `reject_held_email_file` turns down every held file, trashes each and resolves the alert. A resolved alert offers neither, so a second `alert resolve` exits 2 before sending. [backend]
- `describe alert` includes a held email's sender in `spec.body.from_address` when present, at default verbosity and `-v`; `-vv` keeps it in `raw_response.body.from_address`.
- a `late_file` alert says a series cloud source has no loaded file for a reporting period whose broker due date has passed, and no nil return or waiver covers it: one per cloud source and period, with the period in `spec.body.period_key` on `describe alert` and in the `period_key` column of `get alerts` (`--columns`), which is empty for every other type. The scheduled deadline evaluation raises it and resolves it itself when the period gets a loaded file, a nil return or a waiver, is locked, or its due date moves later, and when the cloud source is no longer active or is past its end period; it blocks nothing. It is not resolvable by a user — a non-ops caller is offered no action and ops only `try_again`, and the next evaluation raises it again while the period is still late — so NEXT ACTIONS names `qctl get submission-statuses --cloud-source-id <id>` and `qctl submission-status waive --cloud-source-id <id> --period <key> --reason <text>` instead. [backend]
- Reprocessing does not give every row-level alert a new ID: a matching unresolved finding in the same scope can reuse the existing alert and increase its count. Once that alert is resolved, a later recurrence can create a new record. Re-list with `qctl get alerts --table-id <id> --is-row-level` before resolving findings from a previous run. [backend]
- `qctl alert propose <alert-id>` takes the same `--action`, `-f` and `--dry-run` inputs as `qctl alert resolve` and sends the same request body, but stores it as a change proposal that an approver applies later; nothing on the alert changes, so it never prompts and has no `--yes`. It submits for review unless you pass `--draft`, and `--also-alert`/`--also-warning` name other issues of the same table the resolution also resolves. Follow it with `qctl describe change-proposal <id>` (see `qctl explain change-proposal`).
- an alert is HELD by a change proposal while that proposal is `pending_review`, `changes_requested` or `executing`: a draft holds nothing, and every terminal state (`executed`, `execution_failed`, `rejected`, `withdrawn`, `obsolete`) releases it. `get alerts --has-change-proposal` asks the server for the held ones (`--has-change-proposal=false` for the rest), and `--change-proposal-state` (repeatable) for those held by a proposal in one of the named states, so naming any other state matches nothing. The detail and list responses carry the holder as `change_proposal: {id, state}`, null when none holds it. [backend]
- `--change-proposal-state` takes any proposal state, case-insensitively; an unknown one, or any state together with `--has-change-proposal=false`, is a usage error (exit 2) before anything is sent. When either filter selects held alerts the table adds a `change_proposal` column printed `<uuid> <state>` (header `CHANGE-PROPOSAL`); without one it is an opt-in `--columns` field, and `-o json`/`-o yaml` keep the `{id, state}` object. `describe alert` names the holder in a HELD BY CHANGE PROPOSAL section before NEXT ACTIONS, with `Next: qctl describe change-proposal <uuid>`.
- resolving a held alert directly is not refused: once `qctl alert resolve` commits, the server turns obsolete every `pending_review` or `changes_requested` proposal holding a resolved alert or warning of the same table, which covers the named alert's own holder and any issue the resolve also resolved on the table's other cloud sources; an `executing` proposal is left alone. Before it sends, `alert resolve` (flag and `-f` paths) prints a stderr warning naming the named alert's holder when that holder would turn obsolete; it cannot foresee the other issues a fan-out resolves. To change what a proposal does rather than discard it, use the change-proposal verbs (`qctl explain change-proposal`). [backend]
- `describe alert`'s NEXT ACTIONS footer prints, under each offered action, the backend's catalog entry for it on this issue type: what resolving with it does, its scope (`file`, `source`, `table`, `rows` or `none`), whether it modifies data, whether it is reversible, and its follow-on work. The catalog is compiled into qctl from the API spec it was generated against, so a newer server can differ; `qctl explain alert.alert_actions_list` lists every action's general entry, and `qctl explain alert.issue_type` adds each issue type's label and fix owner. Text output only: `-o json` and the `explain` JSON/YAML carry none of it.
- the alert detail response carries `action_modes`: your mode under the table's change review policy for each offered action — `resolve`, `propose` or `none` — with an action no policy governs always `resolve`, plus `field_names_resolution` or `no_action` only when you may resolve without an action and a policy governs that. Resolving an action whose mode is `propose` is refused with 403 `CHANGE_PROPOSAL_REQUIRED`, and one whose mode is `none` with 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4). The footer prints `qctl alert propose` for the first and `not open to you` for the second; a server that sends no `action_modes` gets `resolve` lines. [backend]
- Resolving `cant_sniff_header` or `multiple_sheets_found`, including with `trash_file`, is refused with `403 PII_ACCESS_REQUIRED` (exit 4) while the caller has effective PII columns masked on the table. Role visibility and active table PII grants are honored; a table with no effective PII columns passes this check. The same check applies to `alert propose` and `change-proposal edit`/`submit`. qctl prints a hint to request temporary access with `qctl pii-access-request request --table-id <table-id> --reason <reason>`, check `qctl get pii-access-requests --table-id <table-id>` and wait for approval before retrying; add `--shared` to both access commands for a table shared from another organization. [backend]
- A mask-shaped value in `spec.cant_sniff_header_params.raw_headers` is refused with 400 (exit 2) for every caller, including one with unmasked access, on direct resolution and proposal create/edit/submit. Supply the actual header names; PII access does not make mask text valid. [backend]
- An `alert resolve` that sends a mask-shaped value to a PII column is refused before the action runs: `400 A masked value cannot be written to a PII column. Enter a new value.`, with no `error_code`, so exit 2. Mask-shaped means text that starts with `•••••` and is exactly 5 or 9 characters long, the shape `field_value`, `another_field_value`, `prefix_candidates` and the body's suggested values take for a viewer who sees the column masked. The check reads `new_value` against the alert's first field, `another_field_new_value` against `another_field_name` and each `field_name_to_value` entry, and applies to the table's `pii_columns` plus each column a PII rule maps, whoever sends it. qctl sends a value as given and leaves that decision to the server. [backend]
- `alert propose` refuses a mask-shaped value up front only on a column the proposer sees masked (`422` at `body.payload.<field>`, same message, exit 2), and `change-proposal edit` does the same; any other mask-shaped value is stored without the resolve-time check, which runs only when `change-proposal approve` executes the resolve and then fails with the 400. [backend]
- the actions that write a value into the data — every `map_value*`, `set_value_to_true*`, `set_value_to_false*` and `validation_add_a_new_keyword__*` action, `overwrite_value` and `reapply_cell_override` — need `source:data:write`, which an organization withholds from its staff (every role but `ops` and `external`) when it turns staff data editing off, and from `external` when it turns external data editing off. Resolving one then is refused with 403 `Your organization has turned off data editing for its staff.` or `Your organization has turned off data editing for its external users.` (exit 4), and `qctl auth me` lists the withheld permissions. On an alert of a table another organization owns, that organization's staff switch applies too: off, it refuses a staff caller with 403 `This table's organization has turned off data editing for its staff.` [backend]
- For a viewer who sees the alert's columns masked, the `--dry-run` skeleton adds a `# masked for you: ...` comment naming which of its `field_value`, `another_field_value` and `prefix_candidates` comments hold masked display text rather than stored values. Copied into `spec`, such a value gets the 400 above.
- on a 403 about the resolve itself, `alert resolve` adds an `Instead:` line naming `qctl alert propose <id> --action <action>` (`alert propose -f <file>` when the resolution needs a manifest) to `CHANGE_PROPOSAL_REQUIRED`, and a `Next:` line naming `qctl get change-review-policy --table-id <table-id>` to `CHANGE_REVIEW_POLICY_DENIED`. A `validation_add_a_new_keyword*` action on an `invalid_keyword` alert also needs the policy's `dataset_rule_patch` `params` key, and a refusal under that key carries `dataset_rule_patch` as its operation, so only the generic `Hint:` speaks. `alert submit` and `alert retract` are checked too (operations `user_alert_submit` / `user_alert_retract`), whose key cannot be proposed: a refusal is a 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4) whose `Hint:` points at `qctl get change-review-policy --table <table>`. [backend]
- a repeated_key, identical_rows or person_marked_duplicate alert is a duplicate group's hold, and only the group's decision lets its rows load: the alert offers no actions, so `qctl alert resolve` refuses it (exit 2) with the command that shows the group, and a reprocess keeps the rows held and raises a new alert on them. The alert body's `group_id` names its group, and `describe alert` adds a NEXT ACTIONS line to `qctl describe duplicate-group <group_id>`; atlas writes `group_id` on a load's repeated_key and identical_rows alerts only after the load commits, so a body without one gets a line to `qctl get duplicate-groups --row-id` instead. [backend]
- a duplicate_not_loaded alert is the hold alert of a duplicate group whose reviewer kept another copy: the group's alert takes this type while its copies are not loaded and goes back to the origin's type (repeated_key, identical_rows or person_marked_duplicate) otherwise, keeping its id. It offers no actions, so `qctl alert resolve` refuses it (exit 2) with the command that shows the group, and a reprocess raises a new alert on its rows. `describe alert` adds NEXT ACTIONS lines to `qctl describe duplicate-group <group_id>` (`qctl get duplicate-groups --row-id` when the body names no group) and to a `qctl rows delete-quarantined --signature` delete of the copies. [backend]
