## USAGE

    qctl describe warning <id>
    qctl get warnings
    qctl warning resolve <warning-id>
    qctl warning retract <warning-id>
    qctl warning submit

## EXAMPLES

    # unresolved warnings in the org (pass --resolved to see resolved ones)
    qctl get warnings

    # warnings raised on one table
    qctl get warnings --table orders

    # highest-impact warnings of one issue type (add --reverse for lowest first)
    qctl get warnings --issue-type user_submitted --order-by impact_score

    # include the recorded actor on resolved warnings
    qctl get warnings --resolved --columns id,issue_type,impact_score,whodunit

    # warnings a change proposal holds, with the proposal's id and state
    qctl get warnings --has-change-proposal

    # only those waiting on a reviewer
    qctl get warnings --change-proposal-state pending_review

    # full detail for one warning, plus the exact command for each action it offers
    qctl describe warning 123

    # resolve it with one of those actions
    qctl warning resolve 123 --action not_anomaly

    # on a rule warning: accept the values the rule generated for a row, or replace them
    qctl warning resolve 55 --action ignore_rule_for_row --row-id 1042 --reason "checked by hand"
    qctl warning resolve 55 --action overwrite_rule_outputs --row-id 1042 --set region=EMEA --reason "known account"

    # an action that needs input: write the manifest, edit it, send it
    qctl warning resolve 9 --action map_value --dry-run > fix.yaml
    qctl warning resolve -f fix.yaml

    # raise your own advisory warning on a cell of a quarantined row
    qctl warning submit --table orders --row 1042 --field amount --comment "looks off"

    # withdraw it again ("I flagged the wrong cell")
    qctl warning retract 8817 --row 1042 --yes

## GOTCHAS

- `get warnings` includes `impact_score` (header `IMPACT-SCORE`) in the default table. `whodunit` is an optional `--columns` field containing the user object, blank when absent; `-o json` and `-o yaml` retain the numeric score and full user object. The default sort remains `id`; use `--order-by impact_score` to prioritize impact.
- `whodunit` can identify the resolver: resolving a warning fills it when it was empty. It is not a reliable raised-by field; user-submitted warnings are created without it, and each flag's author is in `user_submitted_issues[].submitted_by`. [backend]
- `--order-by impact_score` sorts highest first; `--reverse` sorts lowest first. The server computes impact from the issue type's base score plus a logarithmic row-count bonus, multiplied by `0.35 + 0.65 * exp(-age_in_days / 14)` with negative age treated as zero. Warnings receive no blocking bonus; the score is not a percentage. [backend]
- `--issue-type` filters server-side and intersects with the table, data-source and resolution filters. Values are forwarded as typed, so an older CLI can use newly added server types; an invalid type is the server's 422 (exit 2). Shell completion suggests types from the generated metadata.
- Integer fields in a YAML manifest reject fractional numbers during parsing (exit 2): `2.7` is refused instead of becoming `2`. Whole-valued YAML numbers such as `2.0` remain accepted.
- `describe warning <id>` rejects a non-numeric ID locally as bad usage (exit 2), before any API request.
- a warning's `count` is approximate and stops at 1000 too: `count_capped: true` means at least 1000 rows, and `get warnings` prints such a count as `1000+` while `-o json` and `-o yaml` keep the number. The exact figure is `affecting_rows_count`, which `describe warning` reads from the warning's separate stats request and which counts the quarantined and clean rows carrying the warning together; when that request fails the value is left out, one warning goes to stderr, and the describe still exits 0. [backend]
- the alert/warning split is not a conjunction of two switches: the table rule's `spec.severity` policy is applied once, where the issue is minted — and everything that does not resolve to `blocker` lands here. So `spec.severity: warning` forces every data-quality finding of that rule here, `blocker` forces every one into `qctl get alerts` instead, and `as_declared` splits per issue — under `as_declared` a rule whose issues are all warning-severity still lands here, and one emitting both severities raises an alert and a warning on the same row; a configuration error (an undeclared write, or a row filter that does not compile or misses its column) raises an alert whatever the policy. Patching `severity` (or `params`, `state`, `column_mapping`) reprocesses the rows already in quarantine for that rule once the change reaches the live rule — a revalidation candidate holds any of them but `state` until it is promoted, and a draft migration holds a `params` or `state` patch (`qctl guide triage-alerts`) — and does so on a mirror-loaded table too, so loosening the policy releases rows it had quarantined. That reprocess never reaches back into rows already accepted as clean, and their old warnings stay warnings: an upload that re-sends such a row (on a mirror-loaded table, the next mirror upload) quarantines it under a new alert if it now fails, and resolves the old warning when that row was its last live carrier. [backend]
- a warning can carry `body.declared_severity` too, and there it means the policy went the OTHER way: the backend writes the key when the table rule's policy changes the severity, before deciding whether to raise an alert or a warning, so a finding the rule declared `blocker` that a `spec.severity: warning` policy demoted arrives here still declaring `blocker`. `describe warning` renders the raw response, so that key was always in the document — one line among two dozen nulls, with nothing saying whose value it is; the `DECLARED SEVERITY` note in the footer is what says so, and it prints on every view but `-o json`. It is written only when the rule and the policy disagreed, so on most warnings there is no key and no note. [backend]
- a warning a RULE raised is NOT read-only: `qctl warning resolve <id> --action <name>` drives one of the actions the warning itself offers, which is the mirror of `qctl alert resolve`. `submit`/`retract` remain USER-SUBMITTED-only — `submit` mints one, and `retract` reads the warning first and refuses anything else with exit 2 before sending the call. To reclassify or silence FUTURE findings, patch the table rule (`qctl explain table-rule`), not the warning.
- a human can raise a warning directly on cells of QUARANTINED rows (`qctl warning submit`), and unlike an alert it does **not** hold the row. Once the row's other issues clear it goes clean CARRYING the warning, and from then on the note can go stale — editing the flagged cell on a clean row does not update or clear it, because no producer revisits clean rows. If the objection has to survive that, `qctl alert submit` instead. There is no whole-row form: `--field` is required. [backend]
- `warning submit` is quarantine-only too, even though a warning holds nothing: the two verbs are separate routes over ONE shared submit path and one shared token-append, which differ only in the column they write, so a warning runs the alert's guard. To flag a cell on a CLEAN row, move it first — `qctl rows send-to-quarantine <table> --row-id <id>`, then `qctl warning submit`. The row keeps its id across the move (one sequence spans the clean and quarantine tables), but it lands `awaiting_processing_` with a reprocess published, and the guard the submit runs against is `awaiting_processing_ IS NOT TRUE AND ingest_job_id_ IS NULL` — so flagging it straight away answers `row_not_found`, which is also what a wrong row id answers. qctl re-reads each `row_not_found` row, up to ten, and names what it found; the row is ready once `qctl get data <table> --is-bad-data --awaiting-processing=false --filter-by-field-name id --filter-by-field-value <id>` returns it. `rows reprocess-clean` is the wrong verb for this — it sends the row back through validation instead of parking it. [backend]
- **a successful `warning retract` can leave the warning on screen.** `retracted` describes the RECORD, not the row: the token removal reaches quarantined rows only, so a warning whose row has already left quarantine keeps its token and stays on display even though the record is retracted and will not survive the next reprocess. Nothing revisits clean rows to take it off, the backend has no per-row status to say so (it logs it), and qctl therefore cannot report it. [backend]
- `warning submit` is a **per-row partial success**: each row answers `created`, `already_existed`, `row_not_found` or `field_invalid`, qctl prints the successes on stdout (on stderr under `-o json|yaml|name`, where stdout carries the result) and the rest on stderr, and exits 0 as long as one row was flagged. When none was, it exits 2 if any row said `field_invalid` and 3 otherwise. Each row's result also carries `submitted_by` and `thread_id`, which for an `already_existed` row are the ORIGINAL flag's: the success lines add a `discussion: comment-thread/<uuid>` line naming the thread the created rows share, with its `describe comment-thread` recipe, and under the "already carried" line one `row 1050: flagged by Dana Ray <dana@example.com> — comment-thread/<uuid>` per repeated row, either half left out when the server sends it null. `warning retract` is the same shape with `retracted`/`not_found`. One `--comment` can raise several warnings, because the aggregate's identity folds in the cells' observed values. [backend]
- the `--comment` also becomes the first comment of a NEW comment thread on the flagged cells: ONE thread per submit, targeting every flagged cell of every row that submit newly flagged, across all the warnings it raised. A row that answers `already_existed` joins no thread; it keeps its original flag's, and a flag made before servers opened threads has none. A `[@label](mention:<uuid>)` link in the comment notifies that user as in any comment — a bare `@name` does not, `warning submit` has no `--mention`, a self-mention is not notified — and the submit notifies nobody else. The comment itself is immutable: its author can edit that first comment with `qctl comment-thread edit-comment`, which changes the discussion only, never the warning's message; to reword the flag, retract and submit again, which opens a new thread and leaves the old one open. [backend]
- `describe warning` prints the raw `user_submitted_issues` list — per flag its `id`, `row_id`, `field_names`, `submitted_by`, `thread_id`, `created_at` and any `retracted_at`/`detached_at` — and the server sends retracted and detached flags as well as live ones. A FLAGGED BY note after the document groups them one line per flagger, thread and state, live flags first, such as `Dana Ray <dana@example.com>: rows 1042, 1043 (amount) — comment-thread/<uuid> [detached 2026-10-14]`, at most ten lines then `+N more (see -o json)`, followed by a `Next: qctl describe comment-thread <uuid> --table-id <id>` that prefers a live flag's thread. It is YAML comments in the YAML views, plain on `-o table`, and absent from `-o json`. [backend]
- `-o json` and `-o yaml` on `warning submit` print the server's `{issue_item_ids, results}`, and `-o name` prints `warning/<id>` for each warning a flagged row joined. `warning retract` prints the server's `{issue_resolved, results}` and `warning/<id>`. `warning resolve` prints `{id, action, resolved, dataset_id}` for each warning sent an action — `resolved` is the re-read warning's state, null when the re-read failed — and one `List` of them for a file of several documents, never the route's own answer, whose stored file URL can carry a cloud provider's keys and auth info; `-o name` prints `warning/<id>`. Both move their prose to stderr, and `resolve --dry-run` refuses `-o json` and `-o name` because it writes a YAML manifest.
- `warning retract` is keyed by `(warning id, row ids)`, not by the per-row record UUID. Both keys are in the ordinary quarantined-row payload: `qctl get data <table> --is-bad-data --warning-item-id 8817` filters to the rows carrying one, the rendered page marks every flagged cell `[W<warning-id>]` (with `--include-issues` for the message), and `-o json` shows the raw `warning_item_ids_` entries spelled `"<warning-id>-<field>"`. The alert side has the same filter, `--alert-item-id`, with one asymmetry: this one needs no `--is-bad-data` and the alert one is refused without it (exit 2), because a clean row can carry a warning token but never an alert one — `qctl explain alert` carries the mechanism. [backend]
- `warning submit` accepts `--yes` (or `-y`) as a no-op and asks nothing: a warning holds no row, so there is no production consequence to confirm. Both retract verbs do prompt — the alert:resolve permission lets any resolver, including an external data-source-scoped principal, erase someone else's objection. [backend]
- omitting `--resolved` is not "no filter": qctl leaves the param off the wire, and the server then defaults it to `false` — so `get warnings` with no flag shows only **unresolved** warnings; pass `--resolved` to see the resolved ones. [backend]
- when the rule that raised a warning sets its own issue pattern, rows with different messages and values share one warning whose `msg` and `field_value` are the FIRST row's, so every row carrying it shows that one message in `get data --include-issues` — read the value from the row's own cell. Without a pattern the message is part of the warning's identity, and different wording means a different warning. [backend]
- `get warnings` scopes to a table with `--table` (a NAME) or `--table-id` (an ID); neither accepts the other, so a table whose name is a number (`42`) is reachable with `--table 42`. The original `--dataset-id` is a hidden alias of `--table-id` and still works for scripts, but a non-positive alias or one passed together with `--table`/`--table-id` is a usage error (exit 2) checked before config or credentials, not a precedence rule.
- `qctl warning resolve` drives every action a warning offers: parameterless ones with `--action`, and ones that need request fields with a manifest — `qctl warning resolve <id> --action <name> --dry-run` writes the skeleton and `qctl warning resolve -f <file>` sends it. Which fields an action reads is read from `api.WarningActionFields` at runtime rather than written down in the command, so a regenerated spec that adds a required field changes what a manifest must carry with no code change. Verified parameterless today, including: `not_anomaly`, `ignore_issue_for_value`, `validation_add_a_new_keyword` and `ignore_column_for_future_anomalies`. No warning offers try_again: it is an alert action only. [backend]
- thirteen of the nineteen warning actions that `x-warning-action-fields` covers need a request field, and `--action` alone still refuses those (exit 2, naming the fields and the `--dry-run` that writes them) — that strictness is deliberate and the manifest is the way to send them. The `WarningAction` enum carries five more the map never mentions (`append_rule_param_list`, `call_webhook`, `other`, `try_again`, `update_rule_param`) and qctl reads an absent entry as "no fields", so any of them would be driven as parameterless and a manifest setting any field for one would be refused; no issue type offers one today, which is what makes that fail-open safe. Verified to need input today, including: `map_value`, `map_value_for_field`, `overwrite_value`, `validation_add_a_new_keyword__map_value`. [backend]
- a `rule_validation` warning offers `ignore_rule_for_row`, `overwrite_rule_outputs`, `overwrite_value` and the four `map_value*` forms, and not the `validation_add_a_new_keyword*` family. `ignore_rule_for_row` needs row ids — `--row-id`, or `spec.ids` in a manifest: every id must be a live clean or quarantined row of the warning's data source, or the whole request 404s. It ignores the warning's rule for those rows and removes the warning from them; the warning stays open while another row still carries it, so ignoring some of its rows does not resolve it. Read the ids with `qctl get data <table> --warning-item-id <id>`, adding `--is-bad-data` for the quarantined ones. [backend]
- `overwrite_rule_outputs` on a rule warning ignores the warning's rule for the rows in `spec.ids` and writes `spec.field_name_to_value` into them, moving clean ones to quarantine first, then reprocesses them; the warning resolves once no row carries it. It needs rows and values: `--row-id` and `--set <column>=<value>`, or a manifest — `qctl warning resolve <id> --action overwrite_rule_outputs --dry-run` writes one with `ids` and `field_name_to_value` to fill and `reason` commented out — and qctl refuses either missing with exit 2. Every key must be one of the warning's `rule_output_columns` (shown by `describe warning`): qctl refuses another with exit 2 before sending, and the server with a 422. An id that is not a live row of the warning's data source is a 404, and the action is a 400 on a composite table. `--reason` (`spec.reason`) is recorded on each new rule ignore, and sending `reason` with any action but this one or `ignore_rule_for_row` is a 422. So on a rule warning, accepting the values the rule generated for a row is `ignore_rule_for_row` and replacing them is `overwrite_rule_outputs`; `qctl rows set-cell` records no rule ignore. [backend]
- a successful `warning resolve` call is not the same as a resolved warning: `validation_add_a_new_keyword` on an `invalid_keyword` warning can stage the keyword as a rule suggestion instead of adding it — a revalidation candidate when the rule is in `error` or already has one pending, or a suggestion held behind the table's draft migration — answering 200 with its `dataset_rule_suggestion_id` while the warning stays open and before any quarantined row is republished. qctl re-reads the warning, prints that suggestion id (`dataset_rule_suggestion_id` under `-o json|yaml`) and the step that decides it: `qctl suggestion accept <uuid> --table-id <id>` for a draft-migration suggestion, which applying the migration also attempts, and `qctl describe rule-suggestion <uuid> --table-id <id>` for a revalidation candidate, which cannot be accepted because its validation run decides it. Either kind resolves the warning when it is applied, but only when the staged keyword is the warning's own value, not a different `new_value`, and the rule's `allowed` params then hold it: once the keyword is live, re-read the warning and, if it is still open, send the same resolve again, which resolves it because the keyword is then already allowed. [backend]
- the compound keyword actions — `validation_add_a_new_keyword__map_value`, `__map_value_for_field`, `__map_value_for_field_for_source`, `__map_value_for_source` and `__overwrite_value` — add `spec.new_value` as a keyword and fix the value in one request, so on an `invalid_keyword` warning whose keyword would be staged rather than applied they are refused with a 409 that carries no error code, and nothing is applied. qctl recognizes the refusal by the action sent and names the two steps: `validation_add_a_new_keyword` on its own with the same `spec.new_value` (`qctl warning resolve <id> --action validation_add_a_new_keyword --dry-run` writes the manifest; without `new_value` it adds the warning's own value), followed through any suggestion it stages until the keyword is live, then the compound action again for the value fix. [backend]
- a staged keyword change holds the rule's live keyword list plus the one new keyword, and accepting it overwrites the rule's params with that list. So two keyword resolves staged behind one draft migration each carry only their own new keyword, and accepting both leaves the rule with only the one accepted last; a second keyword resolve while a revalidation candidate is pending replaces that candidate's list, dropping the first keyword. This holds across alerts and warnings on the same rule. Resolve one keyword at a time, and get it live before resolving the next. [backend]
- `spec.map_value_once` is alert-only: a current server answers a warning resolve carrying it with a 422, and an older one resolved the warning without ever applying the mapping. `qctl warning resolve -f` refuses the key itself (exit 2, before anything is sent) whether it is `true` or `false`, and the `--dry-run` skeleton leaves it out. The dry-run skeleton explains that one-shot mappings are supported only for alerts. A warning whose value is blank therefore cannot be mapped at all — a learned mapping off an empty value is a 422 too — and `overwrite_value`, where the warning offers it, is what is left. [backend]
- `--action ignore_column_for_future_anomalies` prompts unless `--yes`: it permanently ignores the column and resolves unresolved anomaly warnings on the same column and settings model as the named warning. The prompt names the column and table, with no count. The table-wide value mappings available through `-f` — `map_value`, `map_value_for_field` and their `validation_add_a_new_keyword__` forms — and `accept_gtin_prefix` resolve across the table's data sources without prompting, while `map_value_for_source` and `map_value_for_field_for_source` do not; `accept_gtin_prefix` also resolves matching alerts and warnings whose value carries the accepted prefix. `accept_vin_manufacturer_code` has the same prefix reach using the issue's own manufacturer code. Other context-aware actions can reach beyond the named warning too, including `ignore_issue_for_value`. For external users, cross-source resolution is disabled. [backend]
- `warning resolve` now reaches all 63 warning issue types, `user_submitted` included: its five actions all require `new_value`, which a manifest supplies. `qctl warning retract` remains the verb for "I flagged the wrong cell" — the choice between them is about intent, not capability, the same split as `alert resolve` versus `alert retract`. [backend]
- resolving a warning republishes its quarantined rows for reprocess, so rows can LEAVE quarantine as a result — that is the point of the verb, not a side effect to suppress. Nothing in the response reports which rows moved, so `warning resolve` points at `qctl get data <table-id> --is-bad-data` instead of claiming an outcome. [backend]
- `msg` is the backend's Markdown, and a long value or one containing `~` arrives COMPLETE inside a `~*value*~` marker, with each `\` and `*` in the value escaped by a backslash: `get warnings -o json` and `-o yaml` carry that wire text as sent, while `describe warning` (its default YAML and `-o json`) prints the whole value with the marker gone. The `msg` column of `get warnings` and `describe warning -o table` is a preview wherever a column cap applies — 80 on a terminal, or the `--max-column-width` you pass: to fit the cap it shortens only marked values (head…tail, down to a floor), and a message still too wide after that is clipped at the cap with `…`, whatever that cuts — so read a long message whole from `describe warning`'s default YAML or `-o json`. PII values can also arrive inside `~{…}~`, with backslashes and tildes escaped outside a value marker; rendered views remove this wrapper and keep the API's value and surrounding style. qctl leaves masking to the API. [backend]
- `describe warning` preserves generated API wire shapes while stripping Markdown from `msg`: in its default YAML, `-o json` and `-o table`, UUID fields such as `dataset_rule_id` are canonical strings rather than 16-byte integer arrays.
- `qctl warning propose <warning-id>` takes the same `--action`, `-f` and `--dry-run` inputs as `qctl warning resolve` and sends the same request body, but stores it as a change proposal that an approver applies later; nothing on the warning changes, so it never prompts and has no `--yes`. It submits for review unless you pass `--draft`, and `--also-alert`/`--also-warning` name other issues of the same table the resolution also resolves. Follow it with `qctl describe change-proposal <id>` (see `qctl explain change-proposal`).
- a warning is HELD by a change proposal while that proposal is `pending_review`, `changes_requested` or `executing`, and by an `executed` one whose resolve staged a rule suggestion until that suggestion is applied or dismissed: a draft holds nothing, and every other terminal state (`execution_failed`, `rejected`, `withdrawn`, `obsolete`) releases it. A proposal on the warning whose `action` is `ignore_rule_for_row`, `overwrite_value` or `overwrite_rule_outputs` and that names `ids` holds only those rows, so several proposals can each hold rows of one warning while none holds it whole. `get warnings --has-change-proposal` asks the server for the warnings held whole or by a row (`--has-change-proposal=false` for those held neither way), and `--change-proposal-state` (repeatable) for those a proposal in one of the named states holds either way, so naming `draft` or a releasing state matches nothing. The detail and list responses carry the whole-warning holder as `change_proposal: {id, state}`, null when none holds the whole warning, and the row holders, oldest first, as `row_change_proposals: [{id, state, held_row_count}]`, empty when none holds a row. [backend]
- `--change-proposal-state` takes any proposal state, case-insensitively; an unknown one, or any state together with `--has-change-proposal=false`, is a usage error (exit 2) before anything is sent. When either filter selects held warnings the table adds a `change_proposal` column printed `<uuid> <state>` (header `CHANGE-PROPOSAL`); without one it is an opt-in `--columns` field, and `-o json`/`-o yaml` keep the `{id, state}` object. `describe warning` names the holder in a HELD BY CHANGE PROPOSAL section before NEXT ACTIONS, with `Next: qctl describe change-proposal <uuid>`. Both name only the whole-warning holder: a warning held only by rows gets a blank cell and no section, and its row holders are in `row_change_proposals`, under `get warnings -o json|yaml` and in the `describe warning` document.
- resolving a held warning directly is not refused: once `qctl warning resolve` commits, the server turns obsolete every `pending_review` or `changes_requested` proposal holding a resolved alert or warning of the same table, whole or by a row, which covers the named warning's own holders and any issue the resolve also resolved on the table's other cloud sources; an `executing` proposal is left alone. Before it sends, `warning resolve` (flag and `-f` paths) prints a stderr warning naming the proposal holding the whole named warning when it would turn obsolete; it names no proposal that holds only rows of the warning, and cannot foresee the other issues a fan-out resolves. To revise a proposal instead of discarding it, use the change-proposal verbs (`qctl explain change-proposal`). [backend]
- `describe warning`'s NEXT ACTIONS footer prints, under each offered action, the backend's catalog entry for it on this issue type: what resolving with it does, its scope (`file`, `source`, `table`, `rows` or `none`), whether it modifies data, whether it is reversible, and its follow-on work. The catalog is compiled into qctl from the API spec it was generated against, so a newer server can differ; `qctl explain warning.warning_actions_list` lists every action's general entry, and `qctl explain warning.issue_type` adds each issue type's label and fix owner. Text output only: `-o json` and the `explain` JSON/YAML carry none of it.
- the warning detail response carries `action_modes`: your mode under the table's change review policy for each offered action — `resolve`, `propose` or `none` — with an action no policy governs always `resolve`, plus `field_names_resolution` or `no_action` only when you may resolve without an action and a policy governs that. Resolving an action whose mode is `propose` is refused with 403 `CHANGE_PROPOSAL_REQUIRED`, and one whose mode is `none` with 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4). The footer prints `qctl warning propose` for the first and `not open to you` for the second; a server that sends no `action_modes` gets `resolve` lines. [backend]
- A `warning resolve` that sends a mask-shaped value to a PII column is refused before the action runs: `400 A masked value cannot be written to a PII column. Enter a new value.`, with no `error_code`, so exit 2. Mask-shaped means text that starts with `•••••` and is exactly 5 or 9 characters long, the shape `field_value`, `another_field_value`, `prefix_candidates` and the body's suggested values take for a viewer who sees the column masked. The check reads `new_value` against the warning's first field, `another_field_new_value` against `another_field_name` and each `field_name_to_value` entry, and applies to the table's `pii_columns` plus each column a PII rule maps, whoever sends it. qctl sends a value as given and leaves that decision to the server. [backend]
- `warning propose` stores a mask-shaped value without that check: it runs only when `change-proposal approve` executes the resolve, which then fails with the same 400. [backend]
- For a viewer who sees the warning's columns masked, the `--dry-run` skeleton adds a `# masked for you: ...` comment naming which of its `field_value`, `another_field_value` and `prefix_candidates` comments hold masked display text rather than stored values. Copied into `spec`, such a value gets the 400 above.
- on a 403 about the resolve itself, `warning resolve` adds an `Instead:` line naming `qctl warning propose <id> --action <action>` (`warning propose -f <file>` when the resolution needs a manifest) to `CHANGE_PROPOSAL_REQUIRED`, and a `Next:` line naming `qctl get change-review-policy --table-id <table-id>` to `CHANGE_REVIEW_POLICY_DENIED`. A `validation_add_a_new_keyword*` action on an `invalid_keyword` warning also needs the policy's `dataset_rule_patch` `params` key, and a refusal under that key carries `dataset_rule_patch` as its operation, so only the generic `Hint:` speaks. `warning submit` and `warning retract` are not subject to the policy, unlike `alert submit` and `alert retract`. [backend]
- a repeated_key, identical_rows or person_marked_duplicate warning is on a row its duplicate group let load under a decision, or, for identical_rows, a copy that loaded with no decision because the table does not hold identical copies. It offers no actions, so `qctl warning resolve` refuses it (exit 2) with the command that shows the group: the decision is the group's, not the warning's. A body carrying `group_id` names the group (`qctl describe duplicate-group <group_id>`); otherwise `qctl get duplicate-groups --row-id <row-id>` (with `--include-ended` once the group has ended) finds it.
