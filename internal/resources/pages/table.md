## USAGE

    qctl apply -f <file.yaml>   # kind: Table
    qctl apply table -f <file.yaml>
    qctl describe table [id-or-name]
    qctl diff -f <file.yaml>   # kind: Table
    qctl get table <id-or-name>
    qctl get tables
    qctl share table <id-or-name>... --to <email>
    qctl undelete table <id-or-name>

## EXAMPLES

    # list every table in the org
    qctl get tables

    # summarize standalone tables and series, one row each
    qctl get tables-overview --view needs-attention

    # triage tables, highest attention score first
    qctl get tables --needs-attention --order-by attention_score

    # list tables with score zero, including locked periods
    qctl get tables --needs-attention=false

    # include approval, hold and validation-issue counts
    qctl get tables -v

    # select health columns explicitly
    qctl get tables --columns id,name,attention_score,top_alert,approved_rows_count,on_hold_rows_count,rows_with_issues_count,needs_approval

    # list tables tagged with one table kind
    qctl get tables --table-kind car-policy-bordereau

    # list a series's tables, newest period first
    qctl get tables --series "Monthly reports"

    # reverse period order, selecting the series by UUID
    qctl get tables --series 11111111-2222-3333-4444-555555555555 --reverse

    # list tables whose columns carry standard fields required by the default revision of a rule
    qctl get tables --for-rule fleet-check

    # select another release of that rule
    qctl get tables --for-rule fleet-check --release 1.0.0

    # the summary: columns and their rules, state, row counts, what is blocking
    qctl describe table orders

    # the same summary as a structured object, for scripts and agents
    qctl describe table orders -o json

    # summarize the table whose exact name is "42", rather than table ID 42
    qctl describe table --table 42

    # the applyable manifest — this is what round-trips through apply
    qctl get table orders -o yaml

    # the settings model, backup settings and thresholds
    qctl get table-config orders

    # one row: name, state, destination, row counts
    qctl get table orders

    # running and waiting job counts, streamed over a WebSocket for up to ten minutes
    qctl get table orders --job-activity --watch --timeout 10m

    # create or update the table from that manifest
    qctl diff -f table.yaml
    qctl apply table -f table.yaml

    # recover a deleted table (find one with: qctl get tables --state deleted)
    qctl undelete table orders

    # grant another user read-only access to a table
    qctl share table orders --to alice@example.com

## GOTCHAS

- List records preserve `series`, `period` and `top_alert` as `null` in JSON/YAML when the API returns null.

- `apply -f <file> -o name` prints `table/<id>`, including an unchanged result. Several applied documents print one reference per line in file order; prose goes to stderr.

- Integer fields in a YAML manifest reject fractional numbers during parsing (exit 2): `2.7` is refused instead of becoming `2`. Whole-valued YAML numbers such as `2.0` remain accepted.
- `get tables` shows `SERIES`, `PERIOD`, `CLEAN-ROWS-COUNT`, `BAD-ROWS-COUNT`, `ATTENTION-SCORE` and `TOP-ALERT` by default. `SERIES` is the series name; `PERIOD` is the period key, with `[locked]` when locked; both show `-` for a table outside a series. `TOP-ALERT` is the issue type with `[new files on hold]` when `blocks_ingestion` is true, or `-` when no top alert was returned. `--columns` selects another set, and `--for-rule` uses its own match view.
- `get tables -v` adds `approved_rows_count`, `on_hold_rows_count`, `rows_with_issues_count` and `needs_approval`; an explicit `--columns` overrides the default set even under `-v`. Unknown counts are blank; zero counts show `0`.
- `get tables -o json|yaml` retains the server's structured series, period and top-alert fields and all health counts, including null values and absent keys; `-v` and `--columns` do not project these items.
- `get tables --needs-attention` sends true, `--needs-attention=false` sends false, and leaving the flag unset sends no attention filter. It cannot be combined with `--for-rule`, including explicit false.
- The attention filter keeps positive scores for true and zero scores for false. A locked period has score zero and is included by false. `--order-by attention_score` sorts highest first; `--reverse` shows lowest first. [backend]
- `approved_rows_count` is clean rows plus quarantine rows a person approved; `on_hold_rows_count` counts quarantine rows a person put on hold; `rows_with_issues_count` counts quarantine rows that fail validation. `needs_approval` is true when quarantine-until-approved or a data-review policy requires review. These counts can be unknown (null). [backend]
- `top_alert` carries `alert_item_id`, `issue_type`, `count` and `blocks_ingestion` for the highest-ranked alert counted in `unresolved_alerts`. It is null when there are no such alerts or the period is locked; a missing top alert alone does not prove there are no alerts. `blocks_ingestion` covers a block on either the table or the alert's data source. [backend]
- `get tables --series <exact-name-or-uuid>` resolves names in the current organization; a full UUID skips the series lookup. An empty reference exits 2, a missing exact name exits 3, and a denied lookup preserves exit 4. `--series` cannot be combined with `--for-rule`.
- With `get tables --series` and no `--order-by`, the server orders by period start, then by the time added and member ID, newest first; `--reverse` reverses that order. An explicit `--order-by` replaces period ordering; `--page` and `--limit` still select one page. Ordinary listings keep their ID order. [backend]
- `describe table` includes a Series line with the series name and UUID, period key and lock state, plus period dates when available. Locked periods also show who locked them and when (UTC RFC3339); missing lock metadata says `(unknown)`. JSON/YAML carry `series` and `period` objects for members and omit them for standalone tables. These read-only fields stay out of `get table -o json|yaml` apply manifests.
- A table of a series takes its name from the series and its period, and the series renames it on its own (`qctl explain table-series`). A table PATCH sending any other name is refused with 409 `TABLE_NAME_SET_BY_SERIES`, after the version check; `apply -f Table` never sends one, since it finds the table by `metadata.name` and so sends the name the table already has. [backend]
- `apply -f Table` and `diff -f` find the table by `metadata.name` alone, so a `get table -o yaml` export of a series table whose name the series has changed since names no table. Both then exit 2 before any write, because the export's `status.id` names that table under another name: export it again before editing it, or delete the `status` block to create a new table. A `status.id` of another organization, or one the server answers with 403 or 404, refuses nothing. Without its `status` block the file takes the create path, and the server refuses the create with a 409 on `table_name` (exit 2) while the file still carries the table's own `table_name`, destination, database and schema, which the rename left alone. [backend]
- Empty positional table references exit 2 before authentication or requests, including any empty member of `share table`'s table list.
- `describe table` names `pending_validation` separately in the Rules count (`pending validation` in text, `rules.pending_validation` in JSON/YAML). For a confirmed draft it separately fetches all running ingestion jobs, including dry-run carriers, so a newer finished job cannot hide the wait; BLOCKING lists each job's describe command, and `jobs.running_ingestion` carries their IDs and `is_dry_run` flags. An unavailable lookup warns and contributes no job blocker; an empty result does not diagnose other reasons a migration has not landed.
- Table names resolve exactly and case-sensitively. A missing name exits 3 with the organization-scope note and up to three suggestions from one bounded search in the same organization; suggestions are not selected automatically. An ambiguous exact name exits 2 and asks for an ID. `--table` always means a name, including digits; a numeric name that matches nothing suggests `--table-id <number>`.

- A 403 saying `User is not authorized to access table <id>` (or `tables [<ids>]`) keeps the server message and appends table-grant advice: run `qctl auth me` for your role and email, ask the table owner or an org admin to run `qctl share table <id> --to <your-email>`, then re-run the failed command. A 403 saying `You have view-only access to table <id>` (or `tables [<ids>]`) instead advises changing the grant to editor or owner. Other 403s and lookup 404s keep the organization-scope note.
- `get tables --for-rule` uses the default revision for a rule name or slug. Use `--release` for another release or a revision ID to address that revision directly; of the ordinary table-list flags, only `--page` and `--limit` apply to the match view. Its table output shows full and partial counts; `-o json|yaml` yields raw match rows, and `-o name` yields `table/<id>` for each match.
- String lists in a manifest, including `spec.settings_model.null_values` and `null_values_per_column`, reject unquoted YAML null markers such as `NULL`, `null`, and `~` (and JSON `null`) with exit 2; quote a literal marker, for example `null_values: ["NULL"]`.
- An apply confirmation uses the current context's `organizationName` when its `organization` ID matches the selected org and the `organizations` cache has no name for it; a different uncached `--org` UUID still shows `Unknown`.
- `qctl create table` does not exist — tables are managed declaratively via `qctl apply table -f <file.yaml>` (or `qctl apply -f <file.yaml>` with `kind: Table`); guessing `table`/`dataset` under `create` returns a redirect to `apply`, not a real command.
- A short `kind: Table` manifest needs only `metadata.name` and `spec.destination_id`, `database_name`, `table_name`, and `backup_settings_id`; optional `data_loading_process` may be `append`, `append_skip_identical_rows`, or `mirror`. This uses quick create without reading `GET /datasets/new`. Reapplying the same file preserves the existing schema, migration policy, and loading process. A new table with other settings needs `spec.schema_name`, `migration_policy`, and `data_loading_process` for the full create route; `qctl diff -f` follows the same choice.
- `qctl delete table` does not exist and is not an oversight: deleting a table resolves every unresolved alert, deletes every cloud source and marks every ingestion job killed and kills nonterminal profiling jobs, the permission is held only by the ops and admin roles, and recovery is lossy — so deletion stays in the web UI, where a person confirms it. Typing it returns that explanation (exit 2), not a bare "unknown command", and points at `qctl undelete table` for the recovery direction.
- the backend calls a table a *dataset*; `dataset` and `datasets` work wherever `table` and `tables` name a command (`qctl get datasets`, `qctl describe dataset <name>`, `qctl apply dataset -f ...`), and in `qctl explain`, `qctl guide` and the `qctl create` redirect. `qctl api-resources` takes no arguments; it lists every resource's aliases in an ALIASES column instead.
- `qctl describe table` accepts the table as a positional (ID first, then exact name) or with `--table <name>` / `--table-id <id>`; use `--table` for a numeric-looking name such as `42`. `qctl get table`, `download data`, `undelete table` and `share table` remain positional-only, so their positional `42` means table ID 42.
- the table manifest's `migration_policy` decides what happens to a pending schema change, and a client sets one of two values. `ask_user` — **the backend default** — raises a `needs_review_migration` alert and waits for you (`qctl get alerts --resolvable-by-user`, then `qctl alert resolve <id> --action apply_migration`); one case applies under `ask_user` with no review alert, an additive-only `kind: TableSchema` patch that clones a fresh draft. `frozen` refuses the schema change rather than deferring it — see the next bullet. A third value, `apply_asap`, confirms drafts without a review, and it cannot be set through the API: a create that sends it, or an update that moves a table onto it, is refused `400` with `migration_policy=apply_asap cannot be set through the API. Use ask_user or frozen.` A table that already holds `apply_asap` keeps it, and an update re-sending it passes, but a manifest exported from that table cannot create another one until its `migration_policy` is changed. [backend]
- `frozen` is enforced, and it refuses rather than defers: a profiling run (a training job backend-side) that finds a schema change on a frozen table raises a `migration_frozen` alert and ends the job in `error` at the `combine` step *before* any draft migration is written, and the `PATCH .../migrations` route behind `kind: TableSchema` answers `409 ERR_MIGRATION_CONFLICT` — "This table's schema is frozen and cannot be changed." — when the overrides would move the schema. That alert blocks neither ingestion nor profiling, offers `update_configs_to_recommended_value` (which writes `migration_policy: ask_user`) and `try_again`, and the backend resolves it itself once a migration lands. The `apply_migration` handler is the hole left over: it reads no `migration_policy`, so a `needs_review_migration` alert raised before the table was frozen still applies afterwards. The web UI's migration-policy control does not offer `frozen`, so setting it means `qctl apply table`. [backend]
- the three views of a table answer three different questions, so reach for exactly one of them at a time; they do share a few fields — the name and id, `migration_policy` and `data_loading_process` appear in all three, and the settings model in both `get table -o yaml` and `get table-config` — but nothing beyond that: `describe table` is the human summary (columns with the rules bound to them, state, row counts, what is blocking), `qctl get table <t> -o yaml|json` is the apply-compatible manifest, and `qctl get table-config <t>` is the settings model. Before 2026-08-03 `describe` returned the manifest and `get -o yaml` returned the raw backend response with status counters interleaved into configuration; both changed.
- A table manifest exported with `-o yaml` or `-o json` preserves newline-only string values, literal `<<` keys in settings maps, and control characters when re-applied.
- `spec.compression_type_of_backup_data` picks the backup archive format — `gzip`, `zip` (the backend's default), `snappy_stream` or `tgz` — and it is disregarded whenever `encrypt_raw_data_during_backup` is true: GPG handles compression itself regardless of the choice, and the backed-up file is then recorded with no compression type at all. The column is nullable, but neither write schema carries the key when a manifest leaves it out, so a manifest can choose a compression and cannot clear one back to null. [backend]
- `spec.model_labels` maps a field name to the human-friendly header `qctl get data` prints in its place — the data route builds the response's `labels` from it. After a successful migration the backend seeds every current field with its captured original header (or the normalized field name), preserves existing overrides for fields that survived, and prunes labels for deleted fields. A manifest can override that map: omitting the key keeps the stored value, while `{}` clears it until the next migration seeds the defaults again. [backend]
- `spec.pii_columns` lists the fields kept as personal data — marked by hand, or added when a personal-data rule checking one is deleted or remapped — whose values issues reports count but do not show and API responses mask for a caller without unmasked access. Every newly added entry must name a current field of the table or the apply is refused with 422, so a create with a non-empty list always fails — a brand-new table has no fields yet — and a `get table -o yaml` manifest re-applied under a new name must drop the key first. An entry already stored stays accepted after its field is gone. Omitting the key keeps the stored list; `[]` clears it, but dropping any stored entry needs `pii:grant` (the `admin` and `ops` roles) and is otherwise refused with 403 before anything changes. [backend]
- A manifest that still sets `spec.settings_model.pii_columns`, where the key lived before the backend moved it onto the table, exits 2 naming `spec.pii_columns` as its new home.
- When the backend refuses an apply with 403 for dropping stored `spec.pii_columns` entries, qctl adds `Only an admin can remove a column from the PII list.` after the server's message, names the dropped columns, and exits 4 like any 403; the table kinds and standard fields in the same manifest are not applied either.
- `get table -o json|yaml` carries the table's personal-data columns read-only as `status.effective_pii_columns` (the names) and `status.pii_column_sources`, one `{column, listed_by_hand, rules: [{dataset_rule_id, instance_name}]}` per column, each left out when it is empty or the server sent none; apply and diff ignore both, so edit `spec.pii_columns` instead. `describe table` prints them as `PII columns:` — each column followed by `listed by hand` and the instance names of the rules that map it, or `none`, or `(not reported by this server)` — and `-o json|yaml` carry `pii_column_sources`, `[]` for none and `null` when not reported.
- `effective_pii_columns` is `spec.pii_columns` plus each column that a name, email, phone or address rule on the table maps as its value while the rule is in any state but `deleted`, sorted by name; `pii_column_sources` adds, per column, whether `spec.pii_columns` lists it and those rules, sorted by `instance_name`. Every reader gets both, whatever their `pii_visibility`. Deleting such a rule or remapping its value column adds the column to `spec.pii_columns`, so no column leaves the effective list on its own — but a manifest exported before that, with a non-empty `spec.pii_columns`, lacks the column, and re-applying it drops the entry, which needs `pii:grant`. [backend]
- `spec.table_kinds` is a list of table-kind slugs, and `spec.column_standard_fields` maps column names to standard-field slugs. `qctl get table -o yaml` exports both, and `qctl describe table` summarizes both. On apply, omitting either key preserves its assignments; `table_kinds: []` clears all table kinds, and `column_standard_fields: {}` clears the assignments visible in the table detail. Slugs are resolved before any write; an unknown slug exits 2. `spec.column_concepts` is still accepted as an alias; setting both exits 2.
- `qctl get tables --table-kind <slug-or-id>` resolves the kind and sends its UUID as `problem_domain_id`; it combines with other table filters. The backend requires `problem_domain:read` for this filter, so a user without it gets a 403. Include `--state deleted` when looking for tagged deleted tables. [backend]
- Table-kind and column-standard-field edits use separate PUT requests after any needed table creation or PATCH. The update is not atomic: if a PUT fails, qctl reports the failed step and earlier writes remain. `qctl diff -f` and the apply confirmation show both manifest changes, and diff prints each planned PUT body. A new table has no data fields yet, so create it and apply its schema before setting nonempty `spec.column_standard_fields`; an unknown column on an existing table is refused by the PUT.
- `spec.quarantine_rows_until_approved: true` keeps every row that passes validation in quarantine until someone approves it: while nobody has decided such a row, `qctl get data <t> --is-bad-data` reads `held-for-approval=table_setting` in its Row State (`review_policy` when the table's data-review policy also requires review, `possible_duplicate` for a suspected duplicate) and `qctl describe table` counts it under `held_for_approval` — while a submitted data review of the row is not closed, Row State reads `waiting-for-approval` and `describe table` counts it under `waiting_for_approval` instead — and it leaves once `qctl rows release` or a data review approves it and it passes. Setting the key back to `false` re-queues the table's live undecided quarantined rows for validation, but only when the data-review policy does not require review either, and best-effort: the PATCH commits first and a failed re-queue is only logged. `qctl explain data` has the rest of the held-for-approval state. [backend]
- the manifest is the table's configuration, not its whole record: two keys the dataset write schemas accept are deliberately absent from `qctl get table <t> -o yaml`, so neither can be applied. `not_anomalies_per_column` — the values people mark as not-anomalies, which `qctl alert resolve --action not_anomaly` appends to — is a ledger, and a manifest written before someone resolved an alert would revert them; `redirect_post_submit_to` is a navigation hint the server stamps onto responses rather than a stored field, so setting it would change nothing. Every other configuration key on those schemas is expressible. [backend]
- `spec.settings_model` on a `kind: Table` manifest is an OVERLAY on the table's current settings model, not a replacement: apply reads the table first and puts the stored value on the wire for every key the manifest leaves out, so a hand-written manifest can carry only the settings you actually mean to change. Deleting a key keeps its value; to clear one, write it as `[]` or `{}`, which apply sends as an edit rather than treating as absent. `schema_overrides` is the one settings key apply refuses to send even when the read returns it — schemas change through `kind: TableSchema`, which is the guarded path.
- `qctl diff -f table.yaml` previews top-level `spec` edits, standard-field assignments, and individual `spec.settings_model` keys, followed by the request bodies for the steps it will send; exit 0 is silent when an existing table already matches, and exit 1 means differences. Applying a changed existing table prints the same field changes and confirms before writing unless `--yes` is set; an unchanged apply sends no requests, while creating a new table remains non-interactive. A changed update with `-o json` requires `--yes` because the confirmation preview is prose that would corrupt stdout.
- Planning a full table create first reads `GET /datasets/new` so omitted manifest fields keep the server's defaults. A 401, 403, or 404 from that read stops `diff` or `apply` before the create request; 403/404 keep the backend message, their exit code, and the organization-scope note. Other failures retain the compatibility fallback that builds the request from the manifest alone.
- `qctl get table <t> -o yaml` prints every settings key the server sent except `id`, `version_id`, `whodunit_id` and `schema_overrides`, empty values included: a cleared list reads back as `[]` and a zero as `0`, not as a missing key — which is what makes that manifest safe to re-apply as a NEW table. A create sends every key the block omits as an explicit null (all but `xls_date_mode`, which it leaves out of the body), and the server skips a null on a NOT NULL column, or a key the body does not carry, and keeps its own Python default, so a key the read had dropped came back populated on the clone. A key still missing from the block is a third state, distinct from both: the server sent null, or no value at all, for it. `qctl get table-config` prints the same keys for the same reason. [backend]
- `spec.settings_model.key_columns` is valid on a `data_loading_process: mirror` or `append` table; `mirror` itself can only be chosen at creation. Set the keys when creating the table or before its first migration is applied or confirmed: once one is, the backend refuses key changes. To clear the keys, write `key_columns: null`: apply sends it as null and the table has no key columns, while omitting the key keeps the stored value and `[]` is refused with `key_columns cannot be an empty list; use null for no key fields.` qctl sends the manifest settings without reproducing these checks; key-field validation 400s point at `body.settings_model.key_columns`. [backend]
- `key_columns` is also what lets a `mirror` table take partial CDC deliveries — `qctl upload file --delta --delta-cursor <n>`, where each row upserts or tombstones by that key — and a `mirror` table without keys refuses them; `qctl explain file` has the delivery rules. [backend]
- a settings edit is version-checked twice: apply sends the table's `version_id` and the settings model's own, and the server refuses the whole PATCH with a 409 if either moved since the read. The message says `DataSet version mismatch` in both cases, including the one where it is the nested settings model whose version moved — so on a 409 re-read the manifest with `qctl get table <t> -o yaml` rather than retrying the file you have. [backend]
- `describe table` makes at least eight requests (table, schema, rules, suggestions, ingestion job, profiling job, alerts, shared-with) and spans four backend permissions, so a section you cannot read renders `(unavailable: ...)` with a warning on stderr instead of failing the command. Pending suggestions are paginated, and update/delete suggestions each need a detail read when a draft exists. For one column list, `qctl get table-schema <table>` is a single request.
- `describe table` prints a `Not loaded:` line when quarantined rows are duplicate copies a reviewer did not keep — rows carrying an unresolved `duplicate_not_loaded` alert, which the server counts as `not_loaded` — and `-o json|yaml` carries the count as `quarantine_not_loaded` whenever the server sent it, zero included. The count overlaps the Quarantine line's hold buckets, and no `qctl rows --status` value selects these rows: delete them by `--signature`. [backend]
- `describe table` counts suggestion blockers with the same migration gate as `qctl alert resolve --action apply_migration`. With no draft, it reports zero suggestion blockers without reading suggestion details. If the schema or a required suggestion read fails, the suggestions section is unavailable and contributes no suggestion blocker.
- in `describe table`'s column grid a column that is a rule's output marks that rule `(produces)` in its RULES cell — in place where the rule is already listed, appended where it is not, and by SHORT-ID when the rule list cannot name it — and `-o json|yaml` gives the column `produced_by: {rule_id, rule}`; both are read from the `generated_by` stamp on the column's schema definition (the draft's when a draft exists), which a 2.118.0 server does not send on the schema route, so against one no column is marked. [backend]
- a rule whose `dataset_columns` is empty, or names a column the current schema no longer has, cannot appear in the COLUMNS grid; `describe table` lists those under "Rules not bound to a column" rather than dropping them, so the grid is never a complete rule inventory on its own — `qctl get table-rules <table>` is.
- an empty `qctl get tables` does not establish that the organization has no tables: a 404 carrying `NO_TABLE_MESSAGE` renders as an empty result (exit 0; under `-o json` or `-o yaml`, a List with empty `items` and a null `total`) with a visibility hint on stderr in every format. qctl reads the role in the same organization; accounts other than `ops` and `admin` are asked to have a table owner or admin add them, then re-run the same command. If the role lookup fails, the hint stays neutral. The association filter also applies to `qctl get files`; the `ops`-only existence check on `get tables` spans every org and checks only active or disabled tables. [backend]
- `get tables --state` and `--states` accept only the states `qctl get tables --help` lists; any other value, an empty `--states` member included, is bad usage (exit 2) before a request is sent, and the error names the flag and lists the valid states.
- A deleted table is invisible to `qctl get table` and `qctl describe table`: both answer 404 (`dataset {id} is deleted.`). List deleted tables with `qctl get tables --state deleted` or `qctl get tables-overview --view trash`; `qctl undelete table <name>` resolves through the former list. [backend]
- `qctl undelete table <name>` refuses to guess when more than one deleted table has that exact name: it exits 2 before recovery, reports the matching IDs, and asks you to rerun `qctl undelete table <id>` with the one you intend.
- `qctl undelete table` is not a full undo: the table returns to `active`, but its cloud sources return **disabled** and need re-enabling with `qctl enable cloud-source`, which refuses a linked table's composite source, and a table-series cloud source stays deleted; alerts the deletion resolved stay resolved, and ingestion and profiling jobs it killed stay killed. If a table kind or standard field was deleted while the table was trashed, its tags or column assignments were removed and do not return. If the original name has since been taken the server refuses with a 409 and you must pass `--new-name`. Recovery also needs the ops or admin role — the same permission deletion needs. [backend]
- under `-o json` or `-o yaml`, `qctl undelete table` prints the server's `{result, dataset_id, name, state, data_sources_recovered}`, and `-o name` prints `table/<id>`; the prose moves to stderr.
- `qctl share table` resolves every selector before granting access, then deduplicates by table ID in first-selector order: naming one table twice grants and counts it once, and the first selector is the label shown in the banner and result.
- `qctl share table` grants `--permission owner|editor|read_only` (default `read_only`) to active organization members other than external users. Existing grants keep their current level and appear under "already had access"; use `qctl table-member set-permission <user-id> --table <name> --permission <level>` to change one. A table owner or ops/admin can manage other users' grants, and any member can remove their own with `table-member leave`. Only ops/admin can remove or lower the last owner grant. [backend]
- `qctl get tables -o json|yaml` already carries a `users` array per row — the cheapest way to see who a table is shared with, though it lists only grants given through the table's own organization to its active members other than external users — while `qctl get table <t> -o yaml` does **not**, because the detail route's schema has no such field; for one table read `qctl describe table <t>`, whose `Shared with:` line comes from a separate request to that table's `/small` route, whose schema does carry `users`. [backend]
- under `-o json` or `-o yaml`, `qctl share table` keeps the warning banner and confirmation prompt on stderr while stdout remains one machine-readable document; `--yes` skips the prompt but is not required at an interactive terminal.
- `get table <t> --job-activity` prints job counts, which have no name, so `-o name` exits 2; with `--watch`, `-o json` writes one compact object per update and `-o yaml` one document after each `---`, and `--changes-only` drops an update equal to the last in every format. The text view redraws in place on a terminal and appends elsewhere; after a reconnect notice, a malformed-frame warning, or verbose WebSocket diagnostics under `-vvvvvvvv` and above, the next update that is printed starts below it and later updates redraw there.
- `get table <t> --watch` requires `--job-activity`, `--changes-only` and `--provider` require both `--job-activity` and `--watch`, and `--timeout` requires `--watch`. Missing a required mode or passing a negative `--timeout` exits 2 before any request, including an explicit `--changes-only=false` or `--provider first-party` outside a job-activity watch. `get table <t> --job-activity --watch` announces itself on stderr — `watching job activity on table <t>, for up to <d>; resume with: <command>`, with no `for up to` clause when there is no limit — and streams until `--timeout`, where 0 means no limit; unset, it is no limit unless `QCTL_WATCH_TIMEOUT` (a Go duration such as `90s`) sets one. Running out is a clean end: exit 0, after `timed out after <d>; resume with: <command>` on stderr. SIGINT exits 130 and SIGTERM 143, and a close with code 1000 from the server also ends the watch with exit 0, with no `timed out` line.
- the job-activity socket's first dial is not retried: a dial the server answers with 401 or 403 exits 4, with 404 exits 3, with any other 4xx but 429 exits 2, and any other failure exits 1. Once it is open, a dropped connection is redialed after a wait from 1s doubling to 30s, each attempt announced on stderr as `connection lost (<cause>); reconnecting in <wait> (attempt <n>)`, until `--timeout` runs out. A close with code 1008 ends the watch with exit 4, quoting the server's reason with the `qctl auth login` hint; a close with 1002, 1003, 1007, 1009, 1010 or 3000–4999 exits 1; a redial refused with a 4xx other than 429 exits as a first dial would.
- the server re-checks the token behind a job-activity socket every 60 seconds and closes the socket with 1008 `Authentication expired or revoked.` once the token has expired or it finds the token revoked, so a long `get table <t> --job-activity --watch` ends with exit 4 within a minute of that; run `qctl auth login`, then resume. It closes the socket the same way when it cannot reach Redis to check for a revocation, so this exit 4 is not always your token. [backend]
- `get table <t> --job-activity --watch` reads the table over REST before dialing (`--provider third-party` uses the shared-table detail route). A failed read stops the watch with the server's reason and HTTP exit code: 404 exits 3, while 401/403 exits 4. Atlas returns 403 for a missing numeric table ID or one outside the current organization, with `Table <id> is not associated with this organization`; qctl includes the organization-scope advice. An upgrade refused after a successful read still returns a bare HTTP 403 and exits 4 with `websocket handshake failed: HTTP 403 Forbidden`, without the server's reason. [backend]
- An apply can queue automatic re-profiling only for a value change to `fields_to_expand`, `max_boundary_element_length`, `infer_datetime_for_columns`, `infer_datetime`, or `ignore_column_names` within `spec.settings_model`. This also requires a caller whose role is not `external`, an enabled training data item for the table, and either a draft schema migration or files on a table with no existing schema migration. Changing another setting, such as `percent_to_decimal`, does not queue re-profiling. [backend]

- `describe table` shows each shared user's granted level and, when different, effective level; `my_permission_level` is the caller's nullable effective level from `/small`, also printed as `My access:`. The existing `shared_with.users` email list remains available; `shared_with.members` adds the levels.
- `describe table` prints `Personal data:` with your own view of the table's personal-data columns — `masked`, `unmasked by your role`, or `unmasked by a grant until <UTC RFC3339>` — and `-o json|yaml` carry it as `pii_visibility: {status, expires_at}`; `get table -o json|yaml` puts the same object in `status.pii_visibility`, which apply and diff ignore. A server too old to send the field prints `(not reported by this server)`, `pii_visibility: null` and no `status.pii_visibility`, which says nothing about whether values are masked.
- `pii_visibility` describes the reader, not the table: `unmasked_by_role` whenever your role in the table's own organization carries `pii:view` (every built-in role but `read_only` and `agent`), even if you also hold a grant; otherwise `unmasked_by_grant` while you hold an active, unrevoked grant on the table, with `expires_at` the latest such expiry; otherwise `masked`. From another organization only a grant counts, and `expires_at` is null except for a grant. Listing grants needs `pii:grant`, so this is where a grant holder reads their own expiry. [backend]
- `apply -f Table` is subject to the table's change review policy (`qctl explain change-review-policy`): its settings PATCH under the operation `settings_patch`, checked only on the governed settings it would change, so re-applying an unchanged manifest passes, and its table-kind and standard-field PUTs under `problem_domains_put` and `column_concepts_put`, which qctl sends only when `spec.table_kinds` or `spec.column_standard_fields` differ from the live table. A refusal is a 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4) whose `Hint:` names the operation and the refused keys and points at `qctl get change-review-policy --table <table>`; no key of these operations can be proposed, so `CHANGE_PROPOSAL_REQUIRED` never answers them. `undelete table` is not subject to the policy.
