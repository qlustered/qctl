## USAGE

    qctl describe row <row-id>
    qctl download data <table-id-or-name>
    qctl get data [table-id-or-name]
    qctl get deleted-rows [table-id-or-name]
    qctl get rule-ignores [table-id-or-name]
    qctl get value-recommendations [table-id-or-name]
    qctl rows check-unique [table-id-or-name]
    qctl rows delete-quarantined [table-id-or-name]
    qctl rows hold [table-id-or-name]
    qctl rows ignore-rule [table-id-or-name]
    qctl rows release [table-id-or-name]
    qctl rows reprocess-clean [table-id-or-name]
    qctl rows reprocess-quarantined [table-id-or-name]
    qctl rows reset-hold [table-id-or-name]
    qctl rows search-replace [table-id-or-name]
    qctl rows send-to-quarantine [table-id-or-name]
    qctl rows set-cell [table-id-or-name]
    qctl rows unignore-rule [table-id-or-name]

## EXAMPLES

    # Read and reprocess clean rows of a shared table
    qctl get data --table shared-orders --shared
    qctl rows reprocess-clean --table shared-orders --shared --all --yes
    # Park every clean row of a shared table for manual review
    qctl rows send-to-quarantine --table-id 42 --shared --all --yes
    # Narrow a shared-table operation to a source by ID
    qctl rows hold --table-id 42 --shared --cloud-source-id 7 --all --yes
    # Queue a shared-table CSV export
    qctl download data shared-orders --shared --no-wait

    # export every clean row into the working directory (a zipped CSV)
    qctl download data orders

    # export the quarantined rows only, to a path you pick (it is a zip)
    qctl download data 42 --is-bad-data --output ./bad_rows.csv.zip

    # queue the export and return without waiting for the file
    qctl download data orders --no-wait

    # first page of clean rows, as an agent-friendly Markdown payload
    qctl get data orders

    # open the page containing a row, with its neighboring rows
    qctl get data orders --anchor-row-id 1042

    # find a row within the quarantined rows for one alert
    qctl get data 42 --is-bad-data --alert-item-id 8817 --anchor-row-id 1042

    # an exact table name that looks like an ID (the positional 42 means ID 42)
    qctl get data --table 42

    # inspect quarantined rows and which table rules flagged them
    qctl get data 42 --is-bad-data --include-dataset-rule-ids

    # inspect rows flagged by any instance of a rule family
    qctl get data orders --is-bad-data --rule email-check

    # export all quarantine rows flagged by that family
    qctl download data orders --is-bad-data --rule email-check --output ./email-check.csv.zip

    # add source-file provenance and truncate long cell values
    qctl get data 42 --show-metadata --max-cell-chars 80

    # match one complete displayed value; interpret a DateTime term in Los Angeles
    qctl get data orders --search-query 2026-09-15 --search-whole-value --search-timezone America/Los_Angeles

    # surface the unresolved comment threads on these rows, with their thread ids
    qctl get data orders --include-comment-threads

    # read the message behind every [A<id>]/[W<id>] marker on the page
    qctl get data 42 --is-bad-data --include-issues

    # only the quarantined rows one alert holds
    qctl get data 42 --is-bad-data --alert-item-id 8817

    # export just those rows instead of reading a page of them
    qctl download data 42 --is-bad-data --alert-item-id 8817

    # only the quarantined rows somebody has explicitly held back
    qctl get data 42 --is-bad-data --quarantine-hold hold

    # the undecided rows the table keeps until someone approves them, outside a submitted review; Row State names each one's reason
    qctl get data 42 --is-bad-data --held-for-approval

    # only those held as possible duplicates (the reason alone also matches decided rows)
    qctl get data 42 --is-bad-data --held-for-approval --approval-hold-reason possible_duplicate

    # the undecided rows in a submitted data review that is not closed; Row State reads waiting-for-approval
    qctl get data 42 --is-bad-data --waiting-for-approval

    # this request's rows still needing your approval (approver is the default view)
    qctl get data 42 --is-bad-data --review-group-id 11111111-2222-4333-8444-555555555555 --request-state to_review

    # this request's rows you actively flagged
    qctl get data 42 --is-bad-data --review-group-id 11111111-2222-4333-8444-555555555555 --request-view approver --request-state flagged_by_me

    # the sender view's rows still waiting for enough approvals
    qctl get data 42 --is-bad-data --review-group-id 11111111-2222-4333-8444-555555555555 --request-view sender --request-state waiting

    # raw backend response for scripts, instead of the Markdown payload
    qctl get data 42 -o json

    # why is this row quarantined: every rule verdict ever recorded for it
    qctl describe row 1042 --table orders

    # the same, listing every manifest entry instead of only the ones that acted
    qctl describe row 1042 --table-id 42 -v

    # the raw evidence for a script or an audit trail
    qctl describe row 1042 --table orders -o json

    # read the signatures the delete verbs take (the ROW SIGNATURES section)
    qctl get data orders --is-bad-data

    # bring one reserved system column back into the table
    qctl get data orders --is-bad-data --fields email --fields row_number_

    # drop every quarantined row that failed validation; a delete always takes a reason, and these rows load again if re-sent
    qctl rows delete-quarantined orders --status failed_validation --reason "bad export"

    # keep two lines from loading again: delete them by signature (the ROW SIGNATURES section)
    qctl rows delete-quarantined orders --signature 9f2a4c1e --signature 1b7c03d5 --reason "duplicate upload"

    # who deleted which rows, when and why: newest delete first, with the reason given
    qctl get deleted-rows orders

    # the rows one delete removed, as data (DELETE-ID in the listing)
    qctl get deleted-rows orders --delete-id 17 -o yaml

    # deleted rows that came from one file, or from one cloud source, a page of 100 at a time
    qctl get deleted-rows orders --file-id 311
    qctl get deleted-rows orders --cloud-source s3-nightly --page 2 --limit 100

    # release two held rows back toward the clean table
    qctl rows release orders --row-id 1042 --row-id 1043

    # approve every row held for approval; under a review policy or quarantine_rows_until_approved this records your approval, and a row is released only once it has enough approvals
    qctl rows release orders --status held_for_approval

    # send quarantined rows back through validation
    qctl rows reprocess-quarantined orders --all

    # park EVERY live clean row for manual review (a different route)
    qctl rows send-to-quarantine orders --all

    # send EVERY live clean row back through validation (the same move-all route)
    qctl rows reprocess-clean orders --all

    # park rows with a note kept as a discussion on them (--comment is optional)
    qctl rows send-to-quarantine orders --row-id 1042 --comment "wrong currency"

    # reprocess every clean row after adding rules, telling the table's followers why
    qctl rows reprocess-clean orders --all --comment "new currency rule"

    # how many quarantined rows say "N/A" anywhere? (preview only, writes nothing)
    qctl rows search-replace orders --search "N/A" --replace "" --dry-run

    # strip leading whitespace from one field of the quarantined rows
    qctl rows search-replace orders --search '^\s+' --replace "" --regex --field city

    # delete an exact-case marker, in one source, without a prompt
    qctl rows search-replace orders --search "TBD" --replace "" --case-sensitive --cloud-source-id 7 --yes

    # write one field on the quarantined rows you name (the grid's cell edit)
    qctl rows set-cell orders --row-id 1042 --row-id 1043 --field state --value CA

    # blank a cell: an empty string, which is not a SQL NULL
    qctl rows set-cell orders --row-id 1042 --field notes --value "" --yes

    # read a row back (set-cell prints this line for each row it named)
    qctl get data orders --is-bad-data --filter-by-field-name id --filter-by-field-value 1042

    # who changed this row's cells, when and why: the row's own change log
    qctl get data orders --is-bad-data --show-row-logs --filter-by-field-name id --filter-by-field-value 1042

    # the table's record of its cell edits: an item names a change, not the rows it touched
    qctl get history --table orders --model TableValueOverwrite

    # are these columns a key over the clean rows? (exit 0 yes, exit 1 no)
    qctl rows check-unique orders --column order_id

    # a composite natural key: the columns are checked TOGETHER, never one at a time
    qctl rows check-unique orders --column region --column order_id

    # the verdict as data, with whatever duplicate groups the server sampled
    qctl rows check-unique 42 --column email -o json

    # this row is fine: stop ONE rule flagging it, in one cloud source, with a reason on record
    qctl rows ignore-rule orders --cloud-source-id 7 --rule email_check --row-id 1042 --reason "known test account"

    # every row a rule is currently told to ignore in that source
    qctl get rule-ignores orders --cloud-source-id 7 --rule email_check

    # every rule ignored on one row, as data
    qctl get rule-ignores orders --row-id 1042 -o yaml

    # let the rule flag that row again
    qctl rows unignore-rule orders --cloud-source-id 7 --rule email_check --row-id 1042

    # what should this cell say? the values the recommender proposes, best first
    qctl get value-recommendations orders --field state --value CA

    # what does this column normally hold? (an empty query lists its own values)
    qctl get value-recommendations orders --field state --value "" -o name

    # rank for the alert holding the cell: its allowed values are searched first
    qctl get value-recommendations 42 --field state --value Calif. --alert-item-id 8817

    # narrow the value mappings consulted to one cloud source of this table
    qctl get value-recommendations orders --field city --value "Anahiem" --cloud-source s3-nightly

## GOTCHAS

- `get data`, `download data` and `rows` accept `--shared` to select shared tables; otherwise they use owned tables. Shared selection resolves table names among tables shared into the current organization and selects their third-party data routes, including row confirmation counts. Pass `--shared` on every invocation; it is not a context setting and qctl does not retry against owned-table routes.
- With `--shared`, row operations support `--cloud-source-id` and `--file-id` wherever that verb supports the scope, but refuse `--cloud-source` names, `rows ignore-rule` and `rows unignore-rule`. Shared-source and shared-file writes send the selected table as `dataset_id`. `get data` refuses `--include-comment-threads`, `--include-issues` and `--rule`; `download data` also refuses `--rule`. Use `--dataset-rule-ids` for a rule filter by UUID. These unsupported combinations exit 2 before credentials or requests.
- qctl has no `rows delete-clean`: only quarantined rows can be deleted. Move clean rows with `rows send-to-quarantine --row-id`, then delete them with `rows delete-quarantined --signature --reason`; `qctl rows delete-clean` exits 2 with that recipe.
- `rows delete-quarantined` requires `--reason` at every scope and selector, sent as the delete's `comment`; a missing or blank reason, or one over 10000 characters, exits 2 before any request.
- the server stores a delete's reason with who deleted which rows and when. [backend]
- `get deleted-rows` lists the newest delete first and a delete's rows by row id. A row is listed once per delete that removed it, so a row restored by undo and then removed by a new delete appears twice, while a redo flips the original record's `undone` back to false instead of adding one. [backend]
- an undone delete stays in `get deleted-rows` with `undone` true. A delete that wrote no exclusion entry is marked undone only when the undo restored all its rows, but a `--signature` delete that added exclusion entries is undone as a change to that exclusion list and is marked undone even when some rows were not restored. [backend]
- an external user sees only the deleted rows of the cloud sources granted to them, and `get deleted-rows` naming another source with `--cloud-source-id`, or a file outside the grant with `--file-id`, answers 403 (exit 4). [backend]
- for every other caller, `get deleted-rows --file-id` naming a file of another table answers 404 (exit 3), while a `--cloud-source-id` is not checked against the table: a source of another table lists nothing. [backend]
- `get deleted-rows --file-id` matches a row through any file it came from, and FILE shows only the first (`+N` counts the rest; `-o json` lists them all). A file whose record is gone keeps its id with a null `file_name`, shown as `file/<id>`, but that id cannot be a `--file-id` filter: the route answers 404 (exit 3) for a file that no longer exists. [backend]
- `get deleted-rows` checks `--limit` (1-100) and `--page` before any request (exit 2), has no `--shared` form, and auto-detects no cloud source: without a cloud-source flag it sends no source filter. After a delete that removed rows, `rows delete-quarantined` prints a `qctl get deleted-rows` line, narrowed to its cloud source at cloud-source scope, to nothing at file scope (it lists the whole table), and never to `--delete-id`.
- `rows delete-quarantined` with `--file-id` reads the file metadata and verifies its table before confirmation, including with `--yes`. A file from another table exits 2; a failed metadata read stops the command without deleting rows. With `--shared` the metadata comes from the shared file read, so a server without that route fails the command with 404 (exit 3) and nothing is deleted.

- `get data --anchor-row-id <id>` opens the page containing that row under the same filters and ordering, overriding `--page`; a row outside the selected clean/quarantine bucket or filters returns 404 (exit 3). The response includes the one-based resolved `page`. [backend]
- The Markdown summary and next-page hint use the resolved page. Remove `--anchor-row-id` when continuing with `--page`, and keep the other filters, ordering and limit. An anchored 404 names the row, table, bucket and explicit filters; it does not prove the row is absent from the table. `--anchor-row-id`, `--page` and `--limit` must be positive (exit 2 before any request); the default limit is 20.

- `get data` needs `source:data:read`. External callers can use `--table-id` to read rows from sources assigned to them in the current organization; table-name lookup requires separate table-list access. Source data access does not grant table settings, value recommendations or whole-table row operations. [backend]

- While waiting for a prepared download, `--wait-timeout` and SIGINT/SIGTERM cancel an inbox poll in flight, including a request waiting to retry; a successful response arriving after cancellation is discarded.

- `--rule <slug>` on `get data` and `download data` resolves an exact family slug from `get rules` and selects all of its instances on the chosen table, across releases and lifecycle states, by family ID. The RULE column of `get table-rules` is the family's display name, so use `get rules --columns slug,name` to find its slug. `--rule` requires `--is-bad-data` and conflicts with `--dataset-rule-ids`; an unknown family or a family with no instances on this table exits 3 before reading data or queuing an export. A family match can still return zero flagged rows.
- Empty positional table references in `get data` and `download data` exit 2 before authentication or requests; omit an optional positional argument instead of passing `""`.
- `--search-whole-value` changes `--search-query` from substring matching to an exact match against the displayed cell value; `--search-timezone` accepts an IANA zone and controls which half-open UTC range a DateTime day term names (default UTC), while Date columns ignore the zone. Both flags are available on `get data` and `download data`; an unknown zone is rejected by the backend. [backend]
- the Markdown view applies each numeric column's server-declared display format: currency gets a `$` and grouping, percent scales the stored fraction by 100, and `display_decimals` controls half-away-from-zero rounding; a plain number with no `display_decimals` is left unformatted — a Decimal keeps the digits the server sent, while a Float sent as `100.0` prints as `100`. On a quarantine page a cell marked `[U]` is the exception — Atlas says it still contains unconverted source text, so qctl leaves that text untouched. `-o json`/`-o yaml` keep the server's values plus `field_display_formats` and `not_converted` arrays, and a Decimal cell arrives as a string carrying every stored digit, with trailing fractional zeros dropped — so the display format is the only rounding: a money cell storing `1.00499` arrives as `1.00499` and prints as `$1.00`, the `1.00` that search and the CSV export also show. [backend]
- `--filter-by-field-value` on a money or percent column is compared with the STORED value, not the displayed one: for `equals`, `not_equals`, `greater_than` and `less_than` — `equals` is the default `--filter-operator` — the backend drops `$`, `%`, commas and whitespace from the term and divides a percent term by 100, so `12.5` and `12.5%` both find a cell storing `0.125`, and a term that is not a number is a 400 (exit 2). The comparison is exact, so a money cell storing `10.005` shows as `$10.01` and `10.01` does not find it; on an `--is-bad-data` page it reads the converted value, so a cell marked `[U]` never matches, and `qctl rows set-cell` writes a cell's text without updating that value. A plain number column takes the term as typed, and `contains` goes through the search match instead. [backend]
- `--search-query` matches a number column as the DISPLAYED digits without their decoration: the term loses `$`, `%`, commas and whitespace and is never divided, so `12.5` finds a percent cell shown as `12.50%` and `1234.5` a money cell shown as `$1,234.50`, while a plain number with no `display_decimals` is matched as PostgreSQL prints the stored value; a term that is not a number matches no number column at all. `--search-whole-value` compares the whole rounded digits to your term, so `12.5` does not match a cell shown as `12.50%` but `12.50` and `12.50%` do. A quarantine cell matches its displayed digits once converted and its source text until then. `--search-regex` ignores `--search-whole-value` and `--search-timezone` and matches the stored text, except in a converted quarantine money, percent or `display_decimals` cell, where it matches the displayed digits with no `$`, `%` or commas: `^12\.50$` finds a converted quarantine percent cell shown as `12.50%` but not a clean one, whose stored text is the fraction. [backend]
- a caller who sees a table's PII masked — no `pii:view` (the `read_only` and `agent` roles) and no active PII access grant on the table — finds a masked column's cell only by its whole stored value: `--search-query` matches that column only on a literal, case-sensitive equality, typed on the clean table and as text on an `--is-bad-data` page, whatever `--search-regex`, `--search-case-sensitive` or `--search-whole-value` say, so the display-digit and date-range matching above do not apply to it, while the other columns keep the chosen mode. A `--search-by-field-name` naming a masked column also skips the server's regex validation, so an invalid pattern is a literal term there instead of a 422. `--filter-by-field-name <masked column>` takes only `--filter-operator equals` (the default) and `contains`, both as whole-value equality; `not_equals`, `greater_than` and `less_than` are `400 PII columns support exact value filters only for a masked viewer.` (exit 2). `download data` applies the same rules, and `get data -o json` names the masked columns in `masked_fields`. [backend]
- `get data` names every column it carries masked on a `Masked fields:` line in the summary — including masked columns outside `--fields`, whose values still reach CELL HISTORY — and prints each masked cell, steward-pinned value and row-log value as sent, never in the column's display format. [backend]
- `get data --order-by` and `download data --order-by` naming a column the caller sees masked, with or without a leading `~`, are refused with `400 PII columns cannot be sorted by a masked viewer: <columns>.` (exit 2), which names every masked column the ordering asked for; the other columns sort as usual. [backend]
- `qctl rows set-cell --value` on a percent column is in DISPLAY units, because the backend divides a numeric value by 100 when it writes the cell and marks it converted, so the re-clean that follows does not divide it again: `12.5` and `12.5%` both store `0.125`, and `0.125` stores `0.00125` — type what the grid shows, not what `-o json` returns. A money column takes dollars, with `$` and grouping commas stripped and nothing scaled. [backend]
- `qctl rows search-replace` rewrites a cell's stored TEXT, so on a percent column the units are whatever that cell holds: a converted cell holds the fraction (`0.125`) and stays marked converted, so a replacement there is kept as written — nothing divides what you typed, unlike `set-cell` — while a cell still marked `[U]` holds its source text (`12.5%`) and is divided by 100 when it is re-cleaned. `--search` is matched against that same stored text, not the displayed value. [backend]
- `download data` writes a money, percent or `display_decimals` column as its rounded DISPLAY digits with no `$`, grouping comma or `%` — a percent cell storing `0.125` is `12.50` in the CSV — while a plain number is written as PostgreSQL prints it and a quarantine cell still marked `[U]` keeps its source text, so the CSV and `get data -o json` agree on such a column only where a value already has exactly its display places: a percent cell (`0.125` against `12.50`) differs, and so does a money cell storing `1250.50`, which `-o json` sends as `1250.5`. [backend]

- `download data` exports the WHOLE matching set, not the page `get data` shows: the download worker overwrites `page` to 1 and `limit` to ten million before it paginates, so the only ceiling on an export is 10^7 rows. [backend]
- what lands on disk is a ZIP ARCHIVE holding one CSV, not a CSV: the server names the export `<name>.csv` and stores it zipped under that name plus `.zip`, so the default file always ends `.csv.zip`. On current servers it is DATE-NAMED, `<table> - <Clean rows|Quarantine rows>[ including deleted][ (filtered)] <UTC YYYY-MM-DD>.csv.zip`, with ` including deleted` whenever `--deleted-rows` is not `live`; on older servers it is DIGEST-NAMED, `<table-slug>__<filter-tokens>__<digest>.csv.zip` with the `.csv` name capped at 120 characters, and on the oldest servers the cap cuts from the end, so a long name could lose part or all of its digest. qctl writes the bytes as it receives them rather than unzipping (`download file` does not unzip a decrypted backup either), so an `--output` naming a bare `.csv` gets you a zip wearing that name. [backend]
- with no `--output` the destination is the name the SERVER supplies, and qctl reduces it to a bare filename in the working directory: a name carrying `../` or a leading `/` picks the file and never the directory. An `--output` you type is used exactly as typed, so `--output ../archive/orders.csv.zip` still writes where you said.
- qctl CREATES the file `0600`, owner-only, because a whole-table export is the most sensitive thing this CLI writes. That is the create mode: `--force` onto a path that already exists overwrites the contents and leaves that file's own permissions alone.
- that member CSV is the only format on offer: the server writes it with `COPY (...) TO STDOUT WITH CSV HEADER DELIMITER ',' null as '\N'`, and an export with masked PII columns is rewritten in exactly that format, so inside the archive you always get a comma delimiter, a header row, and the two characters `\N` for a SQL NULL rather than an empty field — there is no format flag because there is no format choice. [backend]
- `download data` follows the requester's PII visibility: for a caller without `pii:view` — the `read_only` and `agent` roles — who holds no active PII access grant on the table, every non-NULL cell of each PII column (`spec.pii_columns` plus each column a personal-data rule checks) is written as `•••••` followed by its last 4 characters when the exported text has 9 or more characters, else `•••••` alone, and so are those fields' entries in an exported `row_logs_` column; a NULL stays `\N`. Visibility is decided when the export is queued, so a grant that ends before the file is built does not change that file, and one gained afterwards does not unmask it — re-run the export. Nothing in the file name, the queue response or qctl's output says the CSV is masked; an unmasked export is recorded against the requester. [backend]
- `--page`, `--limit`, `--include-history-flags` and `--include-dataset-rule-ids` are NOT offered by `download data` even though `get data` has them and the route still accepts them: the worker overwrites the first two and the endpoint `del`s the last two unread (`include_history_flags` is "accepted for signature parity only"), so any of them would report a choice the export never made. [backend]
- `download data` announces its wait on stderr before the first poll — `export queued; waiting for the file, for up to 15m0s; re-running this command requests the export again`, the budget being `--wait-timeout` (900 seconds by default) — and an already-queued repeat's `This export was already queued; waiting for it to finish...` goes to stderr as well, so stdout carries only `Successfully downloaded file to: <path>`; `--no-wait` prints no banner, only `Export queued. Re-running without --no-wait requests the export again and waits for the file.` on stdout. Running out of `--wait-timeout` exits 124 with `timed out waiting for the file to be ready` followed by `re-running this command requests the export again`, and writes nothing; SIGINT during the wait exits 130 and SIGTERM 143, after `interrupted; re-running this command requests the export again` on stderr. There is no resume command for either: re-running requests the export again.
- `download data` uses visible escapes for terminal controls such as ESC, BEL and CR in the success path and mark-read warning. Escaping affects the printed text only; the file is written to the original destination, and a mark-read failure still exits 0.
- a repeat of an IDENTICAL export does not add a second inbox row as long as its object key comes out the same: the key is built from the request parameters with no counter or random part — and, for a date-named export, from the UTC date too, so the same export on a later UTC day gets a new key and a NEW row — and a same-key repeat upserts the one notification keyed on that object, bumping COUNT, refreshing `last_notified_at` and clearing `read_at`/`dismissed_at` while its id stays put, which is why qctl correlates on a timestamp and never on a new id. [backend]
- a repeat of an export is refused `409 ERR_QUEUE_KEY_CONFLICT: This view is already queued for downloading` (a code-less 500 on older servers) only in a NARROW window — while the queue message is still unacknowledged, which is the seconds between the POST and the scheduler deploying the export job, NOT the whole time the export runs; inside it the queue key IS the object key, so the refusal means an export writing the same object as yours is already queued and qctl waits for that object, while under `--no-wait` there is nothing to wait for and it stays an error (exit 2 on newer servers, 1 on older ones). That object is the file you asked for unless two different requests share a key, as two long digest-named ones can on older servers where the 120-character cap cut off their digest. The refused repeat still overwrites the queued request with its own, so if the scheduler has not yet picked the message up the job builds YOUR file and notifies you; once it has, qctl collects the other request's file at exit 0 if you sent both, and times out if another user sent the first, because only that job's sender is notified. Once the job is deployed the message is acknowledged and a repeat enqueues a SECOND identical export instead of being refused, which is harmless: while the first export's job is still running the scheduler declines to deploy the second under the same job name and drops it, and after that a second run writes the same object and bumps the same one inbox row. [backend]
- on a server that sends digest-named exports an export can be dropped between the queue and the job with nothing to show for it, and that is NOT the harmless repeat above: the k8s job name is `download-data-view-ds<table-id>-<object key>` truncated to 63 characters and that key carries its distinguishing digest LAST, so on a table whose slug and leading filter tokens fill that budget two exports with DIFFERENT filters share one job name. While the first job's pod is unfinished the second deploy is refused with an error string and creates no Job, and the scheduler acknowledges the queue message regardless of that outcome — so the POST you got a 200 for produced nothing, and the `already queued` refusal cannot warn you because that window closed when the first job was deployed. Re-running re-enqueues it; wait for the first export to finish first. A date-named export's key starts with its digest, so two different exports never share a job name there. [backend]
- the inbox row does carry a `file_name`, but it does not identify an export's request — every filtered export of one kind on one table shares a date-named export's name for the whole UTC day, and a digest-named one hashes parameters the CLI never fully sees — so what identifies it, on a server that returns a `download_handle`, is the `download_handle` the queue POST answers with: the DIGEST half of the object key, repeated on the inbox row, where an equal one is the match outright and a DIFFERENT one is REJECTED, which is what tells two exports of ONE table in flight at once apart. - `--alert-item-id` narrows to the rows ONE alert holds and qctl refuses it without `--is-bad-data` (exit 2, on `get data` and `download data` alike): the filter is applied only under `is_bad_data` server-side, and unlike `dataset_rule_ids_` the parameter is absent from the endpoint's bad-data-only 400 list, so a clean-rows request would be accepted, have the filter dropped, and answer 200 with the whole unfiltered page. - `--quarantine-hold` filters quarantine rows by the manual hold decision and qctl refuses it without `--is-bad-data` (exit 2, on `get data` and `download data` alike): each of `hold`, `release` and `undecided` is an EXACT predicate on `keep_in_quarantine_` — `IS TRUE`, `IS FALSE`, `IS NULL` — so `release` is not the "anything but held" bucket, `--quarantine-hold release` is the same `keep_in_quarantine_ IS FALSE` predicate `qctl rows ... --status approved` selects on, and `undecided` includes the rows held for approval and the rows waiting for approval — add `--held-for-approval=false --waiting-for-approval=false` for the undecided rows that are neither; `get data` also hides deleted rows unless `--deleted-rows` asks for them, and every status-based bulk verb, `reprocess-quarantined` included, skips them. - a quarantined row is HELD FOR APPROVAL when nobody has decided it — `keep_in_quarantine_` NULL, `--quarantine-hold undecided` — and no data-review submission (`qctl data-review request`) holds an unclosed review of it, which would make it WAITING FOR APPROVAL instead, and the table would keep it even once it has no issues, for one of three reasons, the first that applies winning: `possible_duplicate` (the loader quarantined it as a suspected duplicate, `suspected_duplicate_` TRUE), `review_policy` (the table's effective data-review policy has `requires_review`) and `table_setting` (the table's `quarantine_rows_until_approved`). The reason is derived from the two settings and that marker on every read and every re-validation and is never stored, so changing a setting changes every row's reason at once, and a person's `hold` or `release` overrides all three. The review policy holds only a row already in quarantine: a new row that passes at ingest goes to the clean table, which `quarantine_rows_until_approved` would have stopped. [backend]
- `--held-for-approval` lists exactly those rows and `--held-for-approval=false` every other quarantined row — the decided ones, the ones waiting for approval and the undecided ones nothing holds — while `--approval-hold-reason <reason>` matches the row's reason WHATEVER its decision, so pair the two for the undecided rows held for one reason; the backend answers 400 for either filter on a clean read, `=false` included. Approve them with `qctl rows release <table> --status held_for_approval` or through a data review (`qctl guide review-data`); on a table whose review policy requires review or whose `quarantine_rows_until_approved` is on, that release is no longer refused for a row the review gate blocks: it records your approval on each row you may approve and releases only the rows the review gate then lets through. [backend]
- `held_for_approval` counts rows that may still have issues: while the review policy or `quarantine_rows_until_approved` is on, EVERY undecided quarantined row reports a reason, failing rows included, so `qctl rows release --status held_for_approval` also approves rows that are still invalid — a released row leaves as soon as it passes, and releasing it does not make it pass — and the prompt's `N` counts the rows the release matches, not the rows that will reach the clean table. `qctl describe table` prints the table's hold counts — on hold, approved, waiting for approval, and held for approval split by reason — from the same count endpoint over the whole table; the endpoint can narrow to one cloud source or file, a cloud-source-scoped `qctl rows` prompt asks it for that source, and there is no organization-wide count. [backend]
- with both the review policy and `quarantine_rows_until_approved` on, every row that is not a suspected duplicate reports `review_policy` and none reports `table_setting`, so `--approval-hold-reason table_setting` finds nothing, and turning off only one of the two moves nothing, because the other still holds every undecided row. The change that turns off the last one — a table PATCH (`qctl apply table`), an undo or redo of that setting, or a data-review policy PUT or DELETE that ends `requires_review` — re-queues every live undecided quarantined row for validation, but best-effort: it runs after the change commits and a failure is only logged, so re-check with `--held-for-approval` rather than assume the rows moved. A suspected duplicate stays held either way. [backend]

- a `[S]` on a cell means a steward overwrite on that field is still in effect — no undo, revert or applied cell override has ended it, and undoing the later of two stacked overwrites leaves the earlier one in effect — and the STEWARD OVERRIDES section below the table names the value the steward fixes in effect displaced. [backend]

[backend]
- the match count `qctl rows search-replace` prints is summed PER FIELD, not per row: with no `--field` the controller adds `len(rows)` once for every field it searches, so a row whose value appears in two fields is counted twice and the preview can exceed the table's whole quarantined-row count. With `--field` there is one field to sum and the number is rows. [backend]
- a `qctl rows search-replace --dry-run` cannot see skips, and that is the loop's shape rather than a missing feature: the dry run adds the match count and `continue`s before a single row is examined, so `replaced_rows`, `skipped_rows` and `fields_affected` are all zero on a preview and say nothing about what the write will do. Whether a matched row's replacement changes anything is only computed on the real run, and a row where it changes nothing is skipped. [backend]
- `qctl rows search-replace` skips a row that turns busy DURING the write, not before it: the write runs its own SELECT, which already drops a row an ingestion job has claimed or one queued for processing, so a row that turned busy after the preview is not matched at all — it is missing from the write's matched count rather than added to its skipped one. Only a row queued between that SELECT and the batched UPDATE, which carries `AND b.awaiting_processing_ IS NOT TRUE` a second time, is not returned and lands in `skipped_rows`. Replaced rows are then queued for re-validation after the commit, and rows still claimed by an active ingestion job defer through a reprocess intent rather than being stolen mid-flight. [backend]
- `qctl rows search-replace` REVOKES an approval on every row it replaces and never puts one on hold: the UPDATE writes `keep_in_quarantine_ = NULLIF(keep_in_quarantine_, FALSE)` whatever the table's settings, so a row someone released goes back to undecided — waiting for approval while it keeps an unclosed submitted review, otherwise held for approval again wherever a hold reason applies — while a held row stays held and an undecided one stays undecided. The SQL match and the Python replacement read the term the same way, so a wildcard replaces the whole span it matched, and `*` reaches as far as it can: in the default case-insensitive mode `--search 'N*A' --replace X` turns `Name: N/A` into `X`. - a `--status` or `--all` delete skips, rather than refuses, a repeated key the selection splits — some but not all of the key's live copies match, because another copy is in clean data or outside the selection — and deletes the other rows; it does not skip a key whose duplicate group has an effective Keep one decision when every matched copy is one that decision did not load, and deletes those copies. The response's `skipped_repeated_keys` lists every copy of each skipped key, which qctl prints on stderr and adds to the `-o json`/`-o yaml` document only when the server skipped one. [backend]
- the `qctl rows` delete verbs take `--signature` (the hex `initial_signature_` column) and never `--row-id`: the route identifies rows that way, and an id turns into a signature only ONE ROW AT A TIME — `qctl get data <table> --is-bad-data --filter-by-field-name id --filter-by-field-value 1042` is the per-id lookup, and its ROW SIGNATURES section is where the hex comes from, but `GetDataParams` has no `ids` field and `FilterOperator` has no `in`, so there is no bulk form. [backend]
- `signature_` is hidden and is never returned by `qctl get data`, not even with an explicit `--fields signature_`; `initial_signature_` is the one qctl and the web UI both round-trip, and it is the hex the ROW SIGNATURES section prints for every row of the page. [backend]
- `qctl rows release` on a table that requires approval — its data-review policy requires review or its `quarantine_rows_until_approved` is on — records approvals instead of releasing outright, at EVERY selector: it needs `data_review:approve` (a 403 otherwise, and `APPROVER_NOT_DESIGNATED` when a row's review or the policy names approvers and you are not one), skips the rows you edited or submitted for review, records your approval of every other live row it matches and of each of that row's latest changes that carries no veto, and releases only the rows the review gate then lets through, setting the others it approved back to undecided, a held one included. It never reads `auto_release_on_approval`, closes no data review and exits 0 even when it releases nothing: it prints the rows it released, the ones short of approvals (`1 of 2 approvals`), the ones approved but still held — an open alert keeps a releasable row out of `released_row_ids` — and how many it skipped, with the skipped row IDs when returned by the server (up to ten in prose, every ID in JSON/YAML). `qctl rows hold` and `qctl rows reset-hold` never record an approval — that path is keyed on the `release` member of `quarantine_hold`, not on "anything but hold", so a reset never closes the rows' data reviews either. [backend]
- `qctl rows reprocess-clean` sends `quarantine_hold: undecided`, not a null: `quarantine_hold` replaced the nullable `keep_in_quarantine` boolean and is non-nullable on the by-id move route, so the explicit null qctl used to send is now a 422 — and it defaults to `hold` there, so an OMITTED value parks the rows instead of reprocessing them. `qctl rows send-to-quarantine` sends `hold`, `qctl rows hold`/`release`/`reset-hold` send `hold`/`release`/`undecided`. [backend]
- a row reprocessed by `qctl rows reprocess-clean` or `qctl rows reset-hold` carries no hold decision, so it returns to the clean table only if it passes AND nothing holds it for approval — a table that quarantines rows until approved, or one whose data-review policy requires review, keeps an undecided row in quarantine even once it is valid, where Row State reads `held-for-approval=<reason>`, or `waiting-for-approval` while a submitted data review of the row is not closed. A suspected duplicate does not pass while its duplicate group holds it: the group's hold alert keeps it in quarantine, released or not. A row `qctl rows release` released is exempt from the other two and leaves as soon as it has no issues. [backend]
- `qctl rows reprocess-quarantined --status` skips rows already queued for processing; `--row-id` and `--all` do not. [backend]
- a repeated `--row-id` or `--signature` names the row ONCE: `qctl rows` drops duplicates before it acts, so the confirmation prompt's count and the result line agree with the single row the backend's `IN` list touches. The order you typed is kept, first occurrence winning.
- every delete route returns an affected-row count, which qctl prints; a response without one prints "requested" rather than a number. The two move-to-quarantine routes instead return `moved`, `already_in_quarantine` and `not_found`, which qctl reports separately. [backend]
- `rows send-to-quarantine` and `rows reprocess-clean` (either selector) always print the returned moved count, including zero; nonzero already-quarantined counts go to stdout on the table view and missing-ID warnings to stderr. If every explicitly requested ID is missing, the breakdown goes through the error path with exit 3 and no success headline. Other successful responses exit 0, including already-quarantined no-ops, skipped-plus-missing outcomes with none moved, and an empty `--all`. Exit 0 does not promise every requested row changed. Older responses without a moved count say so rather than inventing zero.
- `rows release` keeps exit 0 for a successful approval attempt even when every matched row was skipped; its skipped rows are reported separately and never counted as approved or released. Older responses may omit `skipped_row_ids`; qctl keeps the skip count and reason without inventing IDs. `hold` and `reset-hold` keep their `{affected_rows}` output because they take no approval path.
- under `-o json` and `-o yaml` the `rows` writes print a result document and move their prose to stderr: both deletes, `reprocess-quarantined`, `hold` and `reset-hold` print `{affected_rows}`, null when no count came back, to which a `--signature` delete adds `unmatched_signatures` and `not_excluded_signatures` and a `--status` or `--all` delete adds `skipped_repeated_keys` when it is non-empty; `release` prints `{affected_rows, skipped_rows, skipped_row_ids, released_row_ids, approvals}`, the last four null unless the table requires approval — its data-review policy requires review or its `quarantine_rows_until_approved` is on; `send-to-quarantine` and `reprocess-clean` the server's `{moved, already_in_quarantine, not_found}`, plus `comment_thread_id` or `notified_user_count` when the server set one; `search-replace` the route's `{fields_affected, matched_rows, replaced_rows, skipped_rows}`, the preview's under `--dry-run` or when nothing matched; and `ignore-rule` the created ignore records. None of them has a `-o name` view, because a selector names no rows, and `set-cell` and `unignore-rule` print prose only and exit 2 on `-o json`, `-o yaml` or `-o name`.
- the move counts confirm movement into quarantine, not completed validation or a return to clean data. Already-quarantined rows are skipped without applying a hold decision or triggering reprocessing for them; use `qctl rows reprocess-quarantined <table> --row-id <row-id>` for those rows. The response gives aggregate counts, not the skipped IDs. [backend]
- `--comment` on `qctl rows send-to-quarantine` and `qctl rows reprocess-clean` is optional, and without it the request is unchanged. With `--row-id` it opens ONE discussion on the requested rows, moved or already in quarantine, and qctl prints `qctl describe comment-thread <id> --table-id <t>`; with `--all` it opens no thread and instead notifies the table's internal followers other than you, and qctl prints how many — 0 when nothing moved. A comment covers at most 500 rows. An internal user's comment is hidden from the sender unless `--visible-to-sender`, which the server refuses with 409 `MOVE_COMMENT_SPANS_SOURCES` unless every row comes from one cloud source; on a `--shared` table the comment is always internal and cannot mention anyone. A refused comment moves nothing. [backend]
- `qctl rows send-to-quarantine --all` and `qctl rows reprocess-clean --all` take a SECOND route (`move-all-rows-to-quarantine`), not a wildcard over the by-id one: it moves every live clean row of the table in batches, and qctl sends it the verb's `quarantine_hold` exactly as on the by-id route — `hold` parks the rows, `undecided` sends them back through validation. The route honors that value on current servers; an older server ignores it and parks every row, `reprocess-clean --all` included. [backend]
- `qctl rows send-to-quarantine --all` and `qctl rows reprocess-clean --all` can outlive qctl's 30-second default request timeout on a large table: the route walks the clean side in 5000-row batches inside ONE request and commits once at the very end, so there is no partial progress to observe and a client-side timeout reports failure for a move the server is still running — raise `--request-timeout`, and re-read `qctl describe table` before retrying. [backend]
- With `--cloud-source` or `--cloud-source-id`, `rows delete-quarantined`, `reprocess-quarantined`, `hold`, `release` and `reset-hold` on a table-series source act only on that source's rows in the table you name (positional, `--table` or `--table-id`); the table is required even for the template period. qctl sends that table as `dataset_id` on the source route. Without it the server answers 400, and it rejects a target outside the source's series. [backend]
- `qctl rows hold`/`release`/`reset-hold --all` exists only at cloud-source scope; at table scope the backend rejects an empty selector with 422. All three are one route separated by `quarantine_hold`, so the selector matrix is identical for the three of them. [backend]
- `qctl describe table`'s validation breakdown is the strict count (`IS TRUE`/`IS FALSE`), so the two figures are exact but need NOT sum to the quarantined total — a row whose `passes_validation_` is NULL is in neither bucket, and the counter also drops `is_deleted_` rows. It is also a LOWER BOUND for the rows a table-scoped `qctl rows … --status failed_validation` selects, whose filter is `IS NOT TRUE`, except under `reprocess-quarantined`, which also skips rows already queued for processing; at cloud-source scope the write selects only that source's rows, while the count is the whole table's. [backend]
- `describe row` reaches BOTH sides of the table from one id: the route resolves it against the clean rows first and the quarantined rows second, and takes no `is_bad_data` (nor any other query parameter). Both probes skip tombstoned rows, so a deleted row is not found (exit 3) rather than an empty answer. [backend]
- the evidence widens past the row's current id: a run recorded under a PREVIOUS id is included whenever it shares this row's `initial_signature_`, because a composite recompute tombstones a row and resurrects it under a new id while keeping the signature. Those runs name the older id on their own block, so the payload never silently attributes them to the current one. [backend]
- a run whose `RuleRun` belongs to another dataset is DROPPED from the response with no marker of any kind — without that run's manifest there is nothing to decode its verdict vector against — so `results` can be shorter than what the row's evidence table actually holds, and neither the count nor a gap in the run ids shows it. [backend]
- `Runs: 0` does NOT mean the row was never evaluated: a dataset whose `<table>_rule_verdicts` table has not been provisioned answers 200 with an empty `results`, which is indistinguishable here from a row that genuinely has no verdicts. [backend]
- a null verdict has TWO different causes and `describe row` spells them differently: `unrecorded` means the run's stored verdict vector was shorter than the manifest it ran, so nothing was recorded at that position, while `unnamed code N` means the integer is one this build of the server has no name for — a vector written by a newer build. Neither is "the rule did not run". [backend]
- the `Unattributed issues` line is the row's alert and warning tokens that no entry in that run's manifest claimed: the item they came from no longer names a dataset rule, or no longer exists at all. A row can be quarantined by one of these, so they are printed rather than dropped — but no rule on the table explains them. [backend]
- `describe row` names rules by the same `r-*` aliases `get data --include-dataset-rule-ids` allocates, out of the same local store, so an alias means the same rule in both; it prints them bare (`r-1`) rather than in the `[R: r-1]` wrapper the data page's packed column needs. The revision is its 8-hex SHORT ID, cached on the way out so `qctl get rule <short>` resolves it without listing the catalog; the full UUID is in `-o json`.
- by default `describe row` lists only the manifest entries that did something to the row and counts the rest (`passed`, `not_evaluated`); `-v` lists every entry. An outcome qctl does not recognise is always LISTED, so if the backend renames a verdict, rows appear that used to be summarised rather than the reverse.
- `rows ignore-rule` suppresses one table rule on one row of one cloud source, clean or quarantined. On a clean row it also takes the rule's unresolved warnings of that cloud source off the row, leaving its cells as they are, and a call naming only clean rows reprocesses nothing. When a named row is quarantined, the reprocess it triggers is not limited to that row: every quarantined row the rule flags, in every cloud source of the table, is queued for re-validation, mirror-loaded tables included. A row the rule no longer flags can then leave quarantine unless something else keeps it there. A later upload keeps the ignore only on a mirror table, for a line with the same key (on a keyless table, the same unchanged line), and on an append table, for the same key (without `key_columns`, the same unchanged line) in a new version of the same file; any other upload that carries an ignored row again can flag it again. Wherever it reaches the row, an ignore holds only while the rule keeps the revision it had when the row was ignored and the row's values in the columns the rule reads are unchanged: a run that finds either changed does not apply it, and discards it once the load succeeds. On a key the upload repeats or the cloud source already stores more than once (on keyed append, counting only earlier versions of that file), only the copy paired with the ignored row by equal content or most equal cells keeps the ignore, and lands in quarantine; every other copy can be flagged again. [backend]
- `rows ignore-rule` on a row that is already ignored for that rule keeps the existing ignore: that record, with its original reason and decider, is what comes back, and the new `--reason` is dropped for that row — but the call still queues the reprocess above when a named row is quarantined, as the first ignore did. Every `--row-id` must be a live row of the named cloud source, clean or quarantined, or nothing is ignored and the route names the unknown ids (exit 3). [backend]
- `rows unignore-rule` does not re-flag a row the ignore already let through: the re-validation it queues selects rows by the rule ids they carry, and a row re-validated while ignored no longer carries that rule, so the rule applies to it again only when the row is next re-validated for another reason. Its `--row-id` takes the `ROW-ID` column of `get rule-ignores`, not the quarantine listing: an ignore stays on its row when the row leaves quarantine, and the row keeps its id in the clean table. [backend]
- an ignore does not suppress every issue a rule raises: `validation_problem`, `required_field` and `guest_failure` issues are never suppressed, so a rule can go on flagging an ignored row through those. [backend]
- `get rule-ignores` needs `--rule` or `--row-id`, because the backend has no "every ignore on this table" listing, and it lists one cloud source at a time — a table with several sources has to be told which, and a table with one is used without being named. Only active ignores are listed, so an ignore a load discarded drops out of the list rather than showing as discarded; `-v` adds the `RULE-REVISION-ID` it was decided against. With both flags qctl applies both itself: the backend, given both, silently returns that row's ignores for every rule. [backend]
- when `get rule-ignores` omits both cloud-source flags on a table with several sources, qctl refuses the ambiguous listing with exit 2 and asks for `--cloud-source` or `--cloud-source-id`.
- `--rule` on `get rule-ignores` and `rows ignore-rule`/`unignore-rule` accepts a server-scoped `r-*` alias; one that exists only in another server's cache is not found (exit 3), while the same spelling can resolve to a different rule when both servers allocated it. A registered alias for another resource kind is bad usage (exit 2).

- `describe row` lists a `not_applicable` verdict at default verbosity: the rule's row filter skipped this row, so it raised no finding. The JSON and YAML evidence include the run's `row_filter` when recorded. [backend]
- the table's change review policy governs the `rows` verbs that change rows: `delete-quarantined` (operation `rows_delete`, or `bad_rows_delete` when it deletes every quarantined row), `send-to-quarantine` and `reprocess-clean` (`rows_quarantine_move`), `hold`, `release` and `reset-hold` (`quarantine_hold_update`, keys `hold`, `release` and `undecided`), `set-cell` (`clean_cell_modify`), `search-replace` (`cell_values_search_replace`, checked on the write only: its preview and `--dry-run` are not, so the refusal comes after the preview) and `ignore-rule` / `unignore-rule` (`rule_row_ignore_create` / `rule_row_ignore_delete`), with `--cloud-source` or `--file-id` too, under the policy of the rows' table. A refusal is a 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4) whose `Hint:` names the operation and the refused keys and points at `qctl get change-review-policy --table <table>`; no key of these operations can be proposed, so `CHANGE_PROPOSAL_REQUIRED` never answers them. `reprocess-quarantined` and `check-unique` are not subject to the policy. A `duplicate-group` decision, which also moves and releases rows, is governed under `data_review_approve` instead. [backend]
