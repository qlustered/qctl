## USAGE

    qctl auth login
    qctl auth logout
    qctl auth me
    qctl auth sessions
    qctl auth sessions revoke [name-or-id]

## EXAMPLES

    # log in to the current context's server
    qctl auth login

    # show who you are logged in as
    qctl auth me

    # list active CLI sessions for the current organization
    qctl auth sessions

    # find sessions whose tokens expired without ever being used
    qctl auth sessions --never-used

    # inspect first use without adding a default table column
    qctl auth sessions --columns name,status,first_used_at

    # revoke an older session by its exact name (or use the displayed ID)
    qctl auth sessions revoke qctl@old-laptop-a1b2c3d4

    # clear every session whose token can no longer authenticate
    qctl auth sessions revoke --expired

    # revoke this CLI session on the server and forget the token
    qctl auth logout

    # only forget the local token, leaving the session alive on the server
    qctl auth logout --local

    # after a password or MFA reset: end every session and token, everywhere
    qctl auth logout --all

## GOTCHAS

- `auth me` uses the organization selected by `--org`, `QCTL_ORG`, or the current context for both its credential and request; it never substitutes the first cached organization.
- `auth me` prints a `Withheld Permissions:` line, left out when empty, naming the permissions your role grants that your organization has turned off, and `-o json|yaml` carries them as `withheld_permissions`. Turning data editing off for staff withholds `dataset:data:write` and `source:data:write` from every role but `ops` and `external`; turning it off for external users withholds `source:data:write` from `external`. `Role:` still names the role, so a 403 for a permission that role normally holds is answered here. [backend]

- Missing or expired credentials exit 4 and name the server and selected organization, including whether the org came from `--org`, `QCTL_ORG`, or the current context. Agents should ask the user to run `qctl auth login` in their own terminal, then re-run the failed command; login can change the stored default organization.

- `auth sessions -o name` prints `session/<delegation ID>` for every session, named or not, and `auth sessions revoke` takes that line and revokes exactly that one session, where a name revokes every session that shares it.
- After a named or `--expired` revoke succeeds, `auth sessions revoke` also removes any locally stored credential whose `token_name` belongs to a delegation it revoked, including the other credential ordinary commands were not using. Under the plaintext-token opt-in this cleanup still reads the keyring, so a desktop may show its unlock prompt.
- `auth sessions --never-used` lists only sessions with at least one token, all tokens expired, and no recorded first use on any token. Expiry is the age cutoff: a fresh unused token and a token revoked before its future expiry are excluded. Sessions with no token rows are omitted with a count warning; a failed token lookup returns an error instead of an empty filtered result. This flag only filters the inventory and does not revoke anything.
- `auth sessions` includes `first_used_at` in JSON/YAML and offers it through `--columns first_used_at`, leaving the default table columns unchanged. It is the earliest recorded first use across the session's tokens, or null when no first use is recorded or token information is unavailable. The backend stamps `first_used_at` only while it is null, so the timestamp measures first use and says nothing about recent activity. [backend]
- `auth sessions` lists the server's active CLI sessions for the current user and organization and marks the one correlated with the locally stored `token_name` as current — but *active* means only that the delegation has not been revoked, since `list_my_delegations` filters on `revoked_at IS NULL` and a delegation carries no expiry column of its own, so a session whose token expired long ago stays in the list until something revokes it. `auth sessions revoke <name-or-id>` revokes every exact-name match, while a displayed delegation ID addresses exactly one session and is the way to reach a legacy unnamed one. It claims only what this run actually revoked: a session can end between the list that found it and the DELETE that targets it — deleted outright (404) or revoked from somewhere else (a 200 carrying `success:false`, which is not an error status) — and both are finished outcomes reported as `had already ended` with exit 0. The list never shows another user's session, because it is filtered by owner; a 403 means you do not own that delegation or lack `ORG_VIEW`, and it exits 4 like any other refusal. [backend]
- `auth sessions` reports a STATUS column, and it is a join qctl computes rather than a field the server returns: a delegation row carries `created_at` and `revoked_at` and no expiry column at all, so the command also reads `GET /orgs/{org}/users/me/api-tokens` — same `ORG_VIEW` permission, filtered to your own delegations in this organization — with `include_revoked` and `include_expired` both forced on, because that route defaults them to false and would otherwise return only live tokens, leaving a session whose token died last month indistinguishable from one that has no token row at all. `active` means at least one token under that delegation is unrevoked and not yet expired, and is the only value that means the session can still reach the organization; `expired` means it has tokens, none of them can authenticate, and at least one merely timed out — the ordinary state of accumulated clutter, since a CLI token lasts 24 hours by default while the delegation behind it never expires; `revoked` means every one of its tokens was revoked outright, which `DELETE /orgs/{org}/users/me/api-tokens/{id}` does without touching the delegation, so the row is a leftover somebody ended deliberately rather than one that lapsed; `unknown` means qctl could not tell. EXPIRES is the latest expiry among the tokens that make the session live when it is `active`, and among all of its tokens otherwise — so a `revoked` row can legitimately show a FUTURE expiry, because the token was killed before it lapsed, and STATUS rather than EXPIRES is what answers whether a session still works. [backend]
- What qctl does with a liveness lookup it could not make is its own decision, and the inventory and the bulk revoke deliberately make opposite ones. The list is the load-bearing half — it is what you need most when something is broken — so a failed api-tokens call leaves every row `unknown`, warns on stderr naming the failure, and still exits 0; that warning is also the only thing separating that `unknown` from a delegation no token row names, since a failed lookup makes EVERY row unknown at once. `auth sessions revoke --expired` refuses instead, surfacing the lookup's own error without issuing a single DELETE: on missing information every session looks equally dead, and the one live login on another machine would go with the rest. What it does revoke is exactly the `expired` and `revoked` rows — never an `unknown`, and never this machine's own session, because `current` is a `token_name` string match and two delegations sharing a name are therefore both current, so sweeping the dead one would delete the credential belonging to the live one. It reports how many sessions it left unclassified rather than implying everything dead is now gone, and finding nothing to revoke is exit 0, not an error. `--expired` together with a name or ID, and `revoke` with neither, are both exit 2 before any request is made.
- What `auth sessions revoke` does with the LOCAL credential is qctl's own decision, not the server's. Revoking your own session deletes its stored credential whether the delegation was still there to revoke or had already ended, and both outcomes say so — otherwise the already-ended path would log this machine out while printing only `nothing was revoked`. When the OS keyring and `~/.qctl/credentials.json` hold two different credentials (see `auth logout` below), only a credential whose `token_name` is among the sessions this revoke matched is deleted: the other one belongs to a session it did not touch, so it is kept and named, with `later commands will use it` when the next command reads it, and `auth login` named instead when it will not — the plaintext opt-in reads only the file, and a credential that has already expired cannot authenticate. With one credential stored, or both matched, nothing usable is left and `auth login` is named. Revoking only some other session touches nothing stored here, even when the other half holds that session's credential. A revoke that fails partway through several same-named delegations is the one case that keeps the credential: the count it revoked before the failure is reported, but which of them was this machine's is not knowable, and throwing away the only handle on a session that may still be live is the orphan this command exists to prevent — so it says the credential was kept, and that `auth logout --local` forgets it once `auth sessions` shows the session is gone.
- A second `auth login` for the same server and organization — and an ops `auth switch-org` that replaces a target-org credential — retires the session it replaces, because the exchange endpoint creates a brand-new delegation on every call and never reuses one, so without that the first session stays live on the server with no local handle to revoke it by. qctl stores the new credential first and cleans up afterwards, so a local write failure leaves the old credential usable instead of stranding both. Which token authenticates the cleanup depends on whether the old one still can: a live one revokes its own session, which is what reaches it even when the new login belongs to a different user, while one that is expired locally or rejected by the server is revoked by name with the NEW token — `revoke_my_delegation` asks only that the caller own the delegation, and the list it is matched against is filtered by owner, so that reaches your own stale session and can never touch anyone else's. That second case is the ordinary one rather than an edge: a CLI token lasts 24 hours by default (qctl sends no `expires_in_seconds`, so the backend's own default applies) while the delegation behind it never expires, so a daily re-login would otherwise add one more permanent line to `auth sessions` every day. [backend]
- When login or ops `switch-org` replaces a credential, three of qctl's own decisions are deliberate and none of them is a missed revoke: a live credential the write left in place is left alone — the fallback file's copy after a keyring store, or the keyring's after a keyring write that failed without a refusal and fell back to the file — because it still has a local handle there and revoking it would only break the commands that read it; a replaced credential whose `token_name` equals the new session's is left alone, because revoking by that name would end the login just made; and a still-live credential stored before qctl minted names matches no delegation at all, so it warns on stderr and points at `auth sessions`, where its delegation ID can revoke it (an unnamed credential that has already expired is silent — there is nothing left to act on). Any other cleanup failure leaves the login successful and names the old session plus the `auth sessions revoke` retry on stderr, as a single line: a name can match several delegations, so a cleanup that revoked one and was then refused says exactly that and nothing else — never a `Revoked the previous CLI session` on stdout beside a `could not revoke` for the same session on stderr. If the local STORE is what failed, qctl revokes the session the exchange had just minted, with that session's own token, before returning the error — otherwise a failed login would leave a live session nothing local can address, and every retry would leave one more.
- The OS keyring and `~/.qctl/credentials.json` can hold two different credentials for one server and organization (see `auth logout` below), and login or ops `switch-org` retires each one its write replaces, not only the one ordinary commands were reading: a keyring write overwrites the keyring's copy even when the file's newer copy is the one in use, and a keyring that refuses the write loses its own entry while the new token replaces the file's, so both go. Each is revoked with its own token, under the rules above, and the one ordinary commands were not reading is reported as `Revoked the other CLI session "<name>" for this organization, whose credential was stored in <location>.` (`the target organization` under `switch-org`). With the plaintext opt-in, flag or environment, only the file is written, so only the file's copy can be replaced; an older keyring entry stays, and the flag form warns about it as described below.
- `auth login` is browser-based OAuth (device flow); by default the credential goes into the OS keyring, falling back to a 0600 file automatically when no keyring is available, and also — with a warning on stderr, since that one is a downgrade rather than the documented default — when a keyring that is up and still answering reads of other entries refuses the write (qctl tells that case from an absent keyring by reading a key no login can have written, never by writing a probe entry of its own, so a keyring that refuses reads as well falls back silently); after that fallback write succeeds qctl attempts to remove any older keyring entry for the same server and organization so it cannot shadow the new token if its recorded creation time is later, and counts that removal done only when the entry is demonstrably gone — the delete succeeded, or a read-back says there is no such entry — so a read-back the keyring cannot answer counts as surviving, and login errors naming the entry and both locations rather than reporting success while that older credential could still win an ordinary read (that failure also puts the fallback file back the way it was, since login treats it as "not stored" and revokes the session it just minted — a new token left in the file would otherwise be served, already dead, to every command a keyring that cannot answer a read falls past); set `QCTL_ALLOW_PLAINTEXT_TOKENS=1` (or `--allow-plaintext-token-store` on `login`/`switch-org`) to skip the keyring on purpose instead of relying on the fallback — that opt-in covers storing and ordinary reads only: `auth logout` still reads an entry an earlier keyring login left, revokes its session with its own token, and attempts its removal, reporting the entry if it demonstrably survived; the flag form applies to that `login`/`switch-org` only; later commands consult both stores and use the credential with the later `created_at`, so an older keyring entry cannot shadow the newly stored file token. When the flag is used without that environment setting, login checks for an older readable keyring entry and warns with its exact key if found, pointing at `auth sessions` to inspect and revoke the older session; set `QCTL_ALLOW_PLAINTEXT_TOKENS=1` to make later credential reads use only the file.
- `auth logout` deletes only the credential for the current server **and** org — credentials for other orgs on the same server, or for other servers, are untouched. `--all` is the one exception, and only for other orgs on the **same** server: it deletes the copies of credentials the server has just revoked.
- `auth logout` revokes this CLI session on the server and then deletes the local copy: it calls `DELETE /orgs/{org}/users/me/delegations/{id}`, which the backend documents as revoking every CLI token from one device/session, because the route literally named `logout` refuses a bearer caller that asks to end a *single* session — HTTP 400, `A bearer credential cannot end a single session` — since a bearer credential names no cookie session to end; that route's whole-account form is what `--all` calls; older servers may refuse bearer callers even for `--all`. qctl finds its own session by the unique `token_name` it minted at login — the exchange returns neither `api_token_id` nor `delegation_id`, and the bearer token is AES-GCM ciphertext the client cannot decode, so that name is the only correlation key there is. A still-valid credential stored before qctl minted names, or `--local` on one, skips the revoke and leaves the token valid until its own expiry, which logout tells you on stderr; an already-expired credential is simply forgotten with or without `--local`, since expiry already ended the session. Three further cases skip the revoke *silently* — no `Revoked…` line, nothing on stderr — and delete the credential anyway: a `token_name` that matches no delegation, a 401 from either call, which means the server already refuses the token, and a 404 from the revoke, which means the delegation row is gone or belongs to another org. A 403 from either call is permanent — you do not own that delegation, or you lack `ORG_VIEW` — so qctl keeps the credential, says retrying will not help, and points at `--local`; note that an already-revoked delegation is NOT a 404 but a 200 with `success:false`, which counts as a finished logout. Any other failure keeps the credential so you can retry — an unreachable server, a 5xx, a malformed or empty body, a delegation id that is not a UUID. [backend]
- The OS keyring and `~/.qctl/credentials.json` can hold two different credentials for the same server and organization — a login with `--allow-plaintext-token-store` after an earlier keyring login leaves exactly that — and `auth logout` treats each as its own CLI session: it runs the revoke above once per credential, each with that credential's own token and `token_name`, printing `Revoked this CLI session on the server.` for the one ordinary commands would use and `Revoked the other CLI session "<name>" on the server, whose credential was found in <location>.` for the other. Under the plaintext opt-in the fallback file's credential is the one reported as this session whatever its age; without it, the newer one is, and a tie goes to the keyring. A credential whose revoke fails is kept in whichever half holds it while the other is deleted — or named with the by-hand remedy if that delete fails — so a plain retry of `auth logout` finds only the kept one; that run exits non-zero and never prints `Successfully logged out`. `--local`, an unnamed credential and an expired one are handled per credential exactly as above, so `--local` with two stored copies warns about both.
- `auth logout --all` is a different operation from the logout above, and the step to take after a password or MFA reset: it calls `POST /orgs/{org}/logout?all_sessions=true` with your bearer credential and ends **every** session and bearer credential you hold on that server — every browser session, every CLI login on every machine, every API token, in every organization — because the backend leaves a self-logout's revocation scope `global`, and qctl never sends `user_id`, which is the only thing that would narrow it to one org. It reports the server's own `delegations_revoked` and `api_tokens_revoked` counts and never a local guess; cookie sessions are deliberately not among them, since the backend revokes those in bulk through a per-user watermark and has no inventory to count. The call revokes the very token it is made with, and a 200 is still the success signal. On 401 or 403 qctl deletes the local copies anyway — they are worthless either way — and says on stderr that it could **not** confirm the revocation, pointing at the web app's "Sign out of all devices"; on an unreachable server, a 5xx, a 400, or a 200 carrying no `revocation` object, nothing is deleted, so you can retry. [backend]
- `--all` cannot be combined with `--local` (exit 2, before any request is made): one revokes on the server, the other exists precisely so that nothing is sent to it. It also needs a credential that still works — an expired one is refused up front with `token expired`, because it can no longer authenticate the revocation — so if that is where you are, log in again first and then run it.
- After a successful `--all`, qctl deletes the stored credential for every organization it can NAME on that server — the resolved one, every organization your config contexts cache for the same server, and every organization `~/.qctl/credentials.json` holds an entry for — then prints how many of them actually held one. It cannot do better than name them: go-keyring offers Get, Set and Delete and nothing that lists a service's entries, so a keyring credential for an organization no context and no fallback file mentions is one qctl cannot see to delete. If a copy survives the delete, it is named individually, and `--all` exits non-zero even though the server-side revocation line was already printed — because it happened.
- When `auth login` or the ops path of `auth switch-org` needs to write `~/.qctl/credentials.json`, an existing file that cannot be read or parsed blocks the write with exit 1; qctl names the file and leaves its bytes untouched instead of treating it as an empty credential store. Moving it aside lets qctl create a new file, but makes every `token_name` stored there across servers and organizations unavailable to qctl; after logging in, use `auth sessions` in each affected organization to inspect and revoke any older sessions by name or ID.
- `auth logout` now reports a credential the OS keyring refused to delete, and says which copy survived: when it can say the keyring holds no copy but `~/.qctl/credentials.json` could not be cleared — unreadable, unparseable, or not writable — it says exactly that and asks you to inspect that file, rather than claiming the whole logout failed, and it still exits non-zero, because a file it could not clear is exactly the case where it cannot prove no copy of the token is in it. A machine with no keyring at all (a container, CI, a headless server) is silent as before: there is nothing there to have failed, and so is a keyring that refuses the read-back, because qctl reports the entry only when it can still read it back after the failed delete — that read is the only way it can show a copy survived.
- If qctl is using the keyring — the plaintext opt-in above sends both the write and the read straight to the file, so there is no refusal to report — and it is up and still answering reads of other entries but refuses this one, `auth login` and `auth switch-org` warn on stderr that the token was written to `~/.qctl/credentials.json` (mode 0600) instead, and any command whose credential is nowhere to be found reports `the OS keyring refused to return the credential` rather than `not logged in` — do **not** run `auth login` on that message, since it overwrites the file and with it the `token_name` `auth logout` needs to revoke a session that may still be live.
- On a machine where qctl is using the keyring (the plaintext opt-in sends ordinary reads straight to the file, but `auth logout` still reads the keyring entry there — an entry an earlier keyring login left has its session revoked like any other stored credential — while a keyring that refuses counts as holding nothing, so there is no refusal to report; `nothing to do` is printed only once neither half holds a credential and the delete attempt comes back clean, and on a desktop each keyring access can still raise an unlock prompt) and it is up and still answering reads of other entries but refuses this one, and only when no fallback credential is stored either (if the fallback file holds it, logout uses it and proceeds normally), `auth logout` now exits non-zero with `the OS keyring refused to return the credential, and no fallback credential is stored` instead of reporting `nothing to do`, and it never attempts the keyring delete — `--local` does not bypass this, because the read happens before both the revoke and the delete, so if a keyring entry for this server and org is there, remove that one entry by hand — it is service `qctl`, entry `<server>|<org-id>`, and every other server and org is a separate entry under the same service, so removing the whole `qctl` service would delete all of them; that message also means `~/.qctl/credentials.json` holds no copy for this server and org.
