## USAGE

    qctl apply -f <file.yaml>   # kind: TableSchema
    qctl describe table-schema [table]
    qctl diff -f <file.yaml>   # kind: TableSchema
    qctl get table-schema [table]

## EXAMPLES

    # the default view: current fields, plus an ACTION column if a draft is pending
    qctl get table-schema orders

    # bare column names for scripting -- current and draft flattened together, unlabelled
    qctl get table-schema orders -o name

    # schema state, confirmation status and pending rule suggestions
    qctl describe table-schema orders

    # full structured detail for agents: per-field diffs and notable values
    qctl describe table-schema orders -v -o yaml

    # address the table by the flag pair; --table is always a name
    qctl get table-schema --table orders

    # the editable manifest: type, args, nullability and flags per column
    qctl get table-schema orders -o yaml

    # round-trip: read it, edit it, preview it, apply it -- diff exits 0 for no change, 1 when it prints the diff
    qctl get table-schema orders -o yaml > schema.yaml
    qctl diff -f schema.yaml
    qctl apply -f schema.yaml

## GOTCHAS

- `apply -f <file> -o name` prints `table/<table-id>`, including an unchanged result. Several applied documents print one reference per line in file order; prose goes to stderr. This identifies the table whose schema was updated, rather than a column or migration ID; use this reference with `--table-id` to read the schema.

- Integer fields in a YAML manifest reject fractional numbers during parsing (exit 2): `2.7` is refused instead of becoming `2`. Whole-valued YAML numbers such as `2.0` remain accepted.
- `describe table-schema` reports `Status: Processing` and exits 0 when the server identifies schema calculation as in progress. `-o json|yaml` returns `{dataset_id, state: processing, message}` instead of schema fields in that case; retry after profiling settles. Other schema lookup errors keep their normal exit codes.
- `describe table-schema`'s text header includes the pending rule-suggestion count and how many block the draft migration, using every page of pending suggestions and detail reads for update/delete proposals while a draft exists. A failed suggestion read warns on stderr and marks the section unavailable while the schema still prints. When a schema is available, `-o json|yaml` and `-vv` keep the schema response without suggestion reads; inspect proposal parameters with `qctl get rule-suggestions <table> --show-params` or `qctl describe rule-suggestion <id> --table <table>`.
- `describe table-schema` adds `Key step:` and `Key columns:` to its text header when the response carries them, and while a key step is set it prints a key candidates table after the header: one row per suggested key set with COLUMNS, DUPLICATE, IDENTICAL, BLANK and PROBLEM, where PROBLEM is DUPLICATE - IDENTICAL + BLANK, then the current key columns' counts when the server sent them. The heading gives the rows checked and whether they were the whole file; over a sample every count is a lower bound for the file. A null `key_step` prints the stored key columns alone, with no step and no table. `-o json|yaml` carry `key_step`, `key_columns` and `key_column_candidates`, leaving out a null `key_step` or `key_column_candidates` rather than printing `null`; `get table-schema` shows none of them, because the TableSchema manifest takes no keys.
- After a period recreate, `describe table-schema` text shows `Previous key columns:` and `Reuse previous keys:` when previous keys are present; omitted reuse metadata is shown as unknown. Counted previous keys print after the candidates and current-key counts, under the same sample or whole-file heading. Pending carried rules print in a separate table with suggestion ID, rule name, FITS and missing columns, even without a key step. Empty carried-rule lists add no section. `-o json|yaml` preserve `previous_key_columns`, `preselect_previous_key_columns`, `previous_key_columns_counts` within `key_column_candidates`, and `recreated_period_rules` as served.
- `previous_key_columns` names the replaced table's keys from the latest period recreate. `preselect_previous_key_columns` says whether the draft accepts that complete set as an explicit key choice; it does not choose keys automatically or promise zero problem rows. Previous-key counts can be present even when that set is not suggested or cannot be reused. Each `recreated_period_rules` entry describes a pending carried suggestion's column availability, without comparing column types. Applying the migration accepts fitting suggestions unless dismissed and dismisses misfits; explicitly accepting a misfit is refused. Dismissing suggestions can change the fits because their staged outputs are excluded from the server's recheck. [backend]
- `key_step` is `required` on a mirror or append table with no key columns stored, `optional` on one that has them, and null on any other loading process or once the keys are locked — which they are as soon as any migration of the table is current or applied, or a draft is confirmed, so a step shows only before the table's first migration is confirmed. At `required` the review's `apply_migration` must choose key columns or say there are none; at `optional` it may replace the stored key columns, and leaving them out keeps them unless one is no longer a live column of the draft or is a rule output, which is refused. [backend]
- the key candidates are counted over the first file profiled for the table and named by the draft's column names: at most 5 sets of one or two columns, ranked by PROBLEM ascending, then by fewer columns. A set is suggested only with no problem rows or, over at least 100 rows checked, at most 1% of them. Sets an `apply_migration` would refuse as key columns (a column the draft lacks, a deleted or rule-output column, a reserved name) and sets the key type rules exclude (a Decimal, Float, dollar or percent column, an integer named like an amount; alone, a date or an integer not named like an identifier) are dropped before the cap, so `none suggested` can mean every counted set was dropped. The current key columns' counts are matched by set equality and are absent when those columns were not counted; the whole table is absent when the key step is null, the table has no draft, or no file was counted. [backend]

- Before sending a changed `kind: TableSchema` manifest, `qctl apply -f` lists running ingestion jobs on stderr, marking dry-run carriers and giving `qctl describe ingestion-job <id>` for each; `--yes` skips the confirmation prompt but keeps this preview. The lookup is table-scoped and paginated, includes other users' jobs, and warns without refusing the write if unavailable. An unchanged manifest makes no job lookup.
- A confirmed draft can wait before applying: the migration scheduler reschedules while ingestion jobs for the table are running, including the ingestion carriers of rule-validation dry runs; dry runs do not hold the profiling job's active slot. Another running profiling job can also delay the migration. A `blocked` profiling job of the table instead moves the migrate profiling job to `error` ("The schema change was not applied: profiling job N is `blocked` in the `<step>` step."), and the backend re-offers it with a growing backoff while the `migration_ready_to_run` alert stays open, so resolve what blocks that job. Let the running jobs finish, then check `qctl describe table` and `qctl describe table-schema`; `--yes` does not bypass the scheduler's wait. [backend]
- An apply confirmation uses the current context's `organizationName` when its `organization` ID matches the selected org and the `organizations` cache has no name for it; a different uncached `--org` UUID still shows `Unknown`.
- `-o name` reads a server-cached fields endpoint that flattens the current **and** draft schemas into one list of bare names — a draft-added column does appear, a draft-only table returns nothing but draft fields, and nothing in the output says which are pending; use the default view (or `-o yaml`) when you need to tell them apart. It also never falls back to the details endpoint; `describe table-schema` has no `-o name` at all — it declares `table,json,yaml` and rejects `name` with exit 2. [backend]
- `-o json`/`-o yaml` emit a `kind: TableSchema` manifest that `qctl apply -f` accepts and `qctl diff -f` previews; verbosity no longer changes that output. The raw API response — per-field diffs, notable values, the incompatible-override list — moved to `qctl describe table-schema -v -o yaml`, which is the agent surface.
- each manifest field round-trips `display_decimals` when the schema defines it, including the meaningful value `0`; editing it participates in the same `diff -f` preview and complete-definition apply as type, args, nullability, indexing and display flags. `get table-schema -v` and `describe table-schema -v` show it in a DISPLAY_DECIMALS column, where `-` means unset.
- `display_decimals` must be a whole number from 0 to 16383 — anything else is a 422 (exit 2) — and it applies to every numeric type, `Integer` included; on a non-numeric column it is accepted and does nothing. Unset means 2 places for a money or percent column and, for a plain number, no display rounding of its own, and `display_decimals: null` is how a manifest asks for unset back — the one property-level null a block can state, where an omitted line keeps the live value; the preview reads `display_decimals: 0 → unset`, and a null on a column that is already unset is no change and sends nothing. Changing it, or flipping `is_dollar`/`is_percent`, only rebuilds the column's search index: the migration does not rescale stored values, so turning `is_percent` on over loaded rows makes a stored `12.5` show as `1250.00%`. [backend]
- `is_dollar` and `is_percent` both true is refused with exit 2 before anything is sent, `diff -f` included, whenever a block would send the pair — stated in the block, or kept from a live column carrying both, since the override carries every live flag the block leaves out — so set one of them to `false` in that block; an unedited block sends nothing and is not refused. Such a column would show as currency while its cleaner divides loaded values by 100 as a percent, and the backend refuses the pair as well (422, exit 2) — on current servers over the columns your request NAMES rather than every column the table's stored overrides name, so a legacy both-column no longer fails an apply that leaves it alone, and `is_deleted: true` on one now works, because the check skips a column whose merged definition is deleted. Inference no longer marks a column with both, but a column inferred that way earlier keeps them until the table is next inferred. The web UI makes the two mutually exclusive and saves a column carrying both as dollar-only. [backend]
- `trgm_indexed` is the backend's to set, not yours: it follows the column type — `true` for String, Text, Array, Json, Jsonb and every numeric type, absent for the rest — and so does `indexed` on Date, DateTime, UUID, SmallIntArray, IntArray, BigIntArray and UUIDArray, which are always indexed. A matching `trgm_indexed: true` is unchanged even when the details response omits that derived property. A block stating a value the backend would overwrite — `trgm_indexed: false` on a String, any `trgm_indexed` on a Date, `indexed: false` on a Date — is refused with exit 2 before anything is sent, `diff -f` included, because the backend would store its own value and the line would show as a change on every later diff. `get table-schema -o yaml` copies whichever index flags the details endpoint reports, so retyping can leave a derived flag that conflicts with the new type; for example, an unindexed String block carries `indexed: false`, which must be deleted if the block is retyped to Date. When a block retypes one of the always-indexed types and leaves `indexed` unstated, qctl does not copy the old `true` into the request, so the backend drops the old btree or gin method before deriving the target type's flags; an `indexed` line explicitly present in the block is still sent. An unedited block sends nothing and is not refused, and neither is a block that states `is_deleted`, which keeps the flags of the definition it hides: the inferred column's, or — for a column an earlier apply added, which inference does not produce — the migration model's own copy of it, carried on current servers and dropped outright on older ones. [backend]
- the API calls this a *migration* (`datasets/{id}/migration-details`); `migration` and `table-migration` are aliases of both `get table-schema` and `describe table-schema`.
- the ACTION column (`added`/`modified`/`removed`/`unchanged`) appears only when a draft schema change is pending — with no draft, the grid is just the applied schema. On current servers `removed` covers two cases: a column the draft DELETES, which stays in the schema flagged `deleted`, forced nullable, and comes back when a later apply clears the flag — that restore reads as `added` — and a column the draft no longer contains at all. Only the second shows its current definition; every other row, a deleted column included, shows the draft's. On older servers a pending delete read as `modified`, or as `unchanged` when the column was already nullable, except on a column an earlier apply had added: the draft dropped that one outright, so it read as `removed` with no draft definition and could not be restored. [backend]
- the table can be a positional argument (ID first, then name) or the `--table` / `--table-id` pair on this command and every other `selectorPositional` command, including `qctl get data` and `qctl describe table`. `--table` is always a name and is never parsed as an ID, which is what makes a table literally named `42` reachable; the positional form resolves as an ID first and cannot reach it. Four commands remain positional-only — `qctl get table`, `qctl download data`, `qctl undelete table` and `qctl share table` — so on those a table named `42` is only reachable as the table whose ID is 42.
- removing a column from the manifest does NOT drop it: a column absent from `spec.fields` is a no-op. `is_deleted: true` is what stops a column being ingested, and it also adds the column to `settings_model.ignore_column_names` — so a later `qctl apply -f` of a Table manifest carrying a stale `ignore_column_names` silently un-ignores it. [backend]
- that no-op rule applies to individual omitted columns, not to an entirely empty edit: `spec.fields` must name at least one column, and a missing or empty block is rejected client-side with exit 2 because it describes no change at all.
- editing a column pins its whole definition: the override qctl sends is the live definition overlaid with what your block states, so properties that merely happened to match the inferred value become explicit overrides and later re-inference will not move them. `<column>: null` un-pins the column, putting it back to inferred and removing it from `ignore_column_names` — but not on a deleted column: there qctl refuses the null with exit 2 before anything is sent, `diff -f` included, because the backend refuses it with a 409 until the column is restored, so apply a block whose only change is `is_deleted: false` first and the null in a second apply. [backend]
- `is_deleted` is a mode switch, not a property: the backend applies it on its own, discards every other property in the same block, and forces `is_nullable: true` whichever value it takes — so qctl rejects a block that sets it, `false` included, alongside another change with exit 2. `qctl get table-schema -o yaml` emits `is_deleted: true` on a deleted column and omits it on every other. To un-delete a column and then change it, apply `is_deleted: false` alone in its block first and make the change in a second apply: a block that changes a deleted column without stating `is_deleted` is refused with exit 2 before anything is sent, `diff -f` included, because the backend refuses the whole schema change with a 409 until the column is restored and writes none of it, the other columns' changes included. A delete still waiting in a draft counts, since qctl and the backend both let a draft's definition of a column win over the current one. [backend]
- a column name the schema does not have is an ADDITION, not an error: the block is sent exactly as stated, `schema_overrides_merge` writes it into the migration model wholesale, and the migration adds the column with `ALTER TABLE ADD COLUMN`, leaving it NULL until data or a rule fills it. A new column is always nullable — the migration backfills nothing, so it emits NOT NULL only for a column carrying a `default`, which this manifest has no key for; qctl exits 2 on a stated `is_nullable: false` rather than send what the server refuses with a 422, and `is_deleted` (either value) and `<column>: null` exit 2 on such a name too, since there is nothing to delete or clear. The server checks only the name's form: it refuses with a 422 a name that is reserved, starts with `__`, runs past 63 characters, is not already in the table's normalized form, or collides in any casing with a column the table has or ignores — so a well-formed misspelling passes, and the `add column` lines `qctl diff -f` and the apply prompt print are the only thing between it and a new column. [backend]
- renaming a column is still impossible: change a name in the file and you ADD a column under the new name while the old one is left untouched, and pairing the new name with `is_deleted: true` on the old one is two columns rather than a rename — no data moves between them. The route has no rename parameter at all, and the web UI's rename feature is commented out with "Current API does not support field renaming". [backend]
- `describe table-schema -o json|yaml` and `-vv` print each column definition's `generated_by`: the server's ownership stamp — `type: rule_output` plus the `dataset_rule_id`, `rule_revision_id` and `rule_field_name` — on a column a rule produces, and `null` on any other; a 2.118.0 server sends no stamp on the schema route, so against one every column reads `null`. The `get table-schema -v` and `describe table-schema -v` grids mark a stamped column `rule_output` in FLAGS without its owner ID; the `get table-schema -o yaml|json` manifest omits the stamp; `qctl describe table` marks the producing rule `(produces)`, and `qctl describe table-rule <rule>` lists a rule's columns under `spec.produced_fields`. The schema route checks no ownership: a TableSchema apply may set `is_deleted` on a produced column or change its type or size. A column left deleted, or retyped to a type the rule's declaration does not accept, fails the rule's enable check with a 409 (exit 2): enabling the rule is refused, applying the migration skips the automatic enable of a rule waiting in `pending_validation` and leaves it there, and on an enabled rule a change to its produced fields or column mapping is refused. A size change alone passes that check: it compares the rule's declared `precision`, `scale` and `max_length` keys, and a schema apply changes only `args`. No apply removes a produced column from the schema, `<column>: null` included, because the backend carries every rule-produced column over each time it rebuilds the model from an edit. [backend]
- `apply -f` and `diff -f` warn, and never refuse, when an edit changes the `type` or `args` of a live column the server stamps as a rule's output, or sets `is_deleted: true` on one: a `Warning:` block on stdout, or on stderr when `apply -f` runs with `-o json|yaml|name`, names each such column, what the edit changes and the producing rule, and restates the enable-check consequences above. Naming the rule costs one extra request per producing rule, made only when such a column is edited; a rule that request cannot read is shown by ID alone. `apply -f` prints the block before its confirmation prompt, so `--yes` prints it too, and still sends the change; `diff -f` prints it in the preview and keeps its exit code. The stamp comes from the schema route, so against a 2.118.0 server, which sends none, nothing warns. An edit of a produced column that is already deleted is refused with exit 2 before any warning, like an edit of any other deleted column. [backend]
- `is_deleted: true` on a column a table rule's row filter reads is accepted by the schema route. When the migration applies, the stale-column retirement pass deletes enabled builtin rules, including CAF rules, whose filters read a missing or deleted column; every patch to a deleted rule is refused with 409 (exit 2). The pass also dismisses pending suggestions whose filters read such columns. It leaves custom rules and rules in other states alone. Later staged updates/deletes/upgrades can change a rule's filter or state, and produced-field activation can enable a `pending_validation` owner after this pass even when its filter reads the deleted column. A rule left enabled with a filter that no longer compiles raises a `validation_problem` blocker on every row it meets. [backend]
- `apply -f` and `diff -f` warn before an explicit deletion or type change of a column a live table rule's row filter reads. Deletion warnings describe the stale-column retirement pass and qualify later staged changes and produced-field activation; type warnings say the filter may stop compiling or its predicate inputs may change. These are warnings, so the write and exit code are unchanged. They precede apply's confirmation, including under `--yes`; apply sends them to stderr under `-o json|yaml|name`, and diff prints them on stdout. One complete paginated rule list serves deletion and type checks, skipping deleted rules; only enabled readers of deleted columns need detail reads to distinguish builtin from custom. A failed list warns and continues. The filter/mapping checks make no rule lookup without an explicit deletion or type change; `field: null` resets have no per-property diff and are not checked for type changes. [backend]
- Changing a filter column's type can make an operator or literal invalid, or change the values a Starlark predicate receives. The stale-column retirement pass does not retire a rule for a type change. After the migration, run `qctl table-rule test-filter <rule> --table-id <id>` to check the saved filter against the applied schema; it exits 2 with a 409 if the filter no longer compiles. A successful count tests the current schema, so running it before migration does not validate the proposed types. [backend]
- When a migration applies, an `enabled` builtin rule mapping a column the applied schema lacks or marks deleted is retired (`deleted`), and a patch cannot restore it (409, exit 2). A CAF rule whose affected generic slots are all in its revision's `optional_columns` instead loses those mappings and stays enabled, unless another required mapping or its row filter reads a stale column; an optional input on a non-CAF builtin does not get that exception. This pass leaves custom rules and non-enabled rules' mappings and states alone; a custom rule's runtime behavior depends on its code. Pending suggestions mapping stale input columns are dismissed, except a non-candidate CAF suggestion with only optional stale slots and no stale row-filter column drops those slots instead; revalidation candidates are dismissed. [backend]
- `apply -f` and `diff -f` also warn before deleting a column a table rule maps, naming each affected non-deleted rule, its state and mapped columns in a separate block. Enabled rules get retirement, CAF unbinding or custom-rule guidance scoped to the stale-column retirement pass; later staged changes or produced-field activation may change the final state. Non-enabled rules are identified without a detail read. This warning shares the paginated rule list and enabled-rule detail reads with the row-filter deletion warning, then reads each distinct affected CAF revision at most once for `optional_columns`, unless the row filter already retires the rule. A failed detail or revision read gives conditional outcomes; a failed list gives one warning for all rule checks. The warnings precede apply's confirmation, including under `--yes`, and go to stderr under `-o json|yaml|name`; diff keeps them on stdout. They do not refuse the write or change either command's exit code. [backend]
- writing a schema needs the `MIGRATION_EXECUTE` permission, held by the ops, admin and agent roles only; `member`, `editor` and `read_only` can read a schema and get a 403 (exit 4) trying to change one; `external` holds neither permission and gets a 403 reading it too. [backend]
- a successful apply that changes the model kills every in-flight training job for the table, creates a training job at the migrate step, and raises a migration alert — which is why `apply -f` confirms unless `--yes` is given. An existing draft spares you none of the three: the backend looks for the *current* migration first and only falls back to the draft when there is none, so all three run on any table that has ever been applied (`current_only` and `draft_with_current` alike) and are skipped only on a `draft_only` table, where the existing draft is reused. A `frozen` table skips all three for a different reason and much earlier: the whole PATCH is refused `409 ERR_MIGRATION_CONFLICT` before any of them, so no draft is cloned, no training job is killed and no alert is raised — `qctl apply -f` on a frozen table changes nothing at all. Which alert you get follows the table's `migration_policy`: the `ask_user` default opens `needs_review_migration` — except for an additive-only patch on a table with no draft, which applies itself and raises `migration_ready_to_run` instead. A table already holding `apply_asap`, which a client cannot set, takes `migration_ready_to_run` on every change, additive or not. [backend]
- `apply -f` cannot know which of those you get before it writes, so it states all of them in the confirmation prompt and reports the one that happened afterwards: `Waiting for review` plus the `qctl alert resolve <id> --action apply_migration` line — with `--yes` appended when stdin is not a terminal, because that action prompts — when the patch opened a `needs_review_migration` alert, `Applied with no review step` when the backend confirmed the change and queued its migrate job, and `No review step and no migrate job` when it only went into a draft that was already there. The frontend route the API returns for the review is not printed — a CLI caller cannot follow it, so only the alert id inside it survives. [backend]
- `qctl diff -f` previews ONE document. `apply -f` applies every `---`-separated document in a file, so concatenating several tables' manifests works for apply — but diff rejects such a file with exit 2 instead of previewing the first document and staying silent about the rest. Preview each table in its own file.
- an incompatible type change is recorded, not refused: it lands on the migration's `incompatible_overrides` list, which `apply` prints and `qctl describe table-schema -v` renders. [backend]
- `apply -f` sends both concurrency tokens from the read it makes itself just before the write, never from the manifest's `status` block, which apply ignores: `draft_version_id` only while a draft exists, and `settings_version_id` always — the backend made that one optional, so qctl is opting in, and an unrelated edit to the table's config landing between that read and the write is enough to make the schema write a 409 (exit 2). Opting out would not make the write safe: the settings row is version-counted in the database, so a lost update is refused either way, as a 409 `ERR_DB_CONCURRENCY_CONFLICT`, which `apply -f` answers with the re-read named below. The code does not single out a stale token: on current servers a settings- or draft-version mismatch answers `ERR_MIGRATION_CONFLICT` (an older server sends that mismatch with no code at all), the same code the route answers for an edit or null reset of a deleted column, for a `frozen` `migration_policy`, for a confirmed schema change still waiting to be applied, for one being applied right now, and for one an earlier apply left stranded. Only the backend's English sentence separates the seven, so `apply -f` prints guidance that covers all of them: re-read with `qctl get table-schema <t> -o yaml`; restore a deleted column with a block whose only change is `is_deleted: false` and make the change in a second apply; and check `qctl get table-config` for the policy and `qctl get alerts`/`qctl describe table-schema` for the pending change. qctl refuses an edit or null reset of a column its own read already shows deleted with exit 2 before sending anything. [backend]
- `is_deleted: true` on a column a linked table built on this table still reads — as an output column, a matching key or a natural key, in an enabled or in-review revision or its newest draft — is refused with a 409 `ERR_FIELD_IN_USE_BY_COMPOSITE` (exit 2) before anything is written, and re-reading the schema cannot clear it. `apply -f` lists each linked table the refusal names, with its table id, the revision, that revision's state and how it reads the column: remove the column from those linked tables' manifests, apply them, and delete the column once no such revision reads it — a natural key cannot be changed by `qctl apply` at all. A column that is already deleted is not checked, and neither is an un-delete. [backend]
- a column inferred as `Array` whose notable values look like timestamps (`Jan 5, 2024 10:30`) means no datetime format matched, so its comma was read as an array delimiter (`,` `|` `>` `;` by default). Fix it in the table manifest: append the strptime format to the exported `spec.settings_model.datetime_formats` (the key replaces the whole list) or set `datetime_formats_per_column: {<column>: [<format>]}`, then `qctl apply -f`; dates without a time go in `date_formats`. [backend]

- A `DateTime` input without a timezone is not a promise that its clock time will be interpreted as UTC. Supply an explicit `Z` or numeric offset when the instant matters. Clean `DateTime` columns store instants; their returned offset follows the database session's timezone; the web grid can display that instant in the viewer's local timezone. [backend]
- for a caller who sees the table's PII masked — no `pii:view` and no active PII access grant on the table — the `notable_values` of each PII column in `describe table-schema -v -o json|yaml` (and `-vv`) are masked: each value is `•••••`, or `•••••` and its last 4 characters when it has 9 or more, with its count kept, and the top-level `masked_fields` names those columns. The text view prints no notable values. [backend]
- `apply -f TableSchema` sends its schema PATCH under the table's change review policy (operation `migration_patch`, key `schema`); a refusal is a 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4) whose `Hint:` names the operation and points at `qctl get change-review-policy --table <table>`. The key cannot be proposed, so `CHANGE_PROPOSAL_REQUIRED` never answers it. `diff -f` sends no PATCH and is not checked, so it can preview a change that `apply -f` is then refused. [backend]
