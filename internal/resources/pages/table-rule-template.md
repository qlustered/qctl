## USAGE

    qctl apply -f <file.yaml>   # kind: TableRuleTemplate
    qctl diff -f <file.yaml>   # kind: TableRuleTemplate

## EXAMPLES

    # preview a rule template on table 42: the plan, then what each skipped or unmapped entry needs
    qctl diff -f monthly-orders.yaml --table-id 42

    # insert the column_mapping keys an unmapped entry needs into the file, with empty values to fill in
    qctl diff -f monthly-orders.yaml --table orders --write-mappings

    # the stored preview as the server sent it, for a script (the plan goes to stderr)
    qctl diff -f monthly-orders.yaml --table-id 42 -o json

    # apply it to table 42 without a prompt, waiting for the new rules' validation
    qctl apply -f monthly-orders.yaml --table-id 42 --yes --wait

    # apply with this table's own decisions for conflicts the template does not settle
    qctl apply -f monthly-orders.yaml --table-id 42 --resolutions resolutions.yaml --yes

    # read a template's rule merge back by the id diff or apply printed
    qctl describe rule-merge 7 --table-id 42

## GOTCHAS

- A `TableRuleTemplate` is `apiVersion: qluster.ai/v1`, `kind: TableRuleTemplate`, `metadata.name` and `spec.rules`, a list of entries. Each entry needs `rule` (the rule family's slug) and `release`, and may set `instance_name`, `severity`, `params` (display units), `row_filter` (shaped like a `TableRule`'s `spec.row_filter`), `column_mapping` (`{rule_field: table_column}`, partial) and `produced_fields` (each `{rule_field_name, dataset_field_name}`). The file names no table and no dataset id: `diff -f` and `apply -f` take the table from `--table` or `--table-id`, one of them required, so one file serves every table of a report.
- qctl checks the file before any request and exits 2 on: an unknown key, a missing `metadata.name`, `rule` or `release`, an empty `spec.rules`, a blank `instance_name`, a `severity` outside the enum, params holding masked text, a malformed `row_filter`, an empty `column_mapping` value, a produced field without `rule_field_name`, a rule listed twice without an `instance_name` on every one of its entries, and two entries with the same key. An entry's key is its `instance_name`, else its `rule`.
- An optional key PRESENT in an entry is managed: the plan sets it on the table rule and compares it there on every later run. A key left out is never compared or changed, so a matched rule keeps its own severity, params and filter, and a new rule gets the release's default severity, no params and no filter. `row_filter: null` is present, and removes the filter; qctl treats any other key written as null as left out. `column_mapping` is managed field by field: only the fields it names, the rest bind as below. [backend]
- `rule` must be the slug of a rule family of your organization that is not built in, and `release` one of its releases; anything else refuses the whole preview with 422 (exit 2) naming the rule or release it could not find. A release that exists but is `draft`, `in_review` or `disabled` is not refused: the entry plans `skipped` (below). [backend]
- An entry pairs with a table rule by LINEAGE first: the newest `applied` or `partially_applied` merge of a template with the same `metadata.name` into this table that created, replaced or kept a rule for the same entry key, followed through later upgrades. Renaming `metadata.name`, or changing an entry's key (adding, changing or removing its `instance_name`), loses that lineage; an entry whose new `instance_name` names no table rule then plans `created`, a second rule beside the old one, which shows as not in the template. [backend]
- Without lineage, an entry with an `instance_name` pairs with the live table rule of that name (one of another rule family is a `family_mismatch` conflict), and an entry without one pairs with the only live rule of its family (several make an `ambiguous_match` conflict listing them). A rule paired by an earlier entry is not offered again. With no pair the entry plans `created`, or `skipped` (`suggestion_pending`) while a pending create suggestion of the family, of that instance name when one is set, would create it. [backend]
- With lineage the plan is three-way against the entry and configuration the earlier merge recorded: entry unchanged → `kept`, with reason `edited_on_table` when the table rule's managed keys changed since (a template never reverts a table edit); entry changed and table rule not → `replaced`; both → conflict `changed_both`; the rule since deleted → `skipped` (`deleted_on_table`), or a conflict when the entry changed. Without lineage the paired rule is adopted: `kept` when its release and managed keys already match the entry, else conflict `adopted_differs`. [backend]
- Lineage is recorded only by an APPLIED template merge, which records it for its `kept` items too, and the preview does not say whether a `kept` rule has lineage or was only adopted. So when nothing is created, replaced or a conflict and a `kept` entry without a reason pairs with a table rule, `apply -f` still applies the preview after "Nothing to do", without asking: the merge settles `applied` inside the call and creates, replaces and changes no rule, and recording lineage again for a rule not edited on the table changes no later plan. It skips that apply, with a note, while a `kept` entry has reason `edited_on_table`: applying would record the table's edit as that entry's base, and its next entry change would plan `replaced` and undo the edit. An apply blocker on the preview, or the server refusing the apply (403 `CHANGE_REVIEW_POLICY_DENIED`; 409 for a locked period, another applying merge or a moved plan), is a note too, and the exit stays 0. Until lineage is recorded, a change to an adopted entry, a release bump included, plans conflict `adopted_differs` rather than `replaced`: resolve it with `take_source` in `--resolutions`. [backend]
- `keep_target` on an item paired with a table rule — a `replaced` item, or a conflict — is remembered: the applied merge records that rule as `kept` against the declined entry, so later runs plan the entry `kept` (`edited_on_table`) and never offer the change again until the entry changes. Declining a `created` item records nothing; it is offered again. [backend]
- An entry that would create or replace a rule is `skipped` when its release is `draft` (`not_submitted`), `in_review` (`in_review`) or `disabled` (`release_disabled`), or when the table's rule review policy does not let the release onto this table (`needs_table_review`). It is also `skipped` while the paired table rule waits for validation (`waiting_validation`) or its upgrade does (`upgrade_in_progress`). A skipped entry never blocks the others. [backend]
- After the plan, NEXT STEPS prints one line per skipped entry with the command that moves it on: `qctl review request <rule> --release <release>` for a draft (or `qctl enable rule` where no review is required), `qctl get rule-reviews --rule <rule> --release <release>` while a review is open, the same review request with `--table-id` when the table's own policy asks for it, `qctl suggestion accept <uuid> --table-id <id>` for a pending suggestion, and, for a `waiting_validation` or `upgrade_in_progress` entry whose rule passed validation and waits only for its draft migration, `qctl alert resolve <id> --action apply_migration` naming the migration's `needs_review_migration` alert (or the `qctl get alerts` lookup when none is found). qctl never runs them; approving a review takes a role that may approve, which the agent role is not.
- Each field binding shows its source: `override` (the entry's `column_mapping`), `live` (a kept or skipped rule's current mapping), `inherited` (on a replacement, the column the paired table rule used, while the table still has it), or, for a field none of those binds, the one column of a type the field accepts that carries its standard field (`concept`), has the field's name as its original header (`original_name`) or has the name the table's normalizer makes of it (`normalized`). So a mapping chosen once survives every release bump. [backend]
- A required field nothing binds makes the entry a conflict `unmapped`. diff exits 2 and prints COLUMN MAPPINGS TO ADD: the `column_mapping` lines to add to that entry, each followed by its ranked candidate columns as a comment; for a field the release enriches, the comment also offers dropping the key and listing the field under `produced_fields`, which adds it as a new column. `--write-mappings` inserts those lines into the file, keeping its comments and layout, with EMPTY values; the file is refused (exit 2) until each is set to a column, so qctl never writes a guess. Fill them in and commit the file once: the next diff plans the entry normally, and every later table of the report with the same columns needs nothing.
- An unmapped entry whose fix is not a missing key — a `column_mapping` naming a column the table lacks, or a produced field with no `dataset_field_name` on a table with no field name normalizer — gets no lines; COLUMN MAPPINGS TO ADD lists its note under "Fix these entries by hand". `--write-mappings` writes only a block-style YAML file holding one document: stdin and a JSON or flow-style file are refused (exit 2) before the preview, and a flow-style entry or a second document only when there is a key to add, after it. With nothing unmapped it leaves the file alone.
- Every `diff -f` and `apply -f` run stores a NEW rule merge in state `previewed`, which `qctl describe rule-merge <id> --table-id <id>` reads back: it changes nothing on the table but persists that record, and nothing cleans it up. It needs both `dataset:rule:edit` and `rule:instantiate`, which the agent role has, plus access to the table (403, exit 4). The preview first settles the table's applying template merges. [backend]
- `diff -f` exits 0 when nothing would be created, replaced or decided (stdout stays empty, and "Nothing to do" with the skipped entries' next steps goes to stderr), 1 when a rule would be created or replaced, and 2 while an entry is a conflict; on exit 0 `apply -f` may still apply the preview to record lineage (above). Apply blockers do not change the exit code. Under `-o json` or `yaml` stdout is the stored merge as the server sent it and every other line goes to stderr; any other kind refuses `-o json|yaml`, `--table`, `--table-id` and `--write-mappings` with exit 2.
- `apply -f` previews afresh, then: nothing created, replaced or a conflict, or `--resolutions` declining (`keep_target`) every item that is with none of them paired with a table rule → "Nothing to do", exit 0, with no apply request but the lineage-only one above; a conflict with no resolution, or an apply blocker → exit 2 with nothing applied, after the lines to add or a fill-in resolution document; otherwise it asks, on stderr. A `draft_migration` blocker counts only while an item the apply creates, after `--resolutions`, has produced fields. `--yes` skips the question and is required when stdin is not a terminal; it, a `keep_both` entry and an entry whose `rule:` is no template key are checked before the preview is stored. Declining the question applies nothing and exits 0. The template must be the only document in its file (exit 2).
- `--resolutions` takes a `RuleMergeResolution` whose entries are keyed by TEMPLATE KEY: `rule:` is the entry's `instance_name`, else its `rule`. A template conflict never takes `keep_both`; `unmapped`, `invalid_params` and `invalid_row_filter` take only `edit_source` (with the fix) or `keep_target`; `produced_column_collision` and `family_mismatch` take only `keep_target`; `keep_target` on a `created` or `replaced` item declines it. qctl checks each entry before the prompt (exit 2), as the server would with 400. Use it for a table whose columns really differ from the report's; put mappings every table shares in the template. [backend]
- The apply plans the template again and refuses with 409 (exit 2) when the plan moved since the preview — "The table's rules changed since the preview; preview the rule template again." — and qctl says to run the same command again. A table takes one applying rule merge at a time, template or table-to-table: another one applying, a draft migration while an entry would create a rule with produced fields, or a locked period is an apply blocker on the preview, and the server refuses the apply with 409. [backend]
- An upgrade is a replacement: a NEW table rule with a new id on the new release, keeping the instance name. Until the old rule retires — at once when the new rule is not `pending_validation`, else when it is enabled — the new one carries a suffix such as `NAME (2)`; on retirement it takes `NAME` and the old rule becomes `NAME [<its release>]`. Replacing a disabled rule creates a disabled one. When the old rule retires the server reprocesses its quarantined rows itself: the preview's Effects count them, and apply repeats them as a warning before the prompt. [backend]
- A new rule is created `pending_validation` when the table has an active data source or the rule has produced fields, and `enabled` at once otherwise; produced columns new to the table come through a draft migration, which Effects announce. A produced column another entry also produces, or one the table already has from elsewhere, makes a `produced_column_collision` conflict. Validation, waiting notes and settling are as for any rule merge (`qctl explain rule-merge`), except that a template merge with no rule left pending is settled inside the apply call, so its 202 can already read `applied`. [backend]
- `--wait` exits 0 when the merge ends `applied`, or when all it still waits on is the review of a draft migration: it then names the `needs_review_migration` alert and stops, leaving the merge applying. `partially_applied` or `failed` exits 1 (without `--wait` too, when the apply already settled it), and running out of `--wait-timeout` exits 124. The SUMMARY lists each entry's table rule and state, the draft migrations with their alerts, and FOLLOW-UPS such as `qctl alert resolve <id> --action apply_migration`, which apply never runs. Under `-o json|yaml` stdout is the last merge read and `-o name` prints `rule-merge/<id>`.
- Table rules the template does not name, built-in rules included, are in the merge as `skipped` items with reason `not_in_template`; nothing the template applies touches them. [backend]
- The plan lists the table rules the template does not name after its items, leaving out built-in rules: qctl reads each one's rule revision to tell, and lists a rule whose revision it cannot read. `-o json|yaml` and `qctl describe rule-merge` keep them all.
- The apply, never the preview, is gated by the table's change review policy (operation `rule_merge_apply`, key `rules`): a refusal is 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4), and no change proposal can carry the apply, so someone whose role the policy lists must run it (`qctl get change-review-policy --table-id <id>`). [backend]
- Applying a template records no MGA approval of a table series' rules and implies none. Once a rule it created or replaced is enabled, it changes a series table's enabled rules like any manual rule change, and when the series' rule configuration then no longer matches its latest approval, the series' broker report mail stops until `qctl table-series approve-rules` approves it. [backend]
