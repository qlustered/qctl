## USAGE

    qctl apply -f <file.yaml>   # kind: CloudSource
    qctl apply cloud-source -f <file.yaml>
    qctl copy cloud-source <id>
    qctl delete cloud-source <id>
    qctl describe cloud-source <id>
    qctl disable cloud-source <id>
    qctl disable email-intake <cloud-source-id>
    qctl email-intake rotate <cloud-source-id>
    qctl enable cloud-source <id>
    qctl enable email-intake <cloud-source-id>
    qctl get cloud-source <id>
    qctl get cloud-sources
    qctl run sensor-job <cloud-source-id>
    qctl undelete cloud-source <id>

## EXAMPLES

    # every cloud source in the org
    qctl get cloud-sources

    # only the ones feeding one table
    qctl get cloud-sources --table-id 42

    # the same filter by table name (--table is a name, --table-id an ID)
    qctl get cloud-sources --table orders

    # which sources are table-series sources, and how each routes a file to its period
    qctl get cloud-sources --columns id,name,dataset_name,table_series_id,routing_mode

    # what table_series_id takes, and that only a create sets it
    qctl explain cloud-source.table_series_id

    # one cloud source at a glance, including its quarantine breakdown, or a series source's period delta cursors, expected periods and broker due date
    qctl describe cloud-source 42

    # the same summary as an object, including period_delta_cursors for a series source
    qctl describe cloud-source 42 -o json

    # its manifest for apply -f, secrets left out; add credentials to create an active sftp or dropbox source
    qctl get cloud-source 42 -o yaml > cloud-source-s3.yaml

    # create or update a cloud source from a manifest
    qctl apply cloud-source -f cloud-source-s3.yaml

    # the same manifest through the generic dispatcher
    qctl apply -f cloud-source-s3.yaml

    # save a new source before its secrets are at hand: spec.state: draft, then follow the Next: line
    qctl apply -f cloud-source-draft.yaml

    # update with no change list and no question, as a script must
    qctl apply -f cloud-source-s3.yaml --yes

    # turn a cloud source back on (a composite source is refused)
    qctl enable cloud-source 42

    # turn one off: polling stops, and uploads and dry runs start failing
    qctl disable cloud-source 42

    # check for new files right now instead of waiting for the schedule
    qctl run sensor-job 42

    # a portal series source's email intake: on or off, its address, and whether issues reports go out on their own
    qctl describe cloud-source 42

    # turn its email intake on; senders who have not had the email welcome are scheduled one if the source is active
    qctl enable email-intake 42

    # also send each loaded file's issues report automatically (=false stops that; leaving the flag out keeps the setting, except on the first enable)
    qctl enable email-intake 42 --auto-send-issues-report=true

    # turn it off; the address is kept for the next enable
    qctl disable email-intake 42

    # replace the address after confirming; mail to the old one is dropped from then on
    qctl email-intake rotate 42

    # the same without emailing the senders the new address, and without the question
    qctl email-intake rotate cloud-source/42 --no-notify-senders --yes

    # who may send files to the intake (see qctl explain email-sender)
    qctl get email-senders --cloud-source-id 42

    # copy into an existing table, changing the files selected
    qctl copy cloud-source 42 --to-table orders_eu --set s3-prefix=eu/ --state draft --yes

    # copy an active source; secrets.yaml resupplies its secret, e.g. s3_secret_key: ${S3_SECRET_KEY}
    qctl copy cloud-source 42 --set s3-prefix=eu/ --secrets-file secrets.yaml --yes

    # copy into a table series: --to-table names one of its tables, and the copy must read other files
    qctl copy cloud-source 42 --to-table orders_2026_10 --set table-series-id=6f1c2b4e-0d3a-4c5b-9e8f-7a6b5c4d3e2f --set routing-mode=latest_unlocked --set s3-prefix=monthly/ --state draft --yes

    # remove one -- soft delete; recovery depends on server support
    qctl delete cloud-source 42

    # find a deleted cloud source
    qctl get cloud-sources --state deleted

    # attempt recovery (current servers refuse with 404; older servers may accept)
    qctl undelete cloud-source 42

## GOTCHAS

- `apply -f <file> -o name` prints `cloud-source/<id>`, including an unchanged result. Several applied documents print one reference per line in file order; prose goes to stderr.

- Integer fields in a YAML manifest reject fractional numbers during parsing (exit 2): `2.7` is refused instead of becoming `2`. Whole-valued YAML numbers such as `2.0` remain accepted.
- `-v=7` and `-v=8` redact credential fields and `simple_url` in HTTP body logs and query parameters, including nested `copy table --data-sources-file` entries. `-v=9` prints full request credentials and URLs.
- `copy cloud-source <id>` accepts an ID only and defaults to the original's table and state, with the name suggested by the copy template; `--to-table` is an exact name and `--to-table-id` is an ID. It refuses deleted, `qluster_ui` and composite sources, and an active original without `--set` unless it is a `simple_url` source, whose URL is not inherited. Repeatable `--set key=value` accepts non-credential source fields, with hyphens or underscores in the key; target, name and state have separate flags, and the source type stays fixed. `--yes` is required without an interactive terminal; `--dry-run` sends no POST and prints one document with the credential-redacted copy `template` and the `request` with every credential value masked under `-o json|yaml`, while `--dry-run -o name` and `--dry-run --yes` are bad usage (exit 2).
- `copy cloud-source --secrets-file <path|->` supplies the copy's credentials and URL as one YAML mapping keyed by field name; an unknown key exits 2, named by its line unless it is a valid key spelled with hyphens, and lists the valid ones, and other fields go through `--set`. A value of exactly `${VAR}` is read from the environment; an unset, empty or non-UTF-8 variable, an empty value, one containing the mask character `•`, and an unquoted value YAML reads as an anchor no alias uses or a tag other than `!!str` (a leading `&` or `!`) exit 2, and no error shows a value. The copy keeps the source's `s3_access_key` unless the file names one. An active or disabled copy that lacks a field the template lists in `secrets_to_resupply` exits 2 after the plan and before the prompt or the dry-run document; `--state draft` saves it without them.
- `copy cloud-source` prints its plan before confirmation, on stdout for table output or stderr under `-o json|yaml|name`. It shows the source, target table, new name and state, each `--set` field's old and new values, the credentials the file supplies, whether `s3_access_key` is kept or replaced, and the secrets still missing, never a credential value. For a draft missing secrets, the plan and the default result view name the steps that complete it: add them to the spec of `qctl get cloud-source <id> -o yaml`, apply that with `qctl apply -f`, then run `qctl enable cloud-source <id>`. After a copy, `-o json|yaml` masks secret fields unless `--allow-plaintext-secrets` is set.
- Cloud-source copies do not inherit secrets or URLs. The template lists the original-held fields in `secrets_to_resupply`, without their values. `s3_access_key` is not one of them: the template returns it, and the copy stores whatever the request sends. A draft can save without secrets and be configured before activation; active and disabled copies are connection-checked before saving and may fail without their secrets. [backend]
- A successful active cloud-source copy disables the target table's sole active upload source, which the plan names; a draft or disabled copy does not, nor does a copy given `--set table_series_id`. An active copy with a nonempty schedule starts polling; the plan uses the request's schedule, including a `--set` override. When the original has an applied delta cursor, the plan states that the copy starts without one. [backend]
- The server can still refuse a `copy cloud-source` after the plan and the confirmation, with a 400 (exit 2) that saves nothing and leaves the target table's upload source active. Whatever state the copy takes, it refuses a copy that would read the same files as an active source anywhere in the organization, the original included: the same location (bucket and endpoint, SFTP host, port and user, Dropbox folder, or URL) and the same value in every field the message names, so a `--set` that changes none of them does not get past it, even with `--state draft`. That error shows `Field: pattern`, or `excel_sheet_name` for `simple_url`, but changing any field the message names clears it. Two checks come last, after any connection check: an active copy into a table whose `data_loading_process` is `composite` is refused with `Field: state`, while a draft or disabled one passes, and a copy in any state is refused with `Field: name` when any source of the target table already holds its name, a deleted one included; choose another with `--name`. When that active copy would also disable the target's upload source, the name clash should come back as a 409 `Cloud source name is already used.` instead, also exit 2: this is reasoned from the handler, not observed. [backend]
- A `simple_url` that `--secrets-file` supplies to a copy must start with `http:` or `https:`, in lowercase, and a `schedule` must be valid cron, drafts included; qctl checks neither, and the server answers 400 `Invalid Simple URL` with `Field: custom_api_file_url`, or `Invalid Cron Value` with `Field: schedule`. An active or disabled copy is connection-checked with only the secrets the request supplies, and for `simple_url` the check sends the URL a HEAD request that must answer 200, or 307 with a `Location` that contains `googleusercontent.com`. A failed check, of any source type and for any cause, is one 400 (exit 2) with no `Field:` and the message `Could not connect to the copied cloud source. Check its connection settings and supplied secrets.`: unlike `apply`, a copy never shows the provider's own error. [backend]
- String lists in a manifest, including `spec.settings_overrides.null_values` and `null_values_per_column`, reject unquoted YAML null markers such as `NULL`, `null`, and `~` (and JSON `null`) with exit 2; quote a literal marker, for example `null_values: ["NULL"]`.
- An apply confirmation uses the current context's `organizationName` when its `organization` ID matches the selected org and the `organizations` cache has no name for it; a different uncached `--org` UUID still shows `Unknown`.
- `apply cloud-source` looks through every page of a table's name search before deciding that a source is new; names containing the manifest name do not count as an exact match.
- `describe cloud-source <id>` and `get cloud-source <id>` take a numeric ID, not a name, and reject anything else locally as bad usage (exit 2), before any API request; `qctl get cloud-sources --table <name>` lists the IDs.
- the two views of one cloud source answer different questions: `describe cloud-source` is the human summary — type, table, state, schedule, last ingest, row counts, unresolved alerts, and the names of the overrides that are set, never their values — and `qctl get cloud-source <id> -o yaml|json` is the apply-compatible manifest. `describe cloud-source -o yaml|json` emits the summary as a structured object, not a manifest; `describe` used to print the manifest, so a script that read it from there must switch to `get`.
- On a series source, `describe cloud-source` adds `Intake:`, the source's own `start_period_key` and `end_period_key` (`(none)` when unset), and `Broker due:`, its `broker_due_days` (`the series' schedule` when null). These are the stored values, not the periods the source is expected for or its due dates: `qctl get submission-statuses --cloud-source-id <id>` lists those. `-o json|yaml` carries the three under `intake`, each `null` when unset, and leaves `intake` out for a source outside a series. Change them in the manifest from `qctl get cloud-source <id> -o yaml`.
- A series source is expected for periods only while it is `active`: from the later of the series' `first_period_key` and its own `start_period_key`, whichever are set, through the earlier of its `end_period_key` and the period holding today, and for no period when neither is set. The server does not require `start_period_key` to be at or after the series' first period. Its broker due date is `broker_due_days`, else the series' broker due days, after each period ends, moved to the Friday before when that falls on a Saturday or Sunday. [backend]
- For an ordinary source with a positive quarantined-row count, `describe cloud-source` makes an extra count request scoped to that source: the Rows line adds passed/failed validation counts, Quarantine lists hold counts, including waiting for approval and any per-reason split, and Not loaded, when above zero, counts the duplicate copies a reviewer did not keep. `-o json|yaml` adds `quarantine_by_validation`, `quarantine_by_hold` and `quarantine_not_loaded`. A failed count read warns on stderr and omits all three; zero or unknown quarantined counts and all table-series sources skip the request and omit them too. Use `describe table <period-table-id>` to inspect a series period's table-wide breakdown.
- A cloud-source manifest exported with `-o yaml` or `-o json` preserves newline-only string values, literal `<<` keys in override maps, and control characters when re-applied.
- `describe cloud-source` names an override as set whenever it is not null: the backend applies every non-null `*_override` over the table setting whose name is the same without the suffix, which is the name the summary prints, and null means the source inherits the table's value. `false` and `""` replace the table's value; an empty list or map is set too but changes nothing, because a list override extends the table's list and a map override is merged into the table's map one key deep — so a `*_per_column` override replaces the table's whole entry for each column it names, and leaves the table's other columns alone. It never names `excluded_row_signatures`, the ledger of deleted rows' signatures, which is never null. [backend]
- the Alerts count in `describe cloud-source` is the source's unresolved alerts that are not row-level, so the row-level alerts on its quarantined rows are not in it; `qctl get alerts --table <t> --is-row-level` lists those, for every source of the table, except any parked for a migration, which only `--resolve-after-migration` lists. Both leave out every unresolved alert on a locked table-series period's table except a `series_file_routing` or `late_file` one. [backend]
- `describe cloud-source`'s Last ingest is when an ingestion job on the source last finished, a finished dry run included; a job that ends in error, is killed or is stopped does not move it, so a source whose every run failed shows `never`. [backend]
- the backend calls this a *data source*; `data-source` and `data-sources` work wherever `cloud-source` and `cloud-sources` name a command (`qctl get data-sources`, `qctl describe data-source <id>`, `qctl apply data-source -f cloud-source.yaml`), and in `qctl explain`, `qctl guide` and the `qctl create` redirect.
- `data_source_type` accepts exactly seven values, which qctl checks client-side before sending: `s3`, `s3_compatible`, `sftp`, `gs`, `dropbox`, `simple_url`, and `qluster_ui` — `s3_compatible` is the type for an S3-compatible store other than AWS S3, such as a self-hosted RustFS (it was called `rustfs`, and before that `minio`; neither is accepted), and `qluster_ui` is the type the platform auto-creates per table for files pushed in directly rather than fetched from a bucket, so you rarely write it yourself.
- `get cloud-sources --state` and `--states` accept only the states `qctl get cloud-sources --help` lists; any other value, an empty `--states` member included, is bad usage (exit 2) before a request is sent, and the error names the flag and lists the valid states.
- `--limit 0` means *unlimited* here, not "use the default": like `get files`, this listing auto-paginates client-side, so zero asks for every cloud source in the organization. Every other `get` command refuses `--limit 0` as a usage error. `--chunk-size` is a different knob — the per-request page size, minimum 1 — and it never caps the total.
- `spec.settings_model_id` is optional and you should normally omit it: `apply` reads the settings model from the table `spec.dataset_id` names and fills it in for you. Supplying one that belongs to a different table is refused with exit 2 before anything is created.
- `apply` substitutes a credential's `${VAR}` only when it is the entire field value; dollar signs in other credential values are kept literally.
- `delete cloud-source` is a SOFT delete: it sets the source's state to `deleted`, so `describe cloud-source` answers 404 afterwards and only `qctl get cloud-sources --state deleted` finds it — and the same call resolves every unresolved alert on the source, which `undelete cloud-source` does not un-resolve. Ingested rows and stored files are untouched. [backend]
- `undelete cloud-source` attempts recovery through `run-sensor-cronjob`, whatever the source's type — the endpoint `enable cloud-source` uses for a type with a sensor; there is no dedicated cloud-source recovery route. On current servers, that endpoint rejects a deleted source with 404 (exit 3) before it checks the type, so this recovery path is unavailable. Older servers may accept it: the source returns `active`, its resolved alerts stay resolved, and polling resumes if it has a schedule. [backend]
- `delete cloud-source` needs `source:delete`. The sensor routes used by `disable`, `run sensor-job`, `undelete cloud-source`, and `enable` on a type with a sensor need `dataset:ingest:launch` and check access to the source's table: admin and ops pass for any table in the organization; other permitted roles need a grant that is not read-only. Enabling an upload source (`qluster_ui`) uses the source update route and needs `source:edit` and, except for admin and ops, a grant on the table that is not read-only; an external caller is refused with 403 (exit 4), because that update sets `state`, which an external user cannot change. A permitted request still encounters the deleted-source checks, so `undelete cloud-source` remains unavailable on current servers. [backend]
- An external user's update may change only `schedule`, the parsing fields `csv_delimiter`, `csv_quotechar`, `csv_escapechar`, `encoding_probably`, `identify_header_by_column_names`, `raw_headers`, `chunk_size_to_read_for_header` and `ignore_column_ids`, and every `spec.settings_overrides` key; an `apply` that changes or clears any other field is refused with 403 (exit 4). [backend]
- `enable cloud-source` on a source that is already `active` is a no-op on the server: for a type without a sensor qctl writes nothing, and for a type with a sensor it still sends `run-sensor-cronjob`, but that route writes the state, checks the connection and runs the files guard only for a source that is not active, so on an active one it commits nothing, the ORM listener that deploys the cronjob does not fire, and a cronjob that went missing is not redeployed. On a source that is not active the write does fire it: with a schedule it queues a RUN whose deploy creates the cronjob or replaces the live one, and with no schedule it takes the listener's other arm and queues a KILL, which is why enabling an unscheduled source starts nothing. To redeploy a missing cronjob, disable the source, wait a minute, then enable it: the scheduler applies the disable's KILL asynchronously, but skips it if it finds the source active again, so it does not turn the source back off. If the enable's connection check fails, the source stays disabled. This is REASONED from the handlers and SQLAlchemy's `after_update` contract, not observed. [backend]
- Only six source types have a sensor: `s3`, `s3_compatible`, `sftp`, `gs`, `dropbox` and `simple_url`. For any other type, `run-sensor-job` and `run-sensor-cronjob` answer 400 `Source type <t> does not support sensor runs.`, so qctl refuses `run sensor-job` on one locally (exit 2), before its active check, and `enable cloud-source` turns an upload source (`qluster_ui`) on through the source's update route instead: it reads the source's `version_id`, then writes only `state: active` at that version, and if anything writes the source in between, the server answers 409 (exit 2) — run `enable` again. That update skips the connection check for `qluster_ui`, and nothing polls the source afterwards; files reach it through `qctl upload file`. [backend]
- A composite source belongs to the linked table that owns it: `enable cloud-source`, `disable cloud-source` and `run sensor-job` each refuse one locally (exit 2), naming that table, before any write. Neither of `enable`'s routes could turn one on — the sensor routes answer 400 for its type, and the update route's connection check answers 400 because there is no connection handler for `composite` — so `disable` refuses it too, since `enable` would not turn it back on. `undelete table` returns a linked table's composite source `disabled`, like every other source of the table except a table-series source, which stays deleted. [backend]
- a duplicate `run sensor-job` answers `409 ERR_QUEUE_KEY_CONFLICT` (500 on older servers) and says the queued run was moved nearer the top of the queue. qctl exits 2 for 409 and 1 for 500. [backend]
- the three sensor routes (`run-sensor-job`, `run-sensor-cronjob`, `disable-sensor-cronjob`) reject a deleted source with 404 before queuing or changing its state. After that, `run-sensor-job` answers 400 for a draft, and both run routes answer 400 for a source type without a sensor; `disable-sensor-cronjob` checks neither. qctl refuses deleted sources locally for `enable`, `disable`, `delete` and `run sensor-job` (exit 2), and `run sensor-job` also refuses a type without a sensor and then any source that is not active, so its disabled-source refusal is qctl's own: the server's manual sensor route still accepts a disabled source. The delete route has no state check and can return success for an already-deleted source. [backend]
- a cloud source that is not `active` rejects direct file uploads and dry runs with a 400 and is skipped by composite runs, drift watching and stuck-job healing — which is why `disable cloud-source` is wider than its name and why `run sensor-job` refuses a non-active source. [backend]
- creating an active non-`qluster_ui` source outside a table series in a table that has exactly one active `qluster_ui` source auto-DISABLES that `qluster_ui` source — an `apply` side effect on a source the manifest never names. `qluster_ui` is the type the platform auto-creates per table for files pushed in directly. [backend]
- `spec.state: draft` creates the source as a draft, and only a create takes it: `draft` is its only value, an update whose manifest carries `spec.state` exits 2 (change an existing source's state with `enable` or `disable cloud-source`), and `get cloud-source <id> -o yaml` puts the state under `status`, never `spec`. The server still checks a draft's `schedule`, its URL's scheme and that no active source reads the same files, but it neither connects to the source nor disables the table's upload source, and the later `enable` does not disable it either, so the upload source stays active. A draft saves without its secrets: qctl skips its own sftp and dropbox credential check for one, and a `simple_url` draft may leave out `simple_url`. `apply` then prints a `Next:` line: remove `spec.state`, add the secrets, apply again, then `qctl enable cloud-source <id>`. [backend]
- the server checks a cloud source's connection, with its stored secrets and any the request supplies, on an `apply` create that is not a draft, on every `apply` update of a source that is not a draft (a disabled one included, whichever fields change), and on `enable cloud-source` of a source that is not active. A failure is a 400 that saves nothing: a failed create does not disable the table's upload source, and a failed enable leaves the source as it was, so a draft stays a draft. An `s3` or `s3_compatible` source with neither `s3_access_key` nor `s3_secret_key` is checked and read unsigned, so a bucket that allows anonymous listing passes and a private one fails; a key a create leaves out is stored empty. [backend]
- a `simple_url` must start with `http:` or `https:`, in lowercase: any other is a 400 `Invalid Simple URL` on a create or an update, drafts included, and the error's `Field:` is `custom_api_file_url`, not `simple_url`. Its connection check sends the URL a HEAD request, which must answer 200, or 307 with a `Location` that contains `googleusercontent.com`; any other status, a timeout or an unreachable host fails the check with a 400. [backend]
- A table-series source carries the series' UUID in `table_series_id` and a `routing_mode` that picks each file's period table: `uploader_chooses`, `file_name`, `column` or `latest_unlocked`. `file_name` needs a `routing_pattern` holding `{period_key}` or both `{YYYY}` and `{MM}`, with no other, repeated or formatted placeholder and `{MM}` only on a monthly series, and `column` needs a nonblank `routing_column`. The server answers 400 (exit 2) to a missing or unknown `routing_mode` with a `table_series_id`, a pattern or column under another mode, any routing field without a `table_series_id`, a `composite` source, a template table (`dataset_id`, the table `get cloud-sources` shows) that is not an undeleted table of the series, and a create in a series holding an undeleted composite table. Only a create sets `table_series_id`: `apply` refuses a manifest that changes it, from null included, with exit 2 before any request, and the server answers 400 to one. [backend]
- A series source may set its intake's `start_period_key` and `end_period_key`, period keys in the format of the series frequency such as `2026-10` or `2026-Q4`, `broker_due_days`, its broker due date in days (0 to 366) after each period ends, and `export_request_days`, the day, in days (0 to 366) after each period ends with 0 its last day, of an email telling the series' followers to ask the sender for the period's export while no file has arrived for it: a null start follows the series' first period, a null end means the intake has no end, a null `broker_due_days` inherits the series schedule, and a null `export_request_days`, the default, sends no such email. The server answers 400 (exit 2) to any of the four on a source outside a table series and to an end period before the start period, and 422 (exit 2) to a period key not in the series frequency's format and to a `broker_due_days` that falls after the series' MGA deadline. [backend]
- Creating a series source, by `apply` or by `copy cloud-source --set table_series_id=...`, needs a grant on EVERY undeleted table of the series in the caller's organization, none of them `read_only`, or the server answers 403 (exit 4); admin and ops skip that check, and external cannot create a source. A non-external user's update, routing included, is checked against the template table alone, and an external user changing `routing_mode`, `routing_pattern` or `routing_column` gets 403. [backend]
- `get cloud-sources` shows a series source under its template table, and `--table` or `--table-id` naming any table of the series lists it too, beside that table's own sources. A user other than admin, ops or external sees a series source, in that listing and through `describe` and `get cloud-source <id>`, while holding a grant on any undeleted table of its series. `copy cloud-source` of a series source makes a source outside every series unless `--set` gives `table_series_id` and `routing_mode`, because the copy template leaves out all four series fields, and with them `start_period_key`, `end_period_key` and `broker_due_days`. [backend]
- `delta_applied_cursor` is server-managed status: the cursor of the last `upload file --delta` job that finished on this source, absent until the first one does. A table-series source keeps that cursor per period instead, so its own `delta_applied_cursor` stays absent. `get cloud-source <id> -o yaml` shows it under `status`, `describe cloud-source` on its `Delta cursor` line, and `get cloud-sources --columns id,delta_applied_cursor` lists it. It is not a `spec` field, so a manifest setting `spec.delta_applied_cursor` is refused before any request, and `apply` never sends it — the server ignores it on create and update in any case. [backend]
- A series source's `period_delta_cursors` lists current, undeleted period bindings in `period_key` order, each with `dataset_id`, `settings_model_id`, `period_key` and `delta_applied_cursor`. A null cursor means none has been applied; zero is valid. Unbound periods are omitted, while locked and disabled periods retain their cursors. Internal callers other than admin and ops see only tables granted in the current organization, including `read_only` grants; external callers authorized for the source see its bindings without a table-grant filter. Ordinary sources return an empty list. [backend]
- `get cloud-source <id> -o yaml|json` puts period cursors under `status.period_delta_cursors`; `describe cloud-source` shows a period/table/settings-model/cursor grid, with `-` for a null cursor, and `-o json|yaml` carries the list as `period_delta_cursors`. An empty list prints no grid. Cursor metadata is read-only: `spec.period_delta_cursors` is refused, and create, update and copy requests carry none.
- polling needs the source to be `active` AND its `schedule` to be non-empty; there is no separate polling switch. Only `schedule: ""` stops polling — `schedule: null` leaves the schedule as it is. [backend]
- `apply` on an existing cloud source reads it first, lists each change as SET, REPLACE or CLEAR with its old and new value — never a secret's value — and asks before sending anything; `--yes` (`-y`) skips the list and the question, and `-o json`, or a run with no terminal to ask on, exits 2 without it. `qctl diff -f` does not take a CloudSource, so answering no is how to preview. The update carries changed fields and, on a repointing update, supplied secrets, pinned to the version `apply` read: if something wrote the source's record in between — such as another `apply` or the web UI, `enable` or `disable`, an alert or warning resolution scoped to the source, or a `rows delete-quarantined --signature --exclude-from-future-uploads` scoped to the source or to one of its files outside a table series — the server refuses it with a 409, nothing is written, and `apply` exits 2 — re-run it to read the source again. Ingestion's own bookkeeping (row counts, Last ingest, the delta cursor) does not cause one, and a source deleted in between answers 404 instead. A manifest the source already matches sends nothing and reports `unchanged`, and a create is sent without a question. A manifest carrying a secret other than `s3_access_key` never matches, because the read masks every other stored secret and never carries `dropbox_authorization_code`: every apply sends it again, so leave it out to keep the stored one — except on an update that changes the source's type, location or file selection, which must send every stored secret again. Before sending a repointing update of a non-draft, apply refuses with exit 2 and lists every missing secret's spec key; set them using ${VAR} and re-run. For a draft, it warns on stderr before writing that omitted secrets will be cleared, including under --yes. A supplied simple_url is re-sent even when unchanged, supports ${VAR}, and is hidden in the change list; a URL already present in an exported manifest counts as supplied. [backend]
- the manifest is the source's whole desired state, and `key: null` counts as leaving the key out: on an update, every `spec.settings_overrides` key the manifest leaves out is CLEARED, putting the source back on the table's value, and so is a `csv_delimiter`, `csv_quotechar`, `csv_escapechar`, `routing_pattern`, `routing_column`, `start_period_key`, `end_period_key`, `broker_due_days` or `export_request_days` it leaves out; every other field it leaves out keeps its stored value, every secret and `schedule` included, and so does a secret whose `${VAR}` expands to nothing or that is still masked — except on an update that changes the source's type, location (bucket, endpoint, region, `s3_access_key`, SFTP host, port or user, Dropbox folder, URL) or file selection (pattern, prefix, folder, `archive_pattern`, `excel_sheet_name`): apply refuses a non-draft locally (exit 2) unless the manifest supplies every stored secret again, and warns that a draft loses each one left out; the server independently enforces resupply for non-drafts with a 400. An unedited `get cloud-source <id> -o yaml` re-applies with no changes for every source type. A new active sftp source needs `sftp_password` or `sftp_ssh_key`, and a new active dropbox source needs `dropbox_authorization_code`; on an update, the server exchanges a supplied Dropbox code for a new access token and answers 400 when Dropbox returns none. Re-applying an OLDER export undoes every override written since it was taken — one added since is cleared, one changed or cleared since goes back to the exported value — and every field it carries goes back the same way: alert and warning resolutions scoped to one source write overrides (`--action map_value_for_source` is one), as does the source's settings page in the web UI, and a `cant_sniff_header` fix writes `chunk_size_to_read_for_header`, `identify_header_by_column_names`, `raw_headers` or a `csv_*` field. An export made by a qctl without `spec.settings_overrides` carries no override and no `csv_*` field, so it clears every one the source has set. The change list shows each, and `apply` warns when the manifest's `status.id` is this source's and its `status.version_id` is older than the live source's. [backend]
- `spec.preload_row_drop_share` is the row-drop share of the pre-load check, greater than 0 and less than 1, and only ops may change it: an update that changes it answers 403 (exit 4) for every other role, admin included, while resending the stored value is accepted from any role but external, which is refused for sending the key at all. A create or copy cannot set it — the server ignores it there, so every new source starts at 0.2 — and although a null turns the check off on the server, `apply` treats `preload_row_drop_share: null` as leaving the key out and keeps the stored share. [backend]
- `spec.dropbox_access_token` is not a manifest key: writes take `spec.dropbox_authorization_code`, a Dropbox OAuth authorization code the server exchanges with Dropbox for the access token it stores, and `apply` refuses a manifest still carrying the old key before any request (exit 2), naming the new one. The read carries the stored token, masked, as `dropbox_access_token` and never carries the code, so `qctl explain cloud-source` marks `dropbox_authorization_code` `<write-only>` and `dropbox_access_token` `<read-only>`. [backend]
- `spec.settings_overrides` is keyed by the table setting's name, without the `_override` suffix of the wire name `qctl explain cloud-source` lists. Each key is also a key of a `kind: Table` manifest's `spec.settings_model` and pastes between the two, except `date_formats`, `date_formats_per_column` and `array_delimiters_per_column`, which the table's settings schema does not carry, so a Table manifest has no key for them. [backend]
- two things the server does on an update fire only when the update changes a value: a change to `ignore_column_ids`, or to the `fields_to_expand`, `infer_datetime`, `infer_datetime_for_columns` or `ignore_column_names` override, may queue the table to learn its schema again if the caller is not external, a file of this source is enabled for training, and the table has a draft migration or has files but no migration yet; and a change to `csv_delimiter`, `csv_quotechar` or `csv_escapechar` (an empty string counts as null) resolves the source's unresolved `cant_sniff_header` alerts the caller may resolve and requeues their unfinished ingestion jobs. `apply` predicts these effects from changed fields without checking the caller's role, enabled training data or migration state, and names them before it asks, or on stderr once the update succeeds under `--yes`. [backend]
- the change review policy of a cloud source's table governs `apply -f CloudSource` (operation `data_source_patch`, checked only on the governed fields the PATCH would change, so re-applying an unchanged manifest passes), `enable cloud-source` on a source with no sensor (the same PATCH, of `state`), and `enable cloud-source` on a sensor-eligible source, `undelete cloud-source` and `disable cloud-source` (`data_source_state_change`). A refusal is a 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4) whose `Hint:` names the operation and the refused keys and points at `qctl get change-review-policy --table <table>`; no key of these operations can be proposed, so `CHANGE_PROPOSAL_REQUIRED` never answers them. `copy`, `delete` and `run sensor-job` are not subject to the policy. [backend]
- On a portal (`qluster_ui`) source in a table series, `describe cloud-source` adds an `Email intake:` line: `on — <address>`, `off (keeps <address>)`, or `off` for an intake never turned on, then whether each loaded file's issues report is sent automatically; the summary ends with a `qctl get email-senders --cloud-source-id <id>` hint, and `-o json|yaml` adds `email_intake` with `enabled`, `address` and `auto_send_issues_report`. Any other source gets none of the three. The fields come from the same `GET /data-sources/{id}`, so the intake costs no extra request.
- Email intake exists only on a portal (`qluster_ui`) source in a table series: `enable email-intake`, `disable email-intake`, `email-intake rotate`, `get email-senders` and every `email-sender` command answer 400 (exit 2) for any other source. Every intake route refuses an external user with 403 (exit 4). Reading the intake and its senders needs `source:read`, and turning intake on or off and rotating its address need `source:edit`. [backend]
- The change review policy of the source's table also governs `enable email-intake` and `disable email-intake` (operation `email_intake_update`: key `enabled`, checked even when the state would not change, plus `auto_send_issues_report` when `--auto-send-issues-report` is given) and `email-intake rotate` (`email_intake_rotate`, key `address`). A refusal is a 403 `CHANGE_REVIEW_POLICY_DENIED` (exit 4) that changes nothing; no key of either operation can be proposed, so there is no change proposal to submit instead. The `email-sender` commands are not subject to the policy. [backend]
- `enable email-intake` gives the source an address only when it has none, and on every run — including one that only changes `--auto-send-issues-report` on an intake already on — schedules the welcome variant that carries the address to each assigned sender who has not had that variant from this source. It schedules nothing while the source is not `active`, skips a sender whose address is refused (the next enable tries again), and its output does not say which senders were mailed. [backend]
- `disable email-intake` keeps the address, and the next `enable email-intake` turns intake back on at that same address; only `email-intake rotate` replaces it. While intake is off, mail to the address is dropped without a reply. The intake accepts mail only from an assigned, active external sender, and only while intake is on and the source is `active`, so `Email intake: on` on a disabled source accepts nothing. [backend]
- `email-intake rotate` replaces the address and leaves intake on or off as it was. By default it schedules the new address to each assigned sender, whether or not intake is on, skipping any whose address is refused; `--no-notify-senders` schedules nothing. Mail to the old address is dropped from then on: while intake is on and the source `active`, a sender still assigned to it whose mail passes authentication is answered with the current address at most once per UTC day, and any other mail to it gets no answer. A source with no address is a 409 on the server. [backend]
- `email-intake rotate` reads the intake first and, before any prompt, exits 2 for a source with no address, and for an intake that is off unless `--no-notify-senders` is given, since an off intake accepts no mail at the address its senders would be sent. It then reads the senders so the prompt can name who gets the new address (up to 10); if that read fails it warns on stderr and asks anyway. It prompts unless `--yes`, exits 2 after that first read when there is no terminal to ask on, and honors protected contexts, so `--yes` does not replace `--context`. `enable email-intake` and `disable email-intake` never prompt.
- `enable email-intake`, `disable email-intake` and `email-intake rotate` take a cloud source id or `cloud-source/<id>`, print the intake as the server sent it under `-o json|yaml` (`email_intake_address`, `email_intake_enabled`, `auto_send_issues_report`) and `cloud-source/<id>` under `-o name`. `--auto-send-issues-report` is a boolean: bare or `=true` turns automatic issues reports on, `=false` turns them off, and leaving it out keeps the current setting — except on the `enable email-intake` that gives the source its first address, which turns them on unless the table's change review policy refuses you `auto_send_issues_report` — so to change only that setting repeat the verb of the intake's current state.
